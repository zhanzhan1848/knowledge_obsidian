# 3DCodeEdit: Benchmarking Instruction-Guided 3D Program Editing

> 📌 一篇**基准（benchmark）论文**，但它提出来的核心概念 —— **geometric foresight（几何预见性）** —— 是货真价实的几何问题：**代码能跑通，但造出的是错误的形状**。它把「LLM 写 Blender 程序」这件事，从「生成」推进到了「编辑」，而编辑恰恰是几何处理里最需要「先在脑中想象结果再动手」的场景。

## 技术概述

### 问题：从「生成」到「编辑」

**现状**：LLM 已经能通过写代码创造 3D 内容，但实际工作流往往**不是重新生成，而是编辑已有程序** —— 因为更快、且控制更精确。

**难点**（论文的核心论点）：
> 一次编辑要求模型 **理解程序构建了什么**，并 **预判一次改动会如何重塑它**。

**与既有基准的差别**：

| 既有基准范式 | 局限 |
|--------------|------|
| 评估**生成** | 只看结果好不好，不看「改」的能力 |
| 评估**简单编辑** | 与「参考答案」逐项对比，过于刚性 |
| **3DCodeEdit** | 覆盖参数级 → 结构级 → 风格级 → 场景构图级的编辑谱系；用**人工审核 checklist** 而非唯一参考答案 |

### 编辑谱系（Edit Taxonomy）

论文把编辑分为几个递进的难度层次（依摘要表述）：

| 层级 | 编辑类型 | 几何难度 |
|------|---------|---------|
| L1 | **参数级**（parameter） | 最低：改尺寸/比例，形状骨架不变 |
| L2 | **结构级**（structural） | 高：改拓扑/构件关系，形状本质改变 |
| L3 | **风格重设计**（style redesign） | 高：同一功能，不同几何语言 |
| L4 | **场景构图**（scene composition） | 最高：多对象的空间关系重排 |

### 关键发现：失败模式已从「代码错」迁移到「形状错」

> **「随着模型变强，它们的失败会转移到 geometric foresight —— 代码能跑，但构建出错误的形状。」**

这是本文最有价值的一句观察：
- 早期模型的失败是**语法/语义/API 错误** ⟹ 属于代码工程问题
- 强模型的失败是**几何/空间推理错误** ⟹ 属于几何问题
- ⟹ **「编辑程序化几何」的能力瓶颈，已经本质上是几何理解与几何预判的瓶颈**

### 核心问题：多轮反馈能否补上预见的缺口？

论文进一步研究：**多轮反馈（multi-turn feedback）**能否补偿缺失的几何预见性。

**结论**（摘要明确给出的对照）：

| 干预手段 | 相对效果 |
|---------|---------|
| **来自独立 reviewer 模型的反馈**（描述渲染结果与请求的差异） | **帮助最大** |
| **最大推理努力（maximum reasoning effort）** | 次之 / 不及反馈 |
| **agent harness（智能体外壳）** | 较弱 |

> **关键结果**：一个 **27B 模型**在多轮反馈下可以**超过 2.8T 参数模型的单轮成功率**。

### 评测方法学：渲染 + checklist

- **不是像素相似度**，也不是「与 GT 网格比对」
- 而是从**渲染结果**（多视角）出发，对照**人工审核的 checklist** 逐项判定
- ⟹ 评估的是**语义正确性**，能容忍实现细节差异

## 复杂度与性能

- **基准规模**：2,592 任务 / 108 个 Blender 程序 ⟹ 平均每个程序约 **24 条编辑指令**（推测）
- **模型覆盖**：17 个模型参与评测
- **总体成功率**：**平均仅 37%**
- **最强模型**：在**结构性编辑**与**风格编辑**上**完成率仍低于 60%**
- **参数级编辑**显然显著高于 37%（摘要以「最强模型仍低于 60% 的结构与风格编辑」反衬参数级更高）—— 具体数值摘要未给

## 数值稳定性

### ✅ 优势
- ✅ **渲染 + checklist 的评估方式**避免了「像素级对齐」的评价偏差 ⟹ 不惩罚合法的等价实现，评的是**几何语义是否正确**
- ✅ **17 模型、多层级编辑的广覆盖** ⟹ 结论「失败模式随模型能力迁移」是跨模型的系统性观察，而非单点现象
- ✅ **反馈源与被评模型分离**（独立的 reviewer 模型）⟹ 避免了「自己给自己打分」的循环论证，也避免了 reviewer 与 generator 同分布导致的共谋
- ✅ **27B + 反馈 > 2.8T 单轮** 这个结论**方向性地**说明：多轮反馈的价值大于单纯扩大模型规模（对参数量的判断有直接工程含义）

### ⚠️ 风险点
- ⚠️ **「geometric foresight」是一个事后归因（post-hoc attribution）的诊断标签**，而非被独立度量的量 ⟹ 「失败转移到几何预见」这一断言的严格性依赖失败分类的完备性与标注一致性；分类学本身是人工定义的，存在主观边界（例如「API 参数用错导致形状错」究竟算代码错还是几何错？）
- ⚠️ **checklist 是人工审核的** ⟹ 主观性、标注成本、以及「pass/fail 二值化」丢失了程度信息（一个 checklist 项部分满足如何计分？摘要未给细则）
- ⚠️ **Blender 程序这一载体本身带有强先验** ⟹ 结论是否迁移到 CAD（B-Rep）、CFD 或点云程序化编辑**未被验证**；「108 个程序」的覆盖面也限制了泛化性
- ⚠️ **结构/风格编辑的成功率天花板（约 60%）可能混入了「任务本身歧义」** ⟹ 即指令表述不清导致 checklist 不可判定。摘要未报告歧义率，也未报告人工一致性（inter-annotator agreement）
- ⚠️ **多轮反馈的成本未被量化** ⟹ 「27B 打败 2.8T」是成功率对比，若把 reviewer 模型的推理成本计入，结论可能反转。摘要未给 token / 时间开销
- ⚠️ **评审者模型的偏好偏差会被固化** ⟹ 若 reviewer 本身对「什么算好形状」有偏，多轮反馈会把编辑推向「reviewer 觉得对」而非「客观正确」⟹ 存在 reward hacking 式的过拟合风险

## 推荐结论

✅ **推荐（概念层面）**，但**几何方法层面无算法可复用**

### 理由
1. **它提出的问题在我们领域成立**：「程序能跑 ≠ 形状对」正是参数化建模、程序化城市/场景生成里反复出现的问题
2. **「geometric foresight」是一个可复用的分析框架** ⟹ 可用来诊断我们自己的程序化几何生成 pipeline：失败到底在代码层还是在形状层
3. **「多轮反馈 > 更大模型」是重要的工程结论** ⟹ 对参数预算受限的场景，直接的杠杆在**反馈机制**而非模型规模
4. **不推荐复现完整基准**的原因：涉及大量人工 checklist 标注；且评测对象是 LLM，不是几何算法

### 与本库几何工作的关系
- 与 [[2026-08-26-ViSculpt-Visual-Centric-Agentic-Geometry-Editing]] 同属「**由 agent 编辑 3D**」赛道，但 ViSculpt 直接编辑**网格**（视觉中心），3DCodeEdit 编辑**程序**（代码中心）⟹ **编辑对象的表示层不同** ⟹ 前者关心像素/几何结果，后者关心「程序 → 形状」的映射正确性
- 与 [[2026-10-27-2610-32978-SceneBloom-Agentic-Indoor-Environment-Generation]] 的 agentic 场景生成互补：SceneBloom 关心「生成」，本文关心「改」

### 落地建议
- 若我们做**程序化几何生成 / 参数化建模**的 LLM 工具 ⟹ 建议**借用它的诊断分层**（参数 / 结构 / 风格 / 构图），在我们的 pipeline 上做一次失败模式归因
- 若我们做**几何生成模型的评测** ⟹ 「渲染 + 人工 checklist」比像素指标更契合语义正确性，值得借用（尽管成本高）
- **具体实现建议**：把「代码能跑」与「形状对」拆成两级 gate —— 先做**执行成功**过滤，再做**几何语义**判定；两者混淆正是现有 LLM 评测的通病
