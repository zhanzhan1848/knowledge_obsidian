## 核心贡献

> Token-level LLM routing 把 cost-quality Pareto frontier 推到新水平，但现有系统存在严重 step desynchronization / 批延迟。TokenRouter 用 request-centric programming + model-centric execution + 数学 throughput model-derived delayed-batching，在多算法 × 工作负载 × 模型对上解码吞吐 **2.01–64.15×** 提升。

1. 提出 **TokenRouter**：为 token-level routed LLM inference 设计的 serving system。
2. 设计原则：**request-centric programming** + **model-centric execution**——开发者描述"单请求视角"的路由逻辑，runtime 自动启动 per-LLM subserver 并异步分发。
3. 数学 throughput model 导出 **delayed-batching scheduler** 的最优超参。
4. 在多 routing 算法 / 工作负载 / 模型对的组合上达到 **2.01–64.15× 解码吞吐** 提升。
5. NeurIPS 2026 接收。

## 技术方案

### 核心思想

Token-level routing 在算法上能更精细地分配 LLM 工作（便宜模型处理简单 token，昂贵模型处理关键 token），但实际系统挑战巨大：(1) 不同 model 速度不同造成 step desynchronization；(2) batch 接纳延迟严重；(3) 实现复杂度高。TokenRouter 通过**抽象分离**（编程视角 vs 执行视角）+**优化调度器**解决这些挑战。

### 关键技术

| 技术 | 说明 |
|------|------|
| Request-centric programming | 开发者从"单请求"角度写 routing 逻辑 |
| Model-centric execution | Runtime 为每个 LLM 启动 subserver，异步 dispatch |
| Delayed-batching scheduler | 数学 throughput model 导出最优超参，避免 batch 延迟 |
| Per-LLM subserver | 每个 LLM 一个独立 subserver，独立调度 |
| Cost-quality frontier | 在保证质量前提下最大化节省 |

### 系统架构

```
Developer → Request-centric routing logic
         ↓
TokenRouter runtime
  ├─ LLM_A subserver (delayed-batching)
  ├─ LLM_B subserver (delayed-batching)
  └─ LLM_C subserver (delayed-batching)
         ↓
Async dispatch per request
```

### 与 session-level routing 对比

| 维度 | Session-level | Token-level | TokenRouter |
|------|--------------|-------------|-------------|
| Cost-quality frontier | 较粗 | 精细 | **精细 + 系统支持** |
| Step desync | 不出现 | 严重 | **subserver 隔离** |
| Batch 延迟 | 中 | 严重 | **delayed-batching** |
| 实现复杂度 | 低 | 高 | **抽象分离降低** |

## 实验结果

- **吞吐提升**：**2.01–64.15×** vs 现有系统
- 跨多种 routing 算法（Cascade / FrugalGPT / Token-level 选择）均有效
- 跨多种工作负载（短 / 长 / mixed length）
- 跨多种模型对（大小模型组合）
- 已在 [GitHub](https://github.com/thu-nics/TokenRouter) 开源

---

## 关键 takeaway

- **算法突破需要系统突破**：算法上的 token-level routing 优势在没有专门系统的情况下无法兑现。
- **抽象分离**是降低复杂度的设计哲学：编程视角与执行视角分离，让开发者写简单代码，runtime 做复杂调度。
- **数学 throughput model → 调度器超参**：这是 serving system 优化的标准路径，值得其他场景借鉴。

---

## 局限性

- 局限于已训练好的多个 LLM 的组合；不支持在线添加新模型
- 吞吐提升幅度（最高 64.15×）依赖特定 routing 算法和模型对的搭配
- 单 subserver 的资源调度（多 tenant 隔离）尚未充分讨论
