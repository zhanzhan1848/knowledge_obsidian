# Redacting Personal Data: A Speed and Accuracy Comparison of Regex, Presidio and Hybrid Designs

## 摘要
许多企业项目会把自由文本（常含 PII：姓名、电话、邮箱、住址、出生日期）发给 LLM，一旦 prompt 发出，这些数据就被复制进供应商系统、应用日志与可观测性追踪。发送前做**脱敏（redaction）**是显而易见的控制手段，但团队很少有**延迟成本**与**漏出率**的数字。本文比较四种任何 LLM 管线都能采用的设计：**纯正则脱敏器**、**Microsoft Presidio**（跑在 spaCy 模型上）、**混合式**（Presidio 只找人名，正则处理结构化标识符）、以及**快速混合式**（直接调用 spaCy 的命名实体组件）。四者共享一条**已知实体规则**（移除系统已知正在处理的那个人）与一致的**占位符方案**（使 LLM 脱敏后仍能区分不同的人）。评测样例工作流 **ProfileAssist**（把简历转成结构化档案），使用 **100 份合成简历**（平均 523 字符，含 **900 个 PII 值**与 **600 个必须保留的业务术语**）。

## 核心贡献
1. 首次给出四种脱敏设计在**延迟与准确率**上的可比数字（纯正则 / Presidio / 混合 / 快速混合）
2. 设计公平对照：四者共享**已知实体规则**与**一致占位符方案**，确保 LLM 脱敏后仍能区分不同的人
3. 评测设定扎实：**100 份合成简历**（平均 523 字符，**900 个 PII 值**，**600 个必须存活**的业务术语）
4. 把「业务术语存活率」与「PII 漏出率」并列为指标，而非只看召回

## 方法与架构
**四种设计**：
1. **纯正则**（regex）；
2. **Microsoft Presidio + spaCy**；
3. **混合**：Presidio 仅找人名，正则处理结构化标识符；
4. **快速混合**：直接调用 spaCy 的命名实体组件。

**公平性控制**：
- **已知实体规则** —— 移除系统已知正在处理的那个人（四者一致）；
- **一致占位符方案** —— 脱敏后 LLM 仍能区分不同的人。

**评测工作流**：**ProfileAssist** —— 简历 → 结构化档案。

**语料**：100 份合成简历，平均 523 字符，**900 个 PII 值**、**600 个必须保留的业务术语**。

- 评测规模：100 份合成简历 / 900 个 PII 值 / 600 个必须存活业务术语

- 明确的工程结论：脱敏是**有成本的真实控制**，不是免费的安全动作

## 局限性
- 合成简历语料单一，真实业务文本（客服对话、日志）的分布差异未覆盖；
- spaCy / Presidio 的 NER 在非英语与罕见姓名上的表现未评估；
- 「已知实体规则」让评测比真实场景略简单（真实场景中已知实体规则往往不可用）。

## 值得注意的点
把「**600 个必须存活的业务术语**」与「900 个 PII 值」并列作为指标，是这篇的亮点 —— 脱敏的真正成本不是误报率，而是**把「销售总监」这类称谓误杀导致下游无法使用**。绝大多数脱敏评估只报前者。
