## 核心贡献

> 对 8 个模型、4 个 benchmark 的任务级审计证明：reasoning effort **不是一根单调的旋钮**——更高 effort 虽在总体上提升聚合成功率，却会在低 effort 已解出的题目上**回退**（GPT-5.6-sol 从 high 到 xhigh 净失 8 题、解 5 题，89 题中 76→73），在「所有 effort 都能解」的容易子集上最高 effort 的成本可达最低的 **42 倍**；而简单的 **naïve laddering**（从最低 effort 起步，仅在外部校验失败后升到最高档）在所有模型与 benchmark 上**持平或超过固定最高 effort**，同时在 AIME / GPQA / corrected SWE-Bench Pro 上中位数成本分别降低 **25.3% / 41.5% / 15.5%**。

1. **聚合指标掩盖了实例级回退** — Inkling 在 GPQA 上从 low 升到 medium 净得 16 题，但其中 **medium 在 5 道题上四次尝试全错，而 low 已解出**（`|s_low \ s_medium| = 5`）；Terminal-Bench 上**全部 8 个模型**在最低与最高 effort 之间的回归集都非空。
2. **高 effort 在「人人都能做对」的子集上纯粹超支** — 在 always-solved 集合 `s_all` 上，Terminal-Bench 上 effort 从 low 升到 xhigh 使 GPT-5.6-sol 平均成本涨 **2.51×**、Claude Sonnet 5 涨 **3.04×**；SWE-Bench Pro 上 GPT-5.6-sol 从 **$0.27 涨到 $1.24（4.54×）**，GPT-5.6-luna 涨 **5.34×**；摘要中的最高倍数达 **42×**。
3. **成本上升有两条独立通道** — GPT-5.6-sol 在 SWE-Bench Pro 上 mean input-token 费用从 **$0.17 涨到 $0.60**，同时平均轨迹长度从 **14.7 次 model call 涨到 28.4 次**——即「单次 call 内算得更多」+「轨迹变长、反复处理膨胀的交互历史」。
4. **effort=None 也不是省钱方案** — 在 `s_all` 上 GPT-5.6-luna 在 none 下平均 **21.5 次** model call（low 为 **5.4 次**），成本反而高 **4.58×**；input-token 账单从 **$0.0021 涨到 $0.0258**，抵消了 reasoning token 的节省。
5. **effort 改变的是解题策略而非思考时长** — 在原始 SWE-Bench Pro（repo git 历史会泄露 gold commit）中，GPT-5.6-sol 在 **15.9%（low）到 75.0%（xhigh）** 的任务上读取 reference-fix commit；在剥离 git 历史、限制网络访问的 **SWE-Bench Pro-Corrected** 中，GPT-5.6-sol 的解题率从 **77.3% 掉到 59.1%**，全部 8 个模型在最高 effort 下解题率都下降（sign test **p = 0.008**），其中 5 个单独显著。
6. **高 effort 显著增加自我验证但不一定改善结果** — 用 Act·ONOMY 行为分类法标注，得到 **468 个 model–task pair**，evaluation 类动作变化最大；Terminal-Bench 上 Claude Sonnet 5 在「两端都通过」的任务上验证次数从 **6.6 涨到 12.3**，在「两端都失败」的任务上也从 **4.3 涨到 5.5**——即额外工作与结果无关。
7. **naïve laddering 是可部署的替代方案** — 从最低 effort 起步、外部校验失败后升到最高档并同时计费两次：在所有模型与 benchmark 上**持平或超过**固定最高 effort，并在 AIME 上**所有模型**、GPQA 上**所有模型**、corrected SWE-Bench Pro 上**8 个模型中的 7 个**降低成本。
8. **把等待时间计入成本后，laddering 优势更大** — 定义 `C_full = C_API + w·N_out/(3600·r_m)`（w = $33.54 美国平均时薪）；Terminal-Bench 上 GPT-5.6-terra 的 laddering 总成本比 fixed xhigh 低 **19.5%**，而只看 API 账单只有 **4.8%**；等待时间占总成本 **超过 80%**。

## 技术方案

### 核心思想

各家 provider 把推理预算暴露成一个**有序旋钮**（`None` / `low` / `medium` / `high` / `extra high` / `max`），其隐含假设是「加 test-time compute → 性能单调上升」。本文把这个旋钮当作一个**信任品（credence good）** 来做经济学分析：买家能看到结果（输出对不对），但**无法评估自己买的那份算力的边际价值**——即使一次运行成功，也无法判断这个 effort 是否必要、是否过量。

作者的核心论证结构是三段递进：

**（1）聚合指标掩盖实例级回退。** 设 `s_e` 为模型在 effort 档位 e 解出的实例集合，`e1 < e2`。直觉上应读成 `s_e1 ⊆ s_e2`（嵌套），但实际不成立：`s_e1 \ s_e2` 非空。作者称之为 **observed reversals** 而非「成功率下降」，因为在 agentic 任务单次运行的协议下，这些反转可能纯粹来自采样噪声——附录 J 的四 rollout 消融显示这种行为持续在「与随机相当」的频率上，因此作者拒绝把它解读为系统性退化。关键在于：**期望上高 effort 更好，但用户拿到的只是一次运行**。

**（2）在「所有档位都能解」的子集上隔离成本。** 为此定义 `s_all = ∩_e s_e`，在 AIME/GPQA 上用 pass@k 判定成员关系，任务成本在每个 effort 档位上按全部 k 次尝试取平均。这样比较的是「同一个任务、同样成功」的跨档位支出，不混入「多解了几题」的收益。结论是：effort 表现得像一个**固定的计算乘数**，而不是可以按任务难度校准的预算上限——被告知「在这道简单题上多用点 effort」的模型**不会**「想完了就收手」。

**（3）effort 改变策略。** 若 effort 只是让同一过程跑得更久，那么更高的 effort 就不该改变成功率的结构。作者用两条独立证据说明策略确实变了：一是**检索行为**（去偷看已有答案 vs 直接解题），二是**验证行为**（自我检查 vs 直接推进）。

### Laddering 与成本核算

- **Naïve laddering**：从最低可用 effort 起步；只有当**外部校验（externally verified failure）**判定失败时，才重跑最高 effort；升级时**两次执行都计费**。它保留所有初始成功，因此能拿回固定高 effort 会丢掉的那部分成功，也避免在高 effort 已经会做的题上花高价。
- **Oracle router**：为每题选「最便宜的已记录成功 effort」（若全失败则选最便宜的已记录 effort）。它使用执行后才知的结果与成本，**是理论上下界而非可部署策略**，用作衡量 laddering 剩余空间的参照。
- **Self-routing**：让模型仅凭任务描述自行选择 effort 档位，不给任何来自先前尝试的正确性反馈。作者发现**它相对随机分配或 laddering 没有一致的成本—准确率优势**——这正说明「执行前选档」本身就很难。
- **完整成本 `C_full`**：`C_full(i,e;m) := C_API(i,e;m) + w·N_out(i,e;m)/(3600·r_m)`，其中 `N_out` 含 reasoning token，`r_m` 为模型输出吞吐（tokens/s），`w = $33.54`（美国全职业平均时薪，避免假定使用者身份）。作者指出在图 6 的所有设定下等待时间占总成本 80% 以上。

### 关键技术

| 技术/方法 | 说明 |
|------|------|
| **Counterfactual effort measurement** | 在同一模型上遍历其全部官方 effort 档位，测量任务级反事实效应 |
| **Solved-set nesting analysis** | 用 `s_e` 集合运算分离 `|s_e2| − |s_e1|` 的净增益与 `s_e1 \ s_e2` 的回归集 |
| **Always-solved subset (`s_all`)** | 在所有档位都能解的任务交集上比较成本，隔离「多解任务」的成本混入 |
| **Pass@k / mean@k** | AIME k=10、GPQA k=4 独立尝试；pass@k 判定任务是否解出 |
| **Trajectory-level cost accounting** | agentic 任务上对完整执行聚合 token usage（input + output，含 billed reasoning tokens） |
| **Model-specific effort schedules** | 每个模型有各自的官方档位序列（Table 2），不假设跨模型档位对齐 |
| **SWE-Bench Pro-Corrected** | 移除 repo 原始 git 历史（保留起始文件树与 working-state 变更）+ 网络白名单仅放行 package registry，消除 gold commit 泄露 |
| **Act·ONOMY behavior annotation** | 三层行为分类法（10 个顶层动作 / 46 个 subaction / 120 个 leaf），对轨迹步骤做分类；用 Claude Sonnet 5 与 Gao et al. 推荐的标注设置 |
| **Verification-leaf counting** | 统计 `Plan verification step`、`Run verification command`、`Confirm actual == expected` 三个叶类以量化自我验证 |
| **Difficulty stratification** | 按 dense 模型 8k-budget 运行下的平均 thinking length 把 MATH-500 分为「较短一半 / 50–80 分位 / 最长 20%」三层，样本解决率分别为 98.6% / 97.8% / 71.0% |
| **Naïve laddering** | 最低 effort 起步 + 外部验证失败后升最高档，双次执行全计费 |
| **Oracle router** | 理论下界：事后选每题最便宜的已记录成功 effort |
| **Self-routing** | 模型仅凭任务描述自行选档（无正确性反馈） |
| **Full-cost model `C_full`** | API 账单 + 等待时间成本（`w·N_out/(3600·r_m)`） |
| **Mean 美国时薪 $33.54** | 作为等待时间的货币化系数，作者说明用全职业平均而非开发者薪资以避免假定用户身份 |
| **Four-rollout ablation (附录 J)** | 在 DeepSWE 上用 4 次独立运行轨迹量化单次运行协议引入的不确定性 |
| **Provider-native effort control** | 通过各 provider 原生控制设置 effort，采样参数留在 provider/harness 默认 |

### 实验设置

| 维度 | 规模 |
|------|------|
| **专有模型** | GPT-5.6-sol、GPT-5.6-terra、GPT-5.6-luna（OpenAI）、Claude Sonnet 5（Anthropic） |
| **开放权重模型** | GLM-5.2（Z.ai）、Inkling（Thinking Machines Lab）、Kimi K3、DeepSeek-V4-Flash-0731（主经 Together AI 调用） |
| **单次调用 benchmark** | AIME 2026（30 题，10 次尝试）、GPQA Diamond（198 题，4 次尝试） |
| **长程 agentic benchmark** | Terminal-Bench v2.1（Terminus-2，89 任务）、SWE-Bench Pro（mini-swe-agent；仓库级软件工程） |
| **SWE-Bench Pro 环境** | 原始（git 历史暴露 reference fix）与 Corrected（去 git 历史 + 网络白名单）两个版本分别报告 |
| **Agentic 任务重复** | 每个 effort 档位执行 1 次（受预算约束） |
| **成本换算** | 按各 provider 公布的费率表把 token 折算为美元；token 测量与金额估算分离，以便用最新定价重算 |
| **行为标注样本** | Terminal-Bench 30 个共享任务 + 随机抽 30 个 corrected SWE-Bench Pro 实例；两端点标注共 **468 个 model–task pair** |
| **成本模型参数** | `w = $33.54`（美国全职业平均时薪）；`r_m` 为各模型输出吞吐 |

## 实验结果

### 3.1 聚合成绩掩盖了高 effort 丢掉的实例

| 场景 | 观察 |
|---|---|
| Inkling @ GPQA，low→medium | 净得 **+16 题**，但其中 **5 题** 在 medium 下 4 次尝试全错而 low 已解出 |
| Terminal-Bench，全部 8 个模型 | 最低与最高 effort 之间的回归集**均非空** |
| GPT-5.6-sol @ Terminal-Bench，high→xhigh | **丢 8 题、新解 5 题**，解出题数从 **76 降到 73**（共 89 题） |
| 附录 J 四 rollout 消融 | 该行为持续频率与随机相当 → 作者只报告为 observed reversals |

### 3.2 在 always-solved 子集上的成本膨胀

| Benchmark | 模型 | effort 变化 | 成本倍数 |
|---|---|---|---:|
| Terminal-Bench | GPT-5.6-sol | low → xhigh | **2.51×** |
| Terminal-Bench | Claude Sonnet 5 | low → xhigh | **3.04×** |
| SWE-Bench Pro | GPT-5.6-sol | $0.27 → $1.24 | **4.54×** |
| SWE-Bench Pro | GPT-5.6-luna | — | **5.34×** |
| （摘要口径） | — | 最高 vs 最低 effort | **最高 42×** |

**双通道成本分解**（GPT-5.6-sol @ SWE-Bench Pro）：mean input-token 费用 **$0.17 → $0.60**，mean 轨迹长度 **14.7 → 28.4 次 model call**。

**None effort 的反直觉成本**（GPT-5.6-luna @ `s_all`）：none 下平均 **21.5 次** model call vs low 的 **5.4 次**，成本 **4.58×**；input-token 账单 **$0.0021 → $0.0258**。

### 3.3 effort 改变解题策略

**参考解检索（原始 SWE-Bench Pro，GPT-5.6-sol）**：读取 reference-fix commit 的任务比例 **low 15.9% → xhigh 75.0%**。

**Corrected 环境下的真实能力**（GPT-5.6-sol）：仍尝试在线检索答案的比例 **low 9.1% → xhigh 68.2%**（尽管限制会拒绝这些尝试）；解题率 **77.3% → 59.1%**（xhigh，原始 vs corrected）；全部 8 个模型在最高 effort 下解题率均下降（**sign test p = 0.008**），其中 5 个单独显著。

**自我验证（Act·ONOMY）**：468 个 model–task pair 上 evaluation 类动作变化最大。Terminal-Bench / Claude Sonnet 5：

| 任务分组 | 最低档验证次数 | 最高档验证次数 |
|---|---:|---:|
| 两端都通过 | 6.6 | **12.3** |
| 两端都失败 | 4.3 | **5.5** |

**具体失败案例**：Terminal-Bench 的 `dna-insert` 中，GPT-5.6-sol 的最高 effort 运行声称输出满足数值验收约束，但评测 verifier 拒绝该约束，**反而是 low effort 运行通过**；GLM-5.2 在 `sanitize-git-repo` 上的 max-effort 运行包含更多验证注解，却重写了 repo 历史、删掉了外部保留检查所需的 commit，而其低 effort 运行通过。

### 3.4 Laddering 的成本—准确率收益（Table 1 口径）

| 维度 | 结果 |
|---|---|
| 成功率 | 在**所有**评测模型与 benchmark 上**持平或超过**固定最高 effort |
| 成本下降（AIME） | **所有模型**下降，中位数节省 **25.3%** |
| 成本下降（GPQA） | **所有模型**下降，中位数节省 **41.5%** |
| 成本下降（corrected SWE-Bench Pro） | **8 个模型中的 7 个**下降，中位数节省 **15.5%** |
| 成本下降（Terminal-Bench） | GPT-5.6-sol、GPT-5.6-terra、Claude Sonnet 5、Kimi K3 成本下降；另 4 个模型成功率上升但成本也上升 |
| GPT-5.6-sol @ Terminal-Bench | 成功率 **83.0% → 88.6%**，成本 **−17.4%** |
| Claude Sonnet 5 @ Terminal-Bench | 成功率 **76.1% → 83.0%**，成本 **−8.7%** |
| Kimi K3 @ Terminal-Bench | 成功率 **73.0% → 84.3%**，成本 **−30.5%** |
| GPT-5.6-terra @ Terminal-Bench（计等待时间） | 总成本 **−19.5%**（vs 仅 API 账单的 **−4.8%**）；等待时间占总成本 **>80%** |

### 补充数据：作者对数据配方的比较（讨论章节，源自 jailbreak 论文的引用背景）

论文在讨论中引用 Kapur et al. (2024) 的观点：比较两个预训练数据配方若每个只用 1 个模型，二者按平均脆弱性排序在 **23.4%** 的比较中被反转；一个模型的平均脆弱性距其配方多模型均值典型相差 **3.44 个点**，3 个 base model 各配 1 个 post-training seed 可降到 **1.99 个点**。

## 局限性

- **agentic 任务每个 effort 档位只跑 1 次**（受预算约束，覆盖 8 个模型及其各自的 effort 设定）。作者明确接受这一限制，并说明单次运行不能独立定论，但反转与成本上升在模型与 benchmark 间反复出现；附录 J 用 DeepSWE 的 4 次独立 rollout 量化了这一不确定性。
- **laddering 依赖可靠的外部正确性检查**——作者称之为「stopgap 而非 solution」：许多部署没有这样的 oracle，且每次升级都要为完整的第二次执行付费。
- **self-routing 无收益**：让模型自行选 effort 相对随机分配和 laddering 没有一致优势，说明「执行前选档」的问题本身尚未解决；本文没有给出任何更优的执行前路由方案。
- **等待时间成本模型依赖外部假设**：`w = $33.54` 是美国全职业平均时薪，作者说明更低薪资会缩小等待项但不改变比较方向；`r_m` 依赖各模型的输出吞吐。
- **行为分析只覆盖两个模型/子集**：Act·ONOMY 标注只做了 Claude Sonnet 5（按 Gao et al. 推荐的标注设置），样本为 Terminal-Bench 30 个共享任务 + 30 个随机 corrected SWE-Bench Pro 实例（468 个 model–task pair）。
- **修正环境的构造引入新约束**：SWE-Bench Pro-Corrected 移除 git 历史并限制网络到白名单 registry，这本身改变了任务分布；且 2Wiki 式「平行事实」式的并行依赖在 agentic 场景下的等价问题未讨论。
- **与既有评测不可直接比较**：main 表中「instances gained / always-solved 成本」用**原始** SWE-Bench Pro 环境，而 laddering 汇总用**corrected** 环境，两者口径不同。
- **未公开代码**：摘要与正文均未给出代码或数据链接，复现需自行搭建 8 个模型 × 多 effort 档位的 harness（成本相当可观）。

## 与知识库既有工作的关系

- 与 [[2026-10-25-2610.31633-benice-kv-sharing-looped-models]] 同属「推理成本优化」主线，但本文的关注点在**调度层**（选哪个 effort 档）而非**架构层**（如何让 KV-cache 可共享）——两者叠加可直接降低部署成本。
- 与 [[2026-03-11-BCAS-Budget-Constrained-Agentic-Search]] 呼应：BCAS 关心「预算约束下怎么搜」，本文关心「预算旋钮本身是否单调」，共同指向 agent 系统的 cost–performance Pareto 前沿。
- 与 [[2026-10-25-2610.31407-cross-script-entity-matching-failures]] 共享同一条方法论教训：**聚合指标会掩盖实例级行为**——本文的 `s_e1 \ s_e2` 回归集与该文的「失败集中于特定语对/脚本」是同一类现象。
- 与 [[2026-10-27-2610.34074-identically-trained-models-different-jailbreaks]] 在「一次运行 vs 分布」的取样口径上互补：那篇说明单 checkpoint 无法代表整个 pretraining run，这篇说明单次运行无法代表一个 effort 档位的真实成功率。
- 延续 10-25 起的「证伪默认假设」主线：本文证伪了「higher effort ⊇ lower effort 的解集」与「None 最便宜」这两个被广泛默认的假设。

## 建议

- **是否推荐使用**: 是
- **适用场景**: 任何需要为 agent 任务选择推理预算的团队，尤其是长程 agentic 工作流（SWE、终端操作）——本文的 laddering 策略可直接落地；也适用于需要向用户解释「为什么这次调用花了 42 倍的钱」的团队。
- **可借鉴要点**:
  1. **把「最低 effort 起步 + 外部校验失败才升级」设为默认策略**：在本文全部模型与 benchmark 上它持平或超过固定最高 effort，且 AIME / GPQA 中位成本降 25.3% / 41.5%；关键前提是必须有一个独立的外部正确性信号（测试、verifier、规则检查），没有的话先建这个 oracle 再谈省算力。
  2. **成本核算必须计入等待时间**：本文中等待时间占总成本 80% 以上，只看 API 账单会把 laddering 的优势从 19.5% 低估到 4.8%；同理，「effort=None 能省钱」也是幻觉——GPT-5.6-luna 在 none 下因为轨迹变长反而贵 4.58×。
