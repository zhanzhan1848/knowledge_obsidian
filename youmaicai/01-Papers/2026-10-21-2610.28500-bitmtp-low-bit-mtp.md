## 核心贡献

> **算法-系统协同设计**框架：在超低比特（1–2 bit）LLM 骨干上实现高效 MTP。关键洞察是**超低比特骨干与 MTP 直接组合会互相抵消收益** —— masked drafting 缺少 next-token 训练提供的中间 token 输入，而更宽的计算与因果 KV 更新又会吃掉步数减少的节省。

1. **联合 NTP + MTP 训练目标**：单一模型同时具备 AR 生成与 block-causal drafting 能力
2. **三种解码模式**：confidence-only / speculative-only / hybrid，提供不同质量-吞吐工作点，**无需独立 draft + verifier 模型**
3. **Accepted-prefix alignment 契约**：保证已提交前缀、物化的因果 KV 边界、CUDA Graph replay 状态三者一致
4. **宽度专用低位执行 + 图复用**：在共享 KV 存储上复用捕获的 CUDA Graph

---

## 技术方案

### 为什么直接组合会失败

| 失效来源 | 机制 |
|---------|------|
| masked drafting | 缺少 next-token 训练时提供的中间 token 输入 |
| 更宽的计算 | 抵消减少解码步数的收益 |
| 因果 KV 更新 | 同上 |

### 解法

| 组件 | 作用 |
|------|------|
| 联合 NTP + MTP 目标 | 单模型双能力：AR 生成 + block-causal drafting |
| 三种解码模式 | quality-throughput 可调，无双模型开销 |
| Accepted-prefix alignment | 维护「已提交前缀 / 物化 KV 边界 / CUDA Graph replay 状态」的契约一致性 |
| 宽度专用执行 + 图复用 | 低位算子按宽度特化，共享 KV 存储复用图 |

## 实验结论

### NVIDIA H20（hybrid decoding，五任务平均）

| 骨干 | 加速比 |
|------|--------|
| BitNet b1.58-2B | **2.2x** |
| Bonsai 1.7B – 4B | **2.1x – 2.4x** |

任务质量 comparable。

### 其他硬件

| 硬件 | 加速比 |
|------|--------|
| RTX 3090 | 最高 **2.0x**（五任务平均吞吐） |
| Jetson Orin | MBPP+ 上 **3.3x** |

覆盖不同骨干、模型规模与 GPU 类型均有效。

---

## 局限性

- 依赖特定超低比特骨干（BitNet / Bonsai），对标准 FP16/BF16 模型的收益未验证
- 需要较窄的硬件支持（低位算子 + CUDA Graph），可移植性待评估
- 三种解码模式的切换策略未在摘要中给出

## 实现建议

- **实现难度**: 高（需要低位 kernel + CUDA Graph 状态管理）
- **预期性能**: H20 上 2.1–2.4x，边缘设备 Jetson Orin 上 MBPP+ 达 3.3x
- **适用场景**: 边缘/端侧部署（1–2 bit 骨干）、显存极度受限的推理
- **建议起点**: 关键在 accepted-prefix alignment 契约 —— 这是正确性前提而非优化，先复现这一状态一致性保证
