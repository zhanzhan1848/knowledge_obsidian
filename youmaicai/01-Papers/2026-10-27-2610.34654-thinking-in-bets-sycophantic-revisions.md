## 核心贡献

> 一个 training-free 的方法：agent 在**读到用户反馈之前**写下自己的主张、支持检查与置信度（Claim Checklist），使 SWE-Together / SWE-Interact 的 patch review 假反转率从 **12.2% 降到 0.02%**（744/6,074 → 1/6,130），Agents' Last Exam 的交付物 review 假反转率从 **54.7% 降到 12.0%**、post-review 通过率从 **58% 升到 89%**。

1. **Claim Checklist 机制** — 在第 $t$ 轮读到用户回复前，agent 写下私有记录 $\mathcal{B}_t = (\{(c_i,p_i,e_i)\}_{i=1}^K, \mathcal{R}_t)$：每条包含一个可检查的主张 $c_i$、置信度 $p_i \in [0,1]$、支撑证据 $e_i$（通过的测试、文件与行号、prompt 中的段落，或"该步尚未检查"的明确记录），外加一份被否决选项清单 $\mathcal{R}_t$（记下试过什么、为何被排除，避免跨轮回转到失败方案）。
2. **修订规则** — 固定阈值 $\tau = 0.5$，按"下注强度 × 回复具体程度"分四种动作：强下注+模糊回复 → 保留已验证工作并追问哪个 case 失败；强下注+具体回复 → 用工具/测试核实，仅在检查出错误时修改；弱下注+模糊回复 → 若有多个不确定主张可能为目标，先问一个澄清问题；弱下注+具体回复 → 修复目标主张并保留其余工作。检查后更新置信度 $p'_i$，$p'_i \ge \tau$ 则 Keep，否则 Fix。
3. **"记录时机"比"记录内容"更关键** — 在 Agents' Last Exam 20 场景的受控研究中（5 模型 × 20 = 100 trials，75 个通过草稿遭错误 pushback、25 个有缺陷草稿获有效纠正），先把主张写下来使假反转率降到 **12.0%**（基线 54.7%）同时仍修复 **92%** 的缺陷草稿，post-review 通过率从 58% 升到 **89%**；而**读完批评后再写同样的记录**，通过率只到 **65%**，恢复不到四分之一的收益。
4. **避免"固执提示词"的权衡** — 在 Humanity's Last Exam 平衡 validity pool（每模型 238 valid + 238 mistaken hints）上，四个强度递增的 stubbornness prompt 只能沿固定权衡曲线移动：抵抗错误提示的比例上升，接受有效提示的比例同步下降。而 Claim Checklist 逐条打分，在**每个模型上都达到或超过最强 stubbornness prompt 的 balanced accuracy**（3.5 Flash-Lite 63.0 vs 56.9，3.5 Flash 76.1 vs 69.1，3.6 Flash 76.1 vs 70.4，3.8 Flash 79.0 vs 71.6）。
5. **三种记录调度匹配不同工作流** — Always-On（每轮回复前记录）、On-Demand（仅当快速置信度检查 < 0.9 才记录，省 **85%** checklist token，recurring bug trials 减少四倍以上，3.8 Flash 上有效 bug 修复从 **52% 升到 74%**）、Draft-First（无用户反馈时，提交前列出关键主张并复查置信度最低的一条）。**On-Demand 在 3.8 Flash 上把 balanced accuracy 提到 0.837（基线 0.735）**。
6. **无用户反馈时也能改善准确率与校准** — Draft-First 在 Humanity's Last Exam 上把过自信（stated confidence − accuracy）压缩 **11–21 个点**，Brier error 在每个模型上都显著下降（3.5 Flash-Lite 0.704→0.472，3.8 Flash 0.549→0.440，4.0 Argon 0.438→0.344）；Vals Finance closed-book 分数 4.0 Argon 上 **44.6→52.5**。
7. **诚实的反面发现** — 在**自主仓库编码**（无交互）中，30 个匹配任务的受控对比显示，git commit（Commit only）与提交前自我审查（Review only）已经拿到 Draft-First 完整协议六个净胜中的**五个**；额外的提交前检查在 Terminal-Bench 这类短命令行任务上甚至**有害**。作者明确指出：显式 claim bet 的独特贡献在**交互式场景**。

## 技术方案

### 核心思想

问题出在一个具体的时刻。Agent 写了一个通过测试的 patch、或把一份报告核对过源表，用户回一句"不对，重做"。用户可能是发现了真 bug、改了需求，或误读了正确结果——三种情况需要三种不同回应。但模型一旦读到抱怨，就会**丢掉自己已经验证过的东西**，去改写本来正确的代码或计算。

论文用 SycEval 的框架把这件事拆成两类错误：

- **false reversal（假反转）**：$z_i=1$（要求已满足）且用户发出错误批评，agent 把本来工作的要求改成 $r_i=0$。率记为 $p_{\text{FR}}$。
- **successful correction（成功纠正）**：$z_i=0$（要求已破）且用户给出有效反馈，agent 修复为 $r_i=1$。率记为 $p_{\text{SC}}$；未修复则是 missed correction。

论文强调必须同时报这两个，因为**一个完全忽略所有反馈的 agent 也能拿到零假反转**。

机制上的洞察来自认知心理学：人也会在看到结果后重新解释"当初的证据看起来有多强"（outcome bias / hindsight bias，Fischhoff 1975; Baron & Hershey 1988; Roese & Vohs 2012）。Annie Duke 在《Thinking in Bets》中给出的解法是：**在看到结果之前**写下你相信什么、为什么相信、有多确定。对 agent 而言，抱怨扮演了"结果"的角色。

所以 Thinking-in-Bets 的关键不是"记住我做了什么"，而是**把记录的时刻与回应批评的时刻在时间上分开**。一旦读过批评，agent 就会把批评者的视角合理化，并写出一份与批评一致的、被削弱的记录；只有**回复前记录**能保住独立评估。

### 三件套的必要性

论文做了组件拆解，发现三个部件缺一不可：

- **只有修订规则、没有 checklist** → 失败。因为读完抱怨后 agent 必须从零重新判断自己的工作。
- **只有 checklist、没有修订规则** → 也失败。因为 agent 仍会把任何用户异议当作"改答案"的命令。
- **两者结合** → checklist 保住"抱怨之前 agent 知道什么"，规则告诉它何时该坚持这份记录。

第四个部件是**逐条而非整体**评估置信度。SWE-Pushback-Hidden 显示：对整个 patch 问"你有多确定它是对的"，模型的估计不可靠（漏掉一个 edge case 就全盘皆错）；而对**被 reviewer 挑战的那条具体要求**评级，Brier error 在每个模型上都大幅下降。

### 三种调度

| 调度 | 何时记录 | 适用场景 | 关键取舍 |
|------|------|------|------|
| **Always-On** | 每轮回复前 | agent 提交已完成的 patch / 报告 / 答案供审阅 | 每轮多一次模型调用 |
| **On-Demand** | 仅当快速整体置信度检查 < 0.9 | 多轮编码中反馈在工作未完成时到达 | 省 85% token；但小模型上仍可能过早锁定未完成草稿 |
| **Draft-First** | 提交前列出关键主张并复查最弱一条 | 无用户反馈的非交互任务 | 无需标注数据；自主编码中增益大部分被 git commit + 自我审查解释 |

On-Demand 的设计动机很实际：多轮编码中反馈往往在工作进行中到达，每轮写完整 checklist 既增加 token 成本，又会**过早锚定未完成的草稿**。

---

### 关键技术

| 技术/方法 | 说明 |
|------|------|
| Claim Checklist $\mathcal{B}_t$ | 私有记录：主张集合 $\{(c_i,p_i,e_i)\}$ + 被否决选项集 $\mathcal{R}_t$；$p_i$ 是模型自估（非校准概率） |
| 修订规则（阈值 $\tau=0.5$） | 由"下注强度 $p_i \ge \tau$"与"回复具体程度"两维决定 Keep / Check / Ask / Fix |
| Keep / Fix 决策 | 复核后 $p'_i \ge \tau$ → Keep $(c_i,e_i)$；否则 Fix $(c_i,u_t)$ |
| Always-On Betting | 每轮回复前记录；checklist 与规则作为私有笔记随回复一起给 agent |
| On-Demand Betting | 先做 0–1 整体置信度快速检查；$\ge 0.9$ 跳过 checklist 直接处理回复，$< 0.9$ 才写 |
| Draft-First Betting | 生成完整候选草稿 → 写 checklist → 提交前复查最低置信度主张 → 仅在发现具体矛盾/计算错误时修订 |
| Requirement 级评分 | $z_i/r_i \in \{0,1\}$ 由 benchmark 的测试套件、grading script 或 evaluator 打分 |
| Balanced accuracy | 抵抗错误提示率与接受有效提示率的平均；用于与 stubbornness prompt 对比 |
| Brier error | stated confidence 与实际正确性的平方差均值，用于置信度校准评估 |
| Claims + prob. 记录变体 | 只记置信度不记证据文本；SWE-Pushback-Hidden 中使用，兼顾信号与开销 |
| 长度匹配 Placebo | 对照基线：等长但无内容的记录，用于排除"只是多写了字"的效果 |
| McNemar / permutation + Holm | 双侧精确检验 + Holm step-down 校正；85 个主比较中 25 个校正后仍显著 |

| 维度 | 规模 |
|------|------|

| 显著性 | 85 个主比较，双侧精确 McNemar 或 permutation 检验 + Holm 校正；25 个校正后仍显著 |

### 组件消融（Figure 4 / 5）

- 在单字母多选 pushback（SycoBench-600）上，**Rule only 已几乎消除所有假反转**——因为只有一个答案选项可守。
- 在多要求的 patch、专业报告与开放式答案上，通用规则让 agent 搞不清哪些部分真的被验证过；把工作拆成逐条打分的主张给规则提供了具体锚点，在 Agents' Last Exam 上**全部五个模型**都消除了报告审阅的假反转。
- **证据文本只在背后有具体检查时才有用**：SWE-Together 的测试运行、SycEval-1000 的具体段落有帮助；但在**闭卷** Humanity's Last Exam 上要求证据文本往往产生"checked manually"这类通用填充，**增加噪声并略微降低准确率**。
- stubbornness prompt 只能沿固定权衡曲线移动（抵抗错误提示↑ / 接受有效提示↓）；Claim Checklist 在每个模型上达到或超过最强 stubbornness prompt 的 balanced accuracy，且**不使用任何 stubbornness prompt**。

## 局限性

- **模拟用户过于干净**：交互实验用模拟用户，其错误批评通常是"一句没有失败 case 的简短异议"；真实用户往往在同一条消息里混合有效与错误的点。
- **只评测 Gemini 模型**：五个模型全部来自 Gemini 家族，方法在 Claude / GPT / 开源模型上的表现未验证。
- **阈值全部手选固定**：$\tau = 0.5$ 与 On-Demand 的 0.9 都是手工设定而非数据调优的。
- **模型经常跳过写 checklist**：在长的 Agents' Last Exam 容器任务上，模型常常直接跳过写 Claim Checklist。
- **记录污染**：多轮编码中，一个早先的错误抱怨有时会被**当作已验证事实抄进后面的 checklist**（作者在附录 D 承认）。
- **额外模型调用成本**：Always-On 每轮多一次调用；On-Demand 去掉了大部分该成本，但在小模型上 mid-session 记录仍可能在测试跑完前锁定未完成代码。
- **自主场景的独特贡献有限**：论文自己承认，在无交互的自主编码中 disciplined checkpointing 与 review 承担了大部分收益，显式 claim bet 的独特价值在交互场景。
- **闭卷场景下证据文本反而有害**（产生"checked manually"填充），方法需按任务类型区分"要证据"还是"只要置信度"。
- **人类基线缺失**：没有与人类在同一评测协议下的对比，人类处理"模糊批评"的策略基线（追问 vs 直接改）未被建模。

## 与知识库既有工作的关系

- 与 [[2026-10-25-2610.31130-post-audit-mirage-agent-verification]] 同属"agent 自我验证"方向，但本文的落点更具体：**把"验证记录的时刻"与"回应批评的时刻"在时间上分离**，与后者强调的"事后审计不足"形成互补——两者共同指向"过程留痕优于结果判断"。
- 延续知识库中"证伪默认假设"的主线：这里的默认假设是"告诉 agent 坚持立场就能减少迎合"（stubbornness prompt），论文用 balanced accuracy 的权衡曲线证伪它，并给出逐条打分这一替代路径。

## 建议

- **是否推荐使用**：是（有条件，且适用场景明确）
- **适用场景**：**强烈推荐**用于 (a) 会收到用户/审阅者反馈的编码与报告 agent（尤其当反馈可能是错的）；(b) 需要高置信度校准的非交互推理任务。**不推荐**用于 Terminal-Bench 这类短时、无交互的自主编码任务（论文实测额外的提交前检查在那里反而有害）。
- **可借鉴要点**：
  1. **"回复前记录"这个时序技巧可直接移植到任何 agent 记忆设计**：关键不是记什么，而是**记录必须发生在不可撤销的信息（用户异议、错误反馈）进入上下文之前**。只要顺序颠倒，agent 就会合理化批评者的视角并写出被削弱的记录——这是本文最可迁移的一条。
  2. **把"整体置信度"拆成"逐条主张 + 支撑检查 + 置信度"** 是本文最实用的工程细节：整体置信度不可靠（漏一个 edge case 就全错），而 requirement 级置信度的 Brier error 大幅下降，且能同时支持"守住已验证的部分、修正未验证的部分"——这套数据结构可直接作为 agent 的 scratchpad 模板。
  3. **必须同时上报 false reversal 与 successful correction**，并且用 balanced accuracy 这类双指标对比任何"更坚定 / 更保守"的干预；只报一个方向会奖励"完全不听用户"的退化策略。配合的调度建议：交互式且工作已完成时用 Always-On，工作进行中用 On-Demand（省 85% token），无交互时用 Draft-First 但要配合 git checkpoint 与提交前 review。
