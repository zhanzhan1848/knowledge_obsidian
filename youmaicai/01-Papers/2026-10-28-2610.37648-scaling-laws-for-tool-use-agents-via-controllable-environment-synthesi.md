## 核心贡献

> **工具使用能力的数据配方，第一成分不是「任务数量」而是「环境多样性」** —— 本文给出了第一个关于工具使用 agent 泛化性的**可控环境合成 scaling law**。

1. **提出 SynthAPI 管线**：**显式控制**所生成环境的**多样性维度** —— **工具（tools）、任务（tasks）、工具所操作的数据库（databases）** 三轴。
2. **大规模实证**：
   - **458,752 个任务**
   - **849 个训练模型**，**4 种不同尺寸**
   - 系统性地变化 SynthAPI 的生成控制变量
3. **核心贡献 —— Scaling Law**：推导出一条**能预测下游工具使用 agent 泛化性能**的 scaling law，**基于所合成环境的规模与构成（scale and composition）**。
4. **三条数据扩展教训**：
   - **数据预算增长时，扩大「工具多样性」与「数据库多样性」比增加任务数量更有效**
   - **提高数据复杂度带来更大的收益**
   - 按这些发现去扩展，得到的 agent **在四个评测基准上优于先前工作（大规模工具使用 agent 与合成环境生成）训练出的模型**

---

## 技术方案

### 核心思想

训练工具使用 agent 需要「环境 + 任务 + 轨迹数据」。以前的合成方法的问题是**不可控**：你不知道生成的数据里工具多样性够不够、数据库多样性够不够，只能盲目生成。

SynthAPI 把这三个轴**变成显式的旋钮**，然后系统扫描 → 拟合出 scaling law。

```text
SynthAPI 旋钮:
   ┌─ 工具多样性   (tool diversity)      ─┐
   ├─ 任务多样性   (task diversity)      ─┼─▶ 可控生成 458,752 任务
   └─ 数据库多样性 (database diversity)  ─┘        │
                                                      ▼
                          849 个模型 (4 尺寸) 系统扫描
                                                      ▼
                              Scaling Law: 泛化性能 ~ f(环境规模, 环境构成)
```

### 关键技术

| 技术 | 说明 |
|------|------|
| **SynthAPI 管线** | 可控的多样性生成 |
| **工具多样性轴** | 生成环境中的工具种类/接口多样性 |
| **任务多样性轴** | 任务组合的多样性 |
| **数据库多样性轴** | 工具所操作后端数据库的多样性 |
| **系统扫描** | 系统性变化生成控制变量 |
| **Scaling Law 拟合** | 泛化性能对环境规模与构成的预测关系 |
| **复杂度提升** | 提高生成数据的复杂度 |

## 公式

```math
\text{Scaling Law 形式（示意）}:\quad
\mathcal{P}(\text{gen}) \;=\; f\Big(
\underbrace{N_{\text{task}}}_{\text{任务数}},\;
\underbrace{D_{\text{tool}}}_{\text{工具多样性}},\;
\underbrace{D_{\text{db}}}_{\text{数据库多样性}},\;
\underbrace{C_{\text{complexity}}}_{\text{复杂度}}
\Big)
```

```math
\text{边际效益对比（核心教训）}:\quad
\frac{\partial \mathcal{P}/\partial D_{\text{tool}}}{\partial N_{\text{task}}}
\;\gg\; 1
\quad\Longrightarrow\quad
\text{多样性扩张优于任务数扩张}
```

```math
\text{复杂度效应}:\quad
\frac{\partial \mathcal{P}}{\partial C_{\text{complexity}}} \;>\; 0
\qquad \text{且随数据预算增大而增强}
```

```math
\text{可控合成（形式化）}:\quad
\mathcal{E} \;=\; \mathrm{SynthAPI}(\theta_{\text{tool}},\; \theta_{\text{task}},\; \theta_{\text{db}},\; \theta_{\text{cx}})
\quad \text{其中 } \theta \text{ 为显式多样性旋钮}
```

## 代码片段

```python
# 概念性伪代码：SynthAPI 的受控环境合成
import random
from dataclasses import dataclass

@dataclass
class SynthesisControls:
    # 显式的多样性旋钮 —— 本文的核心。
    n_tools: int = 5               # 工具多样性
    n_databases: int = 3           # 数据库多样性
    n_task_templates: int = 50     # 任务多样性
    complexity: float = 0.3        # 数据复杂度（多跳数、条件数等）
    seed: int = 0


def synth_api(ctrl: SynthesisControls, n_tasks: int):
    # 按可控旋钮生成环境 + 任务。
    rng = random.Random(ctrl.seed)

    # 1) 生成工具集（受 n_tools 控制）
    tools = sample_tool_schemas(rng, ctrl.n_tools)

    # 2) 生成数据库集（受 n_databases 控制）
    databases = sample_databases(rng, ctrl.n_databases)

    # 3) 生成任务（受 n_task_templates × complexity 控制）
    tasks = []
    for i in range(n_tasks):
        tpl = rng.choice(ctrl.n_task_templates)
        db = rng.choice(databases)
        tool_subset = rng.sample(tools, k=rng.randint(1, ctrl.n_tools))
        task = instantiate(tpl, db, tool_subset,
                           n_hops=complexity_to_hops(ctrl.complexity))
        tasks.append(task)
    return {"tools": tools, "databases": databases, "tasks": tasks}


def derive_scaling_law(sweep_results):
    #     从系统扫描结果拟合 scaling law:
    #     P_gen ~ f(N_task, D_tool, D_db, C_complexity)
    # sweep_results: list of (controls, n_tasks, generalization_score)
    X = np.array([[r.n_tasks, r.D_tool, r.D_db, r.C_complexity] for r in sweep_results])
    y = np.array([r.gen_score for r in sweep_results])

    # 对数空间拟合幂律
    coef, *_ = np.linalg.lstsq(np.log(X), np.log(y), rcond=None)
    exponents = dict(zip(["N_task", "D_tool", "D_db", "C_complexity"], coef))

    # 关键对比：多样性指数 vs 任务数指数
    assert exponents["D_tool"] > exponents["N_task"],         "工具多样性的边际收益应高于任务数"
    assert exponents["D_db"] > exponents["N_task"],         "数据库多样性的边际收益应高于任务数"
    return exponents
```

## 实验结论

- **规模**: **458,752 个任务**，**849 个训练模型**，**4 种模型尺寸**
- **基线**: 先前工作的大规模工具使用 agent 与合成环境生成方法
- **结果**:
  - 得出**预测下游泛化的 scaling law**
  - **数据预算增长时，扩展工具与数据库多样性 > 增加任务数量**
  - **提高数据复杂度带来更大收益**
  - 按此扩展训练出的 agent **在四个评测基准上优于先前工作的模型**

## 局限性

1. **Scaling law 的具体形式未给** —— 摘要只说「推导出一条 scaling law」，**公式与指数完全缺失**，这是本文最核心的产出却无法从摘要获取
2. **基准名称未列** —— 「四个评测基准」不知是哪四个，跨基准泛化性无法判断
3. **模型规模细节缺失** —— 4 种尺寸是多少？若最大只到 1-2B，scaling law 的外推性存疑
4. **合成环境与真实环境的差距** —— 合成环境上的 scaling law **能否外推到真实工具 API**？这是最关键的未回答问题（分布偏移）
5. **“先前工作”的具体对象不明** —— 对比的基线是谁
6. **生成成本未给** —— 45 万个带轨迹的环境，生成算力开销可能巨大
7. **单团队单方向** —— 与 [[LinMix]]（[[2610.37390]]）的数据混合 scaling law 形成有趣对照，但本文缺方法论层面的讨论
8. **复杂度的定义不明** —— “数据复杂度”可以指多跳数、条件分支数、工具参数复杂度，差别很大
9. **无消融说明** —— 三条轴（工具/任务/数据库）的边际贡献如何分解？只有「多样性 > 任务数」的粗结论

- **实现难度**: 高（需要一个可控的合成环境生成器 + 大规模训练/扫描基础设施）
- **预期性能**: 摘要称优于先前工作模型，**但缺具体数值与基线名**
- **适用场景**: **需要训练工具使用 agent、且工具 API 有限**（企业内部 API、私有工具集）—— 此时「环境多样性」的扩展空间是真实瓶颈
- **落地注意**:
  1. **先读正文拿 scaling law 的形式** —— 这篇的价值几乎全在那条公式上，摘要无法替代

## 我的评注

> 这篇最有价值的产出，恰好是摘要给得最少的 —— 那条 scaling law 的形式。但**它给出的三条行动指南已经足够有指导性**：
>
> 1. **数据预算变大时，扩展「工具多样性」和「数据库多样性」优于堆任务数** —— 这条与直觉相符但很少被明确验证。原因是显然的：任务数再多，也只是在同一套工具/后端的组合空间里打转；泛化到新工具需要的是**工具空间本身的覆盖**。
> 2. **提高复杂度收益更大** —— 也是显然的：简单任务教会的是表面模式。
> 3. **两者结合可超过先前工作** —— 这条的实用价值最高。
>
> 方法论上我很喜欢 **SynthAPI 的「显式旋钮」思路**。过去做合成数据最大的问题是黑箱 —— 你生成了一堆数据，但不知道成分是什么，因此也无法做有意义的消融。把工具/任务/数据库三个轴变成**可控参数**，才可能做 849 个模型 × 45 万任务这种规模的系统扫描。这个规模本身就是贡献。
>
> 保留意见：
> - **摘要缺公式**，这是硬伤。这类的核心产出是那条曲线和指数，光有「diversity > quantity」的口号，落地时不知道往哪加预算。
> - **模型规模没给**。849 个模型、4 种尺寸 —— 如果最大只到 1-2B，那么「scaling law」在小规模上拟合出来的曲线，未必在 7B+ 仍成立。这在 LLM 领域是反复出现的陷阱。
> - **合成 → 真实的外推是最大的空白**。真实工具 API 有 Schema 噪声、错误信息、非幂等性、并发问题，这些在合成环境里通常被理想化掉。
>
> 但如果只记住一件事：**做合成数据时，把预算花在「环境多样性」而不是「样本数量」上**。这个结论本身现在就值得用。
