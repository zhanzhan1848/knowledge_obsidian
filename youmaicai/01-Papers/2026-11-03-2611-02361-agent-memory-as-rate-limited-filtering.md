## 核心贡献
1. **可执行基准**：构建一个关于授权（grants）、取款（withdrawals）、撤销与恢复（reinstements）、过期（expiries）、分组（groups）和变更窗口（change windows）的**可执行**基准，策略已知；评分基于**只在一个顺序或一个字段上不同**的历史对，即"仅改变决定性事件顺序或单个字段"的对照设计。
2. **核心实证发现**：开放模型（7B–32B）在 **8 或 16 个事件**后准确率为 **72%–86%**，到 **256 个事件**后跌至 **48%–55%**；而**推理训练**的 32B 模型**读取当前状态（explicit state）**可达 **96% 和 98%**。
3. **"读者依赖的视界"（reader-dependent horizon）**：**120B 的推理模型**在 256 与 512 事件时分别落后显式状态 **4 和 7 个百分点**，在 1,024 事件时落后约 **10 个百分点**——即"显式状态超过长上下文的长度随读者能力增长"。
4. **记忆即递归滤波的理论框架**：决策只通过一个状态依赖于历史，而状态大小由**被跟踪的键的数量**决定。存储少于状态所需条目的 store 会以**由容量决定的时间尺度**遗忘；阅读器模型能在注册测试中以**平均 0.02** 的误差预测其准确率。
5. **严格的信息论下界**：若保留日志行而不顾时间顺序，错误概率趋近**二分之一**，且该界**可达（attained）**。
6. **写入时按依赖筛选优于查询时筛选**：一个在查询时选出被查询状态所依赖行的 retriever，在第一个域的 256 事件处与写入时筛选**打平**——真正起作用的是"按状态的依赖关系做选择"，而这是 filter 在**写入时**（不需要查询）就完成的工作。
7. **跨域冻结复现**：在第二个域用全新措辞做**冻结复现**，重现了同一个视界。

## 问题背景
核心问题：能否让一个读取了完整访问日志历史的语言模型，判断某项服务**现在**是否可以行动？这是一个典型的 agent memory 问题——长期运行的服务必须记住大量事件日志，并在当前时刻做出准入判断。现有 agent memory 方案（向量检索、模型自维护的账本、Mem0 一类记忆库）通常把"记住"和"读取"混为一谈，隐含假设检索能找到相关片段。但摘要指出的结构性事实是：决策所需的不是历史本身，而是历史**折叠后的状态**，且状态的大小由跟踪键的数量决定。更根本的问题在于"折叠"这一步应发生在哪一侧——写入时还是查询时——以及长上下文的**容量**与**时间顺序**这两个独立的失效来源。

## 方法
### 基准设计
可执行基准覆盖授权、取款、撤销、过期、分组、变更窗口，策略（policy）已知。评分使用**配对历史**：两条历史只在**决定性事件的顺序**或**其中一个字段**上不同，其余完全相同。这使配对差异与模型的记忆能力严格对应，而非与任务难度混合。

### 记忆作为递归滤波（形式化）
$$\text{state}_{t} = f(\text{state}_{t-1}, \ \text{event}_t)$$
决策仅通过状态依赖于历史：
$$\text{decision} = g(\text{state}_T)$$
其中状态大小由**被跟踪的键的数量**决定。由此推出两条关键结论：
- 若 store 持有的组件记录数**少于**状态所需，则必然遗忘，且遗忘时间尺度**由容量决定**；
- 阅读器模型的准确率可被预测（注册测试中平均误差 **0.02**）。

### 各类记忆机制对照
| 方法 | 机制 | 关键结论 |
|---|---|---|
| 长上下文阅读 | 读取全部历史 | 随事件数衰减（72–86% → 48–55%） |
| 显式状态 + 推理模型 | 读取当前状态 | 96%、98%（32B）；120B 落后 4/7/约10 点 |
| 保留日志、不管顺序 | 纯追加 | 错误概率趋近 **0.5**（界可达） |
| 解析 + 显式规则更新（filter） | 写入时解析每行，规则应用更新 | 256 事件处 **80%–89%**，优于相关检索、模型自维护账本、StateMem 重实现、Mem0 库 |
| 查询时依赖选择 retriever | 查询时选出被查询状态依赖的行 | 256 事件、第一个域与 filter **打平** |
| 直接应用解析后的更新 | 模型自行应用更新 | 跌至 **58% 和 59%** |

### 关键设计洞察
filter 的核心是"由模型解析每一行、由显式规则应用更新"（a filter in which a model parses each line and an explicit rule applies the updates）。它在 256 事件时达到 **80%–89%**，并**优于**：相关检索（relevance retrieval）、模型自维护账本（model-kept ledgers）、StateMem 的重实现、以及 **Mem0 库**。

### 与"读取时"的对比
一个在**查询时**选择"被查询状态所依赖的行"的 retriever，在第一个域的 256 事件处**与 filter 匹配（matches it）**。作者的推论是：起决定作用的是**按状态的依赖关系做选择**；而 filter 之所以有效，是因为它**在写入时**（无需知道查询）就完成了这一选择。

### 跨域冻结复现
在第二个域采用全新措辞做**冻结复制（frozen replication）**，重现了同一个视界（horizon），说明视界不是第一域的偶然产物。

## 实验结果
### 长上下文 vs 显式状态（开放模型 7B–32B）

| 读取方式 | 事件数 | 准确率 |
|---|---|---|
| 完整历史（长上下文） | 8 或 16 | **72% – 86%** |
| 完整历史（长上下文） | 256 | **48% – 55%** |
| 显式状态（推理训练 32B） | — | **96%** |
| 显式状态（推理训练 32B，另一设置/模型） | — | **98%** |

### 读者依赖的视界（120B 推理模型 vs 显式状态）

| 事件数 | 120B 推理模型落后显式状态 |
|---|---|
| 256 | **4 个百分点** |
| 512 | **7 个百分点** |
| 1,024 | 约 **10 个百分点** |

即：长上下文超过显式状态的长度**随读者（模型）能力增长**。

### 记忆机制对照（256 事件）

| 方法 | 准确率 |
|---|---|
| Filter（模型解析 + 显式规则更新） | **80% – 89%** |
| 查询时依赖选择 retriever | 与 filter 匹配（第一个域） |
| 模型直接应用解析后的更新 | **58%** 和 **59%** |
| 长上下文（开放模型） | 48% – 55% |
| 无视时间顺序保留日志 | 错误概率趋近 **0.5**（界可达） |

### 其他定量结果
- 阅读器模型准确率预测误差：**平均 0.02**（注册测试中）。
- Filter 优于的基线：相关检索、模型自维护账本、StateMem 重实现、Mem0 库（摘要未给出各基线的具体数值）。
- 跨域（第二域、全新措辞、冻结复现）重现同一视界。

## 关键洞察
1. **"显式状态优于长上下文"存在一个可测量的、由读者能力决定的临界长度**，而不是一个普遍常数。32B 推理模型在显式状态上几乎无损（96–98%），而 120B 模型在 1,024 事件处落后约 10 点——更大更聪明的读者**能**从长上下文中挤出的信息更多，但也**不是无限**。这直接反驳了"上下文窗口够大就不需要 agent memory"这一常见论断的前提假设：能力与容量是不同的轴，二者的交点会移动，但不会消失。
2. **时间顺序是一个不可绕过的信息通道**。无视时间顺序地保留日志行，错误概率趋近 **0.5**（二分之一，即随机），且该界可达——这是一个干净且可达的下界，说明**内容保留不等于信息保留**，顺序本身就是承载决策信息的那部分。这意味着单纯的"把更多历史塞进上下文"或"存更多日志"在时间敏感任务上可能完全没有收益。
3. **状态大小由跟踪键数量决定，而非由历史长度决定**——这把"长上下文 vs 记忆"的争论从 token 预算问题转化为**状态维度问题**。一个只有几十个键的服务，其状态是可枚举的；一个键数随用户数增长的服务，状态本身会爆炸，此时 filter 的容量约束会先于上下文窗口成为瓶颈。
4. **写入时筛选 vs 查询时筛选的真正差别在于"是否需要知道查询"**：查询时依赖检索能打平 filter（在第一个域），这说明检索质量问题（选错行）而非"写入还是查询"的时机，才是主要差距来源。这是一个反直觉的结论：**先存后查**并不天然劣于**边写边查**，只要写入时能完成正确的依赖选择。
5. **"模型自己应用更新"是最差的一档（58–59%），甚至远差于长上下文（48–55%）在某些情形下**：模型被委派了"折叠"这个它并不擅长的动作。把状态更新交给**显式规则**（而非模型）是整套方法的关键。这与本文标题"Rate-Limited Filtering"的核心主张一致：记忆系统的瓶颈在写入侧的折叠带宽。
6. **可预测性**：注册测试中阅读器准确率可被以平均 0.02 的误差预测，说明"某模型在某长度下能记住多少"是**可先验估计**的工程量，可以用于容量规划。

## 局限性
- 摘要未给出：所用模型的具体名称与规模清单（仅提及 7B–32B 开放模型、32B/120B 推理模型）、具体域的规模（授权/取款等各有多少类）、事件类型全集、每个域的历史长度设置（8/16/256/512/1024）、准确率的统计方差与置信区间。
- 基准是**合成的可执行**基准（授权/取款/分组/变更窗口），虽然可执行，但领域相对窄，摘要未说明与真实服务访问日志（如云 IAM、支付风控）的结构差距。
- "读模型达到 96%/98%"的显式状态读取方式中，状态是如何构造的（是否由 filter 提供？）存在**方法间的强耦合**——如果 32B 推理模型读的状态正是 filter 产出的状态，则显式状态与 filter 的比较并非完全独立；摘要描述上两者是分列的对照，但耦合关系未澄清。
- 关于"state 的规模由键数决定"与"store 容量小于状态时以容量决定的时间尺度遗忘"的关键论断，摘要**未给出具体实验数字**来支撑（如容量-遗忘曲线的参数）。
- 视界（256/512/1024 的具体交叉点）在不同模型上只给出了 32B 与 120B 两点，**未确定性地刻画"视界随读者增长"的关系**，更像是趋势观察。
- 跨域复现只报告"重现了同一视界"，未给出第二域的具体数值。
- 未评估写入侧成本（解析每行的 LLM 调用开销）与延迟——这恰是"filter 在写入时做选择"这一主张的代价所在，摘要未报告。
- 隐私与合规维度（记忆中的 PII、审计可追溯性）未讨论，而这是 agent memory 的核心实务问题。

## 适用场景
- **长运行 agent / 服务准入判断**：需要根据完整访问日志判断"此刻是否允许行动"的 IAM、权限管理、风控、审计系统。
- **访问控制与策略执行**：策略已知且可编码为显式规则时，把折叠交给规则、交给模型只做解析，是低风险的分工。
- **容量规划**：用"读者模型准确率可预测（误差 0.02）"来为不同规模的模型估算状态跟踪所需的记忆预算。
- **状态键数有限的可记忆系统**：键数量可控（几十到几百）的服务可完全用显式状态替代向量检索；键数无界时需先做键选择。
- **对比与评估框架**：作为评估 agent memory 方案（Mem0、StateMem 类、向量检索、长上下文）的可执行基准范式。
