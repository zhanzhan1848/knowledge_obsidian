# PriorityFEC: Deadline-Aware Streaming FEC for KV-Cache Handoff in Edge Multi-Agent Systems

> **arXiv**: [2610.21390](https://arxiv.org/abs/2610.21390)
> **发表日期**: 2026-10-15
> **分类**: cs.NI (及交叉分类 cs.AI)
> **会议/期刊**: arXiv preprint

## 📋 摘要

边缘端协同部署的大语言模型系统常常需要把任务上下文在多个 agent 之间转交，每次转交都要重新做一次 prefill 计算。复用已经算好的 KV cache 可以消掉这部分冗余开销，但前提是接收方 agent 必须等 KV cache 完整送达才能开始解码。而在严格的时延截止期（deadline）与不可靠的边缘链路下，完整传输整个 KV cache 往往不可行——真正关键的是在截止期内"及时送达有用的那部分 KV 信息"。本文提出 PriorityFEC，一个效用感知（utility-aware）的 KV-cache 交接方案，把「优先级源传输」与「自适应丢包恢复」结合起来。方案先把 KV block 组织成效用感知的源队列（source queue），让重要信息优先发送；随后用 ACK 滑窗 Streaming FEC 配合一个轻量级的 Double Deep Q-Network（Double-DQN）调度器，在截止期约束下动态平衡源数据传输与修复（repair）传输的开销。作者在分布式边缘 LLM 服务原型上实现了 PriorityFEC，用 Qwen2.5-7B-Instruct 与 Llama-3.1-8B-Instruct 在多种工作负载下评测：相比其他传输方案，PriorityFEC 保留了更多有用的 KV 信息，并在"截止期不足以传完整个 KV cache"时取得显著更高的任务准确率。

## 🎯 核心贡献

1. **问题重构**：把边缘多 agent 之间 KV cache 交接重新定义为「在严格截止期与不可靠链路下的效用最大化传输问题」，而非单纯的完整性传输问题——承认"传不完"是常态。
2. **PriorityFEC 传输方案**：效用感知源队列（优先发高价值 KV block）+ ACK 滑窗 Streaming FEC（低成本冗余保护）+ Double-DQN 调度器（自适应分配源数据与修复数据的带宽）。
3. **无模型改动**：完全在传输层工作，不需要修改 LLM 结构或重新训练模型，可直接接入现有的边缘 LLM 服务栈。
4. **端到端验证**：在真实的分布式边缘服务原型上、用 Qwen2.5-7B-Instruct 与 Llama-3.1-8B-Instruct 评测，指标直接对齐下游任务准确率而非单纯的传输吞吐量。

## 🔧 方法/架构

- **Utility-aware source queue**：把 KV cache 切分为 KV block，并按"效用"（对下游任务结果的贡献度）排序放入源队列，源传输优先发送高效用 block，低效用 block 在时间预算允许时再补。
- **ACK-sliding Streaming FEC**：基于 ACK 的滑窗 Streaming 前向纠错，为已发送的数据生成冗余校验块，抵抗不可靠链路上的丢包；相比传统 FEC，其冗余只覆盖滑动窗口而非全量数据，节省带宽。
- **Double-DQN scheduler**：轻量级双深度 Q 网络调度器，在"继续发源数据"与"发修复/冗余数据"之间做动态决策，把 deadline 约束纳入奖励/惩罚，使得带宽在截止期压力下自动向高价值内容倾斜。
- **零拷贝式交付**：接收方在收到足够 KV 信息后即可开始解码，从而与源端的剩余传输并行，缩短端到端等待。

```math
\text{Total KV bits} = B_{\text{src}} + B_{\text{fec}}, \quad
B_{\text{src}} + B_{\text{fec}} \le R \cdot T_{\text{deadline}}
$$

即在截止期 $T_{\text{deadline}}$ 内、链路速率 $R$ 的带宽预算下，分配源数据与冗余修复数据；调度器的目标是在此约束下最大化送达的 KV 效用（utility）。

## ⚠️ 局限性

- 依赖**可靠的效用估计**来构建源队列；若 KV block 的效用估计有偏，优先队列可能把关键 block 排到后面，收益退化。
- 面向**边缘多 agent 场景**，在数据中心内高可靠网络下收益可能有限（完整传输本来就可行）。
- 摘要未提供**绝对数值**（准确率、吞吐、冗余开销比例），难以评估在真实生产网络中的净收益。
- Double-DQN 调度器引入额外训练与状态管理开销，在链路状态快速变化时可能反应滞后。
- 只考虑 KV cache 的**交付**，未涉及 KV cache 的版本一致性、agent 中间状态同步等问题。

## 💡 建议

- 是否推荐使用：**是**（针对边缘多 agent 协同推理场景）
- 适用场景：边缘设备集群间分工会话上下文、需要复用 KV cache 避免重复 prefill、链路抖动且有严格响应时延要求的场景；如做边缘 LLM 服务架构设计，值得作为传输层方案参考。
