## 核心贡献
1. **提出 GROUPASSISTBENCH**：首个基于**真实世界群聊 + 实际部署的助手**构建的记忆基准，覆盖 50 个群、**80,299 条消息**、**2,395 个实例**，标注与标注成本**超过 $53K**。作者声明这是首个同时满足"多参与者真实对话 + 无固定答案的助人请求 + 来自真实用户反馈的评分标准"的记忆基准。
2. **两条正交评估轴**：**任务轴**——记忆召回 L1（有参考答案，按原子事实打分）与记忆使用 L2（无固定答案的服务请求，按逐实例定制 rubric 打分）；**依赖轴**——单条记忆 M1、跨成员分布式记忆 M2、冲突记忆 M3。
3. **核心发现："召回强 ≠ 助人强"**：最强的记忆系统（EverMemOS）在召回上**超过**同骨干的 Full Context（**0.621 vs 0.570**），但在使用上**远远落后**（**0.247 vs 0.431**）。**只评召回会高估记忆对群组的价值。**
4. **依赖结构的退化是普遍的**：14 个被测基线的 L1 Atom Recall 在 M1→M2/M3 全部下降；Full Context (GPT-5.6-terra) 的 L2 分数从 M1 的 **0.505** 降到 M3 的 **0.303**，L1 met 从 0.685 降到 0.377。
5. **RAG 与外部记忆系统的强弱在 L1/L2 上完全反转**：L1 上外部记忆系统更强（EverMemOS 0.621、xMemory 0.546 超过所有 RAG 系统的 0.504–0.539），L2 上**每个 RAG 系统（0.334–0.370）都超过每个外部记忆系统（0.139–0.269）**。
6. **失败机制的分解（497 对记忆的配对分析）**：跨六个记忆系统，**"召回了但没使用"的记忆占所有配对的 21–27%**（Full Context 为 11–16%）；该比例与 L2 排名的相关性（ρ=0.89）**强于召回本身**（ρ=0.56）。进一步分解：**36% 的未使用记忆根本没进入 L2 输入**（检索失败），**64% 已在输入中却未被应用**（应用失败）。
7. **两个可迁移的改进模块**：**RER（Relational Evidence Refinement）**——让检索到的记忆之间的关系显式化并沿关系补充缺失证据，不依赖请求措辞；**ACB（Assistance Constraint Binding）**——判定每条记忆事实的主体、范围、状态与适用性，并把验证后的条件绑定到生成上。两者对三个记忆系统均有稳定增益。
8. **端到端成本分析**：在 2,395 个查询的工作负载下，BM25、dense retrieval、LightMem、RAPTOR、Mem0 的总成本低于 Full Context（dense retrieval 总成本 **$55.0** vs Full Context **$260.4**；RAPTOR 摊销 $127.6 建库成本后为 $204.5），但**低成本不等于高性能**（LightMem 仅 $69.6 却得到最低 L1/L2）。

## 问题背景
记忆是 LLM agent 的核心组件，近期基准已从事实召回转向评估"记住的信息能否支撑个性化"与"agentic 任务完成"。在多用户场景下这一转向尤为困难：群聊要求助手服务**整个群**并产出**一个**回复，且必须调和分散在成员之间、随时间修订、或在群内存在争议的信息。

现有群记忆基准已研究信息的归属、整合与更新，并显示为单用户设计的系统在群组场景有独特失败模式。但它们的评估继承了通用记忆基准的局限：**成功主要以召回衡量**。问题问"谁说了什么"或"哪个值是当前的"，按固定参考答案打分；更接近助人的任务则是多选题或从封闭动作集合中选择。这留下了一个未回答的问题：**一个能检索到正确记忆的系统，能否在无固定答案的服务请求上做出恰当回应？**

另一个局限是现有群记忆基准使用**合成对话**，其任务是否捕捉到真实部署群组中协议、纠正与助人失败的产生方式并不清楚。

单用户场景的证据显示这个区分确实重要：在 AlpsBench 上，记忆把 persona 感知度从 0.41 提升到 0.72，却把情绪恰当性降到**低于**无记忆的骨干模型。

## 方法
### 1. 任务形式化
每个实例 $i$ 由三部分构成：**回答 $q$**、**必需记忆集合 $\mathcal{A}$**、**答案键 $K$**。$\mathcal{A}$ 从不向被测系统展示，其作用是决定评分。**任务轴**（L1 或 L2）固定 $q$ 与 $K$ 的形式；**依赖轴**（M1–M3）描述 $\mathcal{A}$ 的结构。

- **L1 记忆召回**：$q$ 是关于历史本身的问题（如"我们在哪家餐厅订的？"），有参考答案。
- **L2 记忆使用**：$q$ 是开放式的助人请求（如起草计划、做推荐），需要尊重其所依赖记忆的回复。
- **M1 单条记忆**：依赖单一实质记忆。
- **M2 多条记忆**：依赖多条必须组合的记忆，在群聊中通常由不同成员贡献。
- **M3 冲突记忆**：具有 M2 结构且额外包含冲突对 $(a_{old}, a_{new})\subset\mathcal{A}$——同一事物的两个值，其中旧值已被取代。

### 2. 记忆锚定与依赖标注
- **锚定记忆**：每个记忆记为锚 $a=(f,t,e)$——自包含的事实陈述 $f$、确立它的消息 $t$、该消息中的**逐字证据跨度** $e\subseteq x_t$。抽取器提出锚并丢弃那些"移除后不改变回答"的。
- **记忆单元**：同一条消息的锚与近重复事实被合并为一个单元；依赖一个单元则为 M1，两个以上为 M2。M3 额外要求**已验证的冲突对**。
- **冲突对检测**：从历史中的更新表达与值变化中检出候选对，匹配到较早值的锚。由于两个相似值可能涉及不同事务（如住宿预算与车票价格），每个候选获得**三个独立投票**判断两值是否指同一事务，**仅全体一致接受的配对才被采用**。最后验证 $a_{new}$ 在 cutoff 时仍是当前值；若不是，把 cutoff 移到同一事务的下一次变更之前。
- **原生请求 vs 作者撰写实例**：原生请求只覆盖成员恰好问到的记忆；为覆盖其余锚，构建 authored instances——为从清单中抽取的锚集合 $\mathcal{A}$ 撰写查询，查询中每个事实前提都必须引用消息 $t$ 与跨度 $e\subseteq x_t$；cutoff 放在最后一个锚之后的 $\delta_{\min}$ 到 $\delta_{\max}$ 条消息之间，其间无同一事务的更新。

### 3. 评分
- **L1**：答案键 $K_i$ 是参考事实集合 $G_i$。judge 逐事实判断回答是否复现（允许改写），$m_i^g\in\{0,1\}$。**Atom Recall**：
$$R_i = \frac{1}{|G_i|}\sum_{g\in G_i} m_i^g$$
  另外报告事实 F1。
- **L2**：rubric 由三类标准装配：
$$K = R_{\text{ground}}(A) \cup R_{\text{pen}}(A) \cup R_{\text{serv}}$$
  grounding 标准由锚实例化，penalty 标准由锚与记忆状态上的**确定性触发器**加入，service 标准由语言模型为该请求提出。rubric 分数 $S_i$ 按标准加权求和。

### 4. 质量控制
每实例通过确定性门控：每个锚与引用前提必须早于 cutoff；每个跨度必须能在其消息中逐字找到；查询不得泄露必需记忆，也不得（M3）暗示某个值已变。入选评测的实例另通过语言模型审查：每个锚是否必要、查询能否仅凭自身措辞回答、assistant 消息中的锚是否转述了成员确立的事实、（M3）两个值是否涉及同一事务；**每个负面判断必须引用支持它的跨度**，并由程序再次验证。

**人工验证**：三名标注者独立检查 120 个分层实例，**95.8% 按多数票有效、84.2% 全票有效**，逐题两两一致率 93–98%。60 个 L2 实例的 rubric 由标注者就 service 标准的合理性、penalty 标准的相关性与整体完整性评级，**90.0% 按多数通过全部三项检查、86.7% 全票通过**。

### 5. 评测配置
- **被测任务 agent**：GPT-5.6-terra（用于检索与外部记忆系统）；**评测 judge**：GPT-5.6-sol。
- **judge 验证**：三名标注者独立标记了 60 个 L2 实例的 180 条真实回答的每一条 rubric 标准（1,152 次判断）。judge 与人类多数一致率 **89.3%**，与标注者之间的一致率（89.8%）**同一水平**。出错时 judge 倾向给 grounding 与 service 标准**少分**、**过度施加 penalty**，因此评分偏保守。judge 对三个系统的排序与每位标注者完全一致。
- 因原始对话是中文，任务执行与评分均在中文进行以保留语义与语境、避免翻译伪影；同时提供完整英文翻译供参考。
- BM25 与 dense retrieval 返回 top 20 单元；embedding 用 text-embedding-3-small。

## 关键洞察
1. **"记忆基准"如果只测召回，就测错了记忆系统的价值**：EverMemOS 在召回上以 0.621 击败 Full Context 的 0.570，却在助人上以 0.247 落后 0.431。这个**排序反转**是本文最重要的发现——它意味着现有记忆基准的排名可能对实际部署毫无指导意义。
2. **召回与使用的强弱在不同方法族上反转**：外部记忆系统（尤其层次化的）在 L1 上最强，而平面 RAG 在 L2 上全面胜出（0.334–0.370 vs 0.139–0.269）。合理的解读是：**层次化摘要结构会掩盖事实层面的区分**（作者引用 xMemory 相关工作），所以它在"记住哪些事实"上占优，却不擅长"据事实行动"。
3. **"召回了却没用"是独立于召回的第二类失败，且与 L2 排名的相关性强于召回本身**（ρ=0.89 vs 0.56）。这把"使用"从召回的附属品变成了独立的设计目标。
4. **失败可以干净地二分**：36% 是**检索失败**（根本没进输入），64% 是**应用失败**（在输入里却没用）。两种失败都由"cue 依赖"驱动——L1 问题会点名目标记忆，L2 请求往往不点名。这个二分直接给出了两个可分别攻击的模块（RER 与 ACB），且它们的增益互不重叠。
5. **两个改进模块的增益大小与系统自身的瓶颈匹配**：RER 对 LightMem（缺失证据 74%）增益最大（+8.98 met），对 EverMemOS（缺失证据 14%）最小；ACB 反之，对 xMemory（应用失败 78%）与 EverMemOS（86%）增益最大，对 LightMem 最小（其瓶颈是证据缺失，ACB 无法补救）。这种"诊断 → 定向干预"的闭环是本文方法论上最可复用的部分。
6. **冲突记忆（M3）是最难的依赖类型**：Full Context 的 L2 从 M1 的 0.505 掉到 M3 的 0.303。值得注意的是 EverMemOS 的 L2 在 M2/M3 上**上升**（0.137→0.284→0.253），说明其处理冲突的方式虽然 L1 分数不高，却意外地在助人上更稳。
7. **成本与效果脱钩**：最便宜的 LightMem（$69.6）性能最差，最贵的 EverMemOS（$814.9，11,138 查询才回本）虽然 L1 第三但 L2 第十。因此"降低上下文 token"不是有效的优化目标——Full Context 用 52,435 token，L2 仍是最好的之一（0.431）。

## 局限性
- **单一语言与单一助手**：原始对话是中文，任务执行与评分均在中文进行；结论是否迁移到英语或其他语言的群聊未验证。助手是同一个已部署产品（Tencent Yuanbao），其回复风格与能力特征可能影响 L2 的 rubric 判定。
- **judge 依赖**：L2 的全部分数由 GPT-5.6-sol 给出。作者验证了 judge 与人类多数一致率 89.3%（与人类之间 89.8% 同水平），但 89% 的一致意味着约 11% 的标准判定与人类多数不一致；且 judge 偏保守（少给 grounding/service 分、过度施加 penalty），因此绝对分数偏低，不同系统间的相对比较应更可靠。
- **单一切分与单次运行**：多数结果未报告跨随机种子的方差或置信区间（置信区间只在附录 F.2 的组件分析中提供），0.03–0.05 量级的差异不宜过度解读。
- **L2 rubric 部分的自动化**：grounding 与 penalty 标准是确定性生成的，但 **service 标准由语言模型提出**，可能引入与请求不匹配的标准；虽经人工评级（90.0% 通过三项检查），仍非纯人工。
- **任务 agent 单一**：检索与外部记忆系统全部使用 GPT-5.6-terra 作为任务 agent，因此比较的是**记忆组织方式**而非端到端系统；不同记忆系统若配不同 agent 结果可能不同。
- **Full Context 只测了 4 个骨干，且都受限于 52,435 token 的平均上下文**（最大群达 972.8K token），因此"Full Context"在超长群上本质是截断的。
- **基线的实现由作者自行完成**（"author-written baseline adapters"），Mem0/LightMem/A-MEM/MemoryOS/xMemory/EverMemOS 等系统的配置质量会显著影响排名；作者自己在附录 F.1 提供了各阶段细节，但外部复现可能不同。
- **成本分析不含 judge 成本**，也不含建库的人工标注成本（本数据集本身 $53K+ 的标注成本并未计入任何系统的成本比较中），因此"Full Context 最贵"这一结论在计入标注成本后会被削弱。
- **RER 与 ACB 是简单的加法模块**，增益在本设置下测量，未验证其在更强骨干、更长上下文或不同群类型上的稳定性。
- **隐私与发布限制**：原始记录保留在数据提供方处不公开，发布的是经过改写与假名化的派生产物，需额外的隐私与合规审查——可能影响外部独立复现。

## 适用场景
- **群聊助手的评测与选型**：判断一个记忆系统是否真的"服务群组"，而不只是"记住事实"；本文的 L1/L2 与 M1–M3 划分可直接作为评测框架。
- **记忆系统的诊断**：用"召回了但没用"的比例与二分（检索失败 vs 应用失败）定位瓶颈：缺失证据多 → 用 RER；应用失败多 → 用 ACB。
- **改进现有记忆系统**：RER 与 ACB 是与具体记忆系统无关的加法模块，作者在三个拓扑层级的系统上都验证了增益。
- **构建助人类评测**：L2 的"无固定答案 + 逐实例 rubric + 来自真实用户反馈的 penalty"是一套可迁移的评测设计，尤其适用于"没有唯一正确答案但有明确对错标准"的服务场景。
- **成本-效果联合决策**：Figure 3 的成本-质量平面可用于在给定查询量下选择记忆方案（2,395 查询时 BM25/dense/LightMem/RAPTOR/Mem0 总成本低于 Full Context）。

**不适用于**：单用户助手的评测（本文专门针对群组的多成员整合与冲突）；有唯一正确答案的标准 QA（那属于 L1 范畴）；对英文或多语言群聊的结论外推；以及需要按现有记忆基准排名直接做部署决策的场景。
