### 核心贡献
1. 系统对比三种对话 agent 检索设计：主 agent 内置的 skill-based retrieval、非持久化检索子 agent（输出综合答案）、以及本文提出的 persistent retrieval subagent。
2. 提出 persistent retrieval subagent：跨轮维护检索历史，把检索到的证据直接返回给主 agent，并允许主 agent 向同一子 agent 发起纠正请求。
3. 量化了三种设计的成本-延迟权衡：在五种多轮设定下，比 skill-based retrieval 少用 43.3% token、估算 API 成本低 45.0%、平均响应时间缩短 9.1%。

### 技术方案
**核心思想**: 把检索子 agent 的角色从「合成答案」改为「维护检索状态并供给证据」，使多轮追问可以复用已有检索历史而无需重复检索。

| 技术 | 说明 |
|------|------|
| 设计一 | skill-based retrieval：在主 agent 内执行检索技能 |
| 设计二 | non-persistent retrieval subagent：每次生成一份 findings response |
| 设计三 | persistent retrieval subagent：跨轮维护 retrieval history，直接返回 retrieved evidence |
| 纠正接口 | 主 agent 可向同一 subagent 请求 corrections（corrections from the same subagent） |
| 评估场景 | 企业问题分别独立提问、置于共享对话中、作为依赖式追问 |
| 计量指标 | 记录的 agent-model tokens、估算 API 成本、平均响应时间 |

### 实验结果
- **数据集**: 企业场景问题（enterprise questions），五种多轮设定（摘要未说明具体设定名称）
- **基线**: skill-based retrieval、non-persistent retrieval subagent
- **结果**: vs skill-based retrieval：token 减少 43.3%、估算 API 成本降低 45.0%、平均响应时间减少 9.1%；vs non-persistent retrieval：每题响应时间减少 15.6 秒，但 token 多用 65.1%、估算 API 成本高 29.1%

### 局限性
- 相对 non-persistent 设计的成本代价明显（token +65.1%、成本 +29.1%），收益主要体现在延迟
- 摘要未说明具体使用的模型、企业问题数据集来源与五种多轮设定的定义
- 「估算 API 成本」依赖特定价格假设，跨时期结论可能变化

### 关键洞见
> 检索子 agent 的价值不在于「回答得更像最终答案」，而在于「成为检索状态机」——把它的输出从综合答案换成原始证据并跨轮保留，就用 29% 的额外 token 换掉了每题 15.6 秒的延迟，同时相比主 agent 自带检索技能还能省下近一半的模型 token。
