## 核心贡献

> **失败恢复是独立于 clean-start 成功的能力**：在 AndroidFlux 上恢复表现与 clean-start 成功仅部分相关（GUI-Owl-1.5-8B 在首错点 t 得 40.0，Qwen3-VL-32B 30.0、Gemini Flash 3.0 27.5）；显式 CoT 只在做过 GUI 域专门 RL 的模型上有效（GPT-5.6 Terra +17.5pp vs. Qwen3-VL-32B −12.5pp）。

1. **AndroidFlux 失败恢复基准** — 基于 AndroidWorld 构建，在首个可恢复错误**之前（t−n）、当处（t）、之后（t+1）**三类受控检查点回放录制轨迹，使不同 agent 从**完全相同的设备状态与历史**继续；human-verified 集 **80 个案例**（6 个源模型，65 个靠 action replay 复现、15 个靠 emulator snapshot），LLM-verified 集 **312 个 replay 案例 / 104 个任务 / 21 个源模型**
2. **恢复动作 reward modeling 基准** — **100 个恢复状态 / 26 种 AndroidWorld 任务类型**（72 个来自首错点、28 个来自无错步），每状态配对正负候选动作；偏好由**下游 rollout 结果**决定而非规则或 judge：12 个 agent 组成 panel 从每个动作状态 rollout，保留 panel 成功数差距 ≥2 的最极端配对
3. **首错检测器-验证器流水线** — Gemini Flash 3.0 实现的两阶段 detector–verifier，标注集上达到 **90.8% step-level precision**（偏向精确率牺牲召回率），把每个错误归为 **Stagnation / Direction / Execution** 三类；human-verified 集错误分布为 Direction 43.75% 最大类，LLM-verified 集 Stagnation 47.11% 最大类
4. **恢复能力跨架构差异** — human-verified 集 t_all 上 GUI-Owl-1.5-8B **40.0** 领先 Qwen3-VL-8B 28.8、Qwen3-VL-32B 30.0、Gemini Flash 3.0 27.5；agentic 框架 MobileRun 搭载 Gemini Flash 3.0 把 t_all 从 **27.5 提到 67.5**（LLM-verified 集 t 点从 39.7 提到 67.0）
5. **CoT 的域依赖性** — 未做 GUI 域 RL 的模型开推理普遍变差（Qwen3-VL-32B **−12.50pp**、Gemini Flash 3.0 **−13.75pp**、Qwen3-VL-8B **−12.50pp**）；做了 GUI 域 RL 的模型开推理稳定变好（GPT-5.6 Terra **+17.50pp**、GUI-Owl-1.5-32B **+5.00pp**）
6. **Rewinding vs. Injection 的时机依赖** — 按错误发生前步数分桶：早期（≤3 步）rewind **+8.76pp** 而 inject **−1.01pp**；晚期（≥7 步）rewind 降到 **+3.41pp** 而 inject 升到 **+5.86pp**；两者差距 **+12.22pp**（95% CI **[+4.1, +20.8]**），18 个模型中 **17 个**方向一致（sign test p=0.0001）
7. **恢复动作 reward model 近随机** — UI-Genie BT-128K 在 AndroidFlux 100 对上仍近随机，而**未经训练的 GUI expert 动作似然**已达 **0.58–0.60**（UI-Genie 上 0.71–0.74）；最佳单一打分器排对 60/100，至少一个 agent 排对 **82**，加上 BT-256K 后升至 **87**
8. **离线 RL 数据集** — **8,499 个 policy-induced 上下文**（t−n 2,097 / t−1 2,080 / t 2,080 / 成功上下文 2,242），用 offline GRPO + GPRS 训练 Qwen3-VL-4B（LoRA）；只训 tt 的配比恢复最强但 clean-start 退化，**UI 40% / tt 35% / t−1 25%** 的混合同时改善 clean-start 与恢复

## 技术方案

### 核心思想

现有 GUI agent 基准几乎只用「clean start 下的任务成功/失败」评估，隐藏了 episode 内部到底发生了什么。本文的洞见是：**移动环境会动态变化，一个真正可部署的 agent 必须能从非预期状态恢复**，而这需要同时知道两件事——(a) agent 在**哪里**出错，(b) 它能否从错误状态**修复**。

AndroidFlux 的做法是**受控回放（controlled replay）**：先录一个 source agent 的完整轨迹，标注它的**第一个可恢复错误步 t**，然后在 t−n / t / t+1 处把设备状态**还原**，让任意 target agent 从同一状态、同一历史继续。这带来一个关键性质——**同一状态被精确地交给每一个 agent，因此不同 agent 之间的成功率差异可以完全归因于恢复策略本身**。

关键的实现难点是**历史必须跨 agent 迁移**。不同模型输出的格式、窗口长度、是否保留 reasoning 都不同，而且绝对不能把一个模型的 prompt 格式原样塞进另一个模型的上下文。解法是引入 **schema-neutral step record**：每个 response 先被反解成中立记录，再由 adapter **按目标 agent 的原生格式重新渲染**；source 没输出的字段被**合成**（且合成 summary 时严格过滤任何提及 error/mistake/replay/recovery 的措辞，否则等于提前告诉 target「出事了」——那正是基准要测的推断）。恢复上下文里**没有任何标记**表明前缀是回放的、错误的或别人写的；**target 从头到尾不知道需要恢复**，注意到状态已坏本身就是被测能力的一部分。

第二个子基准把问题从「agent 能否恢复」推进到「**reward model 能否识别出能促成恢复的那个动作**」。偏好标签不是由规则或 LLM judge 给出，而是**由后果给出**：把每个候选动作实际执行出去，再让 12 个 agent 从该状态 rollout，用 panel 成功数的差距定义偏好。这比 UI-Genie 的做法更强——UI-Genie 的负例是对干净轨迹的扰动，而这里的负例是**策略在真实被破坏的状态上真实采取过的失败动作**。

### 关键技术

| 技术/方法 | 说明 |
|------|------|
| Controlled replay | 在同一 task seed 下重放录制的动作前缀还原状态；不可复现时回落到 emulator snapshot |
| Checkpoint 设计 | t−n（错前）/ t（首错已提交）/ t+1±（注入正/负恢复动作后）三类受控续跑点 |
| Schema-neutral step record | 中立的逐步记录，作为跨 agent 历史迁移的中间层；原文字段仅供审计 |
| Cross-policy re-rendering | 每个 adapter 按目标 agent 的历史长度/格式重新渲染前缀，并合成缺失字段 |
| Neutral history synthesis | summary 只描述「做了什么」，不复述「为何做」；过滤一切暗示错误的措辞 |
| Detector–verifier 首错检测 | Gemini Flash 3.0 两阶段：候选步提议 + 按结果 UI 状态复检，取最早存活步 |
| 错误三分类 | Stagnation（重复无进展）/ Direction（动作成功但偏离目标）/ Execution（目标对但执行结果错） |
| Outcome-grounded preference | 12-agent panel 从动作后状态 rollout，用成功数差距最大且 ≥2 的配对定义偏好 |
| Cross-agent takeover | 允许 π ≠ π_src，target 继承**别的 agent 的失败与历史**，模拟小模型卡住→大模型接手的生产场景 |
| Offline GRPO + GPRS | 不在环境中执行采样动作，用 Group Preference Reward Shaping 做离线 RL |
| Canary generality | 同一 80 任务重复 4 次的 Docker 重跑，量化 Android 环境的非确定性 |

### 实验设置

| 维度 | 规模 |
|------|------|
| 环境 | AndroidWorld（容器化，116 任务 clean-start；因环境问题剔除 4 任务 → 112） |
| 源模型 | human-verified 集 6 个源模型 / 672 条轨迹；LLM-verified 集 21 个源模型 |
| 评测 agent | 18–27 个模型（通用 VLM：Qwen3-VL-8B/32B、Gemma-4-31B-IT、Gemini Flash 3.0、GPT-5.6；GUI expert：GUI-Owl-1.5/7B/32B、MAI-UI-8B；agentic framework：Mobile-Agent-v3-7B/32B、MobileRun） |
| 硬件 | H100 / A40 / L40S / RTX 4090 容器分片 |
| 基准规模 | 恢复集 80（HV）+ 312（LV）案例；reward modeling 100 对 / 26 任务类型 / 12-agent panel |
| 训练数据 | 离线 RL 数据集 8,499 个决策上下文（seed 42，四片采样） |
| 基线 | UI-Genie BT/SFT（128K/256K 样本）、单 agent 似然打分、oracle 组合 |

### Rewinding vs. Injection（按错误前步数，pp）

| 错误前步数 | n | Rewind | Inject. | Δ |
|------|------|------|------|------|
| ≤3 | 116 | **+8.76** | −1.01 | −9.77 |
| 4–6 | 100 | +7.67 | +7.55 | −0.11 |

| 打分器 | UI-Genie (1,000 pairs) | AndroidFlux (100 pairs) |

| UI-Genie BT-256K | 0.904 + 1.1pp | 近随机（+3pp over 128K） |

| 五 agent 之一 | — | 82 / 100 |

### 离线 RL（Qwen3-VL-4B + LoRA，65 HV 任务，固定 2.4K 训练预算）

| 训练数据配比 | clean-start | 恢复表现 |
|------|------|------|
| UI-Genie 100% | 弱 | **下降** |
| AndroidFlux tt 100% | **下降** | **最强** |
| UI 40% / tt 35% / t−1 25% | **改善** | **改善** |

> 关键诊断：GPRS 训练奖励在各配比下上升幅度相似，**但奖励不是策略质量的直接度量**（被组内重复采样动作抬高）；UI-Genie-only run 拿到相当的最终奖励却有最弱的下游表现，其底层 reward model 分数早早 plateau 后下滑，而含错误邻域上下文的 run 持续提升。

## 局限性

- **仅覆盖 AndroidWorld 与「第一个可恢复错误」** —— 无法重建的错误链（多个交互错误）与其他 GUI 环境（桌面、OSWorld）仍是空白
- **LLM-verified 集继承 detector–verifier 流水线的噪声与源模型不平衡** —— pipeline 从更弱/更啰嗦的策略上捞出更多可用错误，少数源模型主导
- **恢复成功对 Android 非确定性敏感** —— emulator 异步渲染可能截到动画中途；残余设备状态随执行顺序漂移（缓存、权限弹窗、最近使用排序）；批量 serving 使浮点归约顺序依赖 batch 组成，**即使 greedy 解码也不 bitwise 可复现**
- **错误检测器偏向精确率牺牲召回率**（90.8% step-level precision），漏掉的错误不进入基准
- **恢复状态下的历史上下文不可完全保真** —— 访问性树刻意不存储（录制的树描述的是 source 的屏幕而非 target 看到的屏幕），source 未输出的字段只能合成
- **reward modeling 基准规模偏小**（100 对 / 26 任务类型），且匹配子集只覆盖 52 个任务
- **离线 RL 只在 Qwen3-VL-4B + LoRA 上验证**，GPRS 奖励来自 UI-Genie BT-128K，奖励模型本身在恢复场景下近随机，训练信号质量存疑
- **论文未给出代码链接**（comment 为空），复现门槛较高

## 建议

- **是否推荐使用**: **有条件** —— 作为「如何构造 agent 失败/恢复类基准」的方法论范式强烈推荐；作为现成基准则需等代码与更大规模的验证
- **适用场景**:
  - 设计任何**长程 agent 评测**时，检查它是否只报了终态成功率
  - 做**大小模型接力（handover）**系统：小模型卡住后交给强模型接手时，需要评测接手方从**别人制造的状态**恢复的能力
  - 做 **GUI agent 离线 RL** 数据构造：用 policy-induced 上下文（而非干净轨迹扰动）作为训练信号
  - 做 **recovery-aware reward model** 训练：偏好标签来自 rollout 后果，比规则/判分器更可信
- **可借鉴要点**:
  1. **「受控回放 + schema-neutral 中间表示 + 按目标模型重新渲染」**是跨 agent 迁移上下文的三件套，可直接复用到任何「让 B 模型接手 A 模型轨迹」的工程场景；合成 summary 时**过滤一切暗示错误的措辞**是关键细节（否则等于泄题）
  2. **早期失败靠 rewind、晚期失败靠注入正确动作**（+12.22pp 的时机依赖）是一条可立即用于产品设计的经验法则：agent 刚起步时给重来机会，走远了则直接塞一个纠偏动作
  3. **通用推理 ≠ GUI 恢复能力**（Qwen3-VL-32B 开 CoT 掉 12.5pp）：任何「加 CoT 就能变强」的假设在分布外状态下要先验证；且**恢复数据与 GUI 域 RL 是补齐这一缺口的方式**
