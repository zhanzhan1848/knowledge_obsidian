## 核心贡献

> **Agent scaffold 演化中，评测预算有两个用途 ——「指导后续搜索」和「决定最终选谁」—— 这两者的最优分配方式完全不同。** 本文给出的方案在多数设置下**用约一半的评测单元**取得高于全量评测的平均性能。

1. **问题**：LLM 驱动的 agent scaffold 演化通过**迭代的候选生成与评测**改进工作流。评测有两个角色：
   - **指导后续搜索**（search-time feedback）
   - **决定最终 scaffold**（final selection）
   - 但**对每个候选在全任务集上评测的执行成本很高**
2. **实证发现**：
   - **稀疏反馈可以维持 productive evolution**（搜索阶段不需要全量评测）
   - **额外的针对性评测改善最终选择**（选择阶段需要更准）
   - **Replay 分析表明**：**共享的高信息量条目（shared informative items）与共同的评分参照（common scoring reference）支撑了「势均力敌的候选之间的比较」**
3. **提出评测分配框架**：
   - **搜索阶段**：稀疏反馈
   - **选择阶段**：针对性的最终确认
   - **机制**：
     - 一次**短的完全评测 warm-up**，建立**共享的高信息量核心**并**校准一个响应模型（response model）**，其**条目参数在搜索期间保持固定**
     - 搜索后**重新拟合该模型**，应用 **paired successive halving（成对 successive 减半）**
     - **复用已累积的观测**，**只执行缺失的评测**
4. **结果**：在 **4 个 benchmark、2 种演化框架**下，该方法在**多数设置下平均性能高于全量评测**，同时**只用约一半的评测单元**。

## 技术方案

### 核心思想

把评测预算当成一个**两阶段资源分配问题**：

- **搜索阶段**：目标是「找到有希望的方向」⇒ **稀疏反馈足够**
- **选择阶段**：目标是「在势均力敌的候选中挑出最好的」⇒ **需要可靠的成对比较**

关键洞察：**搜索与选择对评测的需求形态不同**，所以不该用同一套评测策略。

```text
❌ 全量评测:
   每个候选 × 全任务集 → 成本 ∝ 候选数 × 任务数
   搜索阶段浪费（不需要这么准），选择阶段勉强（还需成对比较）

✅ 分配框架:
   [warm-up] 短的全量评测 → 选出共享高信息量条目 + 校准响应模型
   [search]  稀疏反馈，响应模型条目参数固定（保持可比性）
   [select]  重拟合响应模型 → paired successive halving
             → 复用已有观测，只补缺失的
```

### 关键技术

| 技术 | 说明 |
|------|------|
| **稀疏搜索期反馈** | 搜索阶段减少评测量 |
| **针对性最终确认** | 选择阶段补足关键比较 |
| **共享高信息量条目** | warm-up 中挑出对区分候选最有用的任务 |
| **共同评分参照** | 让不同候选可在同一尺度上比较 |
| **响应模型（item response model）** | 建模「条目难度 × 候选能力」的潜变量模型 |
| **条目参数搜索期固定** | 保证跨轮次可比性 |
| **重拟合 + 成对 successive halving** | 用配对比较高效淘汰候选 |
| **观测复用** | 不重跑已评测的 (候选, 条目) 组合 |

## 公式

```math
\text{评测成本}:\quad
\text{Cost} \;=\; \sum_{c \in \mathcal{C}} \sum_{i \in \mathcal{I}} \mathbb{1}\big[(c,i) \text{ 被评测}\big]
\qquad
\text{全量: } |\mathcal{C}| \cdot |\mathcal{I}|
```

```math
\text{响应模型（IRT 型）}:\quad
\hat{y}_{c,i} \;=\; \theta_c - \beta_i
\qquad
\substack{\theta_c = \text{候选 } c \text{ 的能力} \\ \beta_i = \text{条目 } i \text{ 的难度}}
```

```math
\text{搜索期条目参数固定}:\quad
\beta_i^{(t)} \;=\; \beta_i^{(t_0)} \quad \forall\, t > t_0
\qquad\text{（保证跨轮次的 } y \text{ 可比）}
```

```math
\text{成对 successive halving}:\quad
\mathcal{C}_{k+1} \;=\; \operatorname{Top}_{\lfloor |\mathcal{C}_k|/2 \rfloor}
\Big( \hat{y}_{c, i_k} \text{ 的成对比较结果} \Big)
\qquad
\text{（配对复用已观测）}
```

```math
\text{信息量（挑高信息量条目）}:\quad
I(i) \;=\; H(\mathcal{L}(\hat{y}_c | \theta_c)) \quad\text{的期望下降}
\;=\; \mathbb{E}_c\big[\text{熵}(p(\hat{y}_c \mid i))\big]
```

```python
# 概念性伪代码：评测分配框架（稀疏搜索 + 成对选择）
import numpy as np

class EvalBudgetAllocator:
    def __init__(self, candidates, items, budget_frac=0.5):
        self.C, self.I = candidates, items
        self.budget = int(budget_frac * len(candidates) * len(items))
        self.obs = {}                       # (candidate, item) -> score
        self.theta = {}                     # candidate ability
        self.beta = {}                      # item difficulty
        self.core_items = None             # 共享高信息量核心

    # ---- warm-up：短的全量评测，建立共享核心 + 校准响应模型 ----
    def warmup(self, n_warmup=20):
        subset = self.C[:n_warmup]
        for c in subset:
            for i in self.I:
                self.obs[(c, i)] = self.run_eval(c, i)

        self.fit_response_model()

        # 挑出「共享的高信息量条目」+ 共同的评分参照
        self.core_items = self.select_informative_items()
        self.fit_response_model(refit_beta=True)
        return self.core_items

    def fit_response_model(self, refit_beta=False):
        # 条目参数在搜索期间固定，重拟合仅发生在选择阶段。
        for i in self.I:
            if i not in self.beta:
                self.beta[i] = estimate_difficulty(i, self.obs)
        for c in self.C:
            self.theta[c] = estimate_ability(c, self.obs, self.beta)
        if refit_beta:
            self.beta = {i: estimate_difficulty(i, self.obs) for i in self.I}

    # ---- 搜索阶段：稀疏反馈 ----
    def search(self, propose_fn, n_rounds=20):
        for r in range(n_rounds):
            new_c = propose_fn()
            # 只评少量条目（稀疏反馈）
            probe = sample_informative(self.core_items, k=3)
            for i in probe:
                self.obs[(new_c, i)] = self.run_eval(new_c, i)
            self.fit_response_model(refit_beta=False)   # beta 固定
        return self.C

    # ---- 选择阶段：重拟合 + 成对 successive halving ----
    def select(self):
        self.fit_response_model(refit_beta=True)   # 允许 beta 更新
        pool = list(self.C)
        while len(pool) > 1:
            pairs = pair_up(pool)
            winners = []
            for (a, b) in pairs:
                # 只执行缺失的评测，复用已累积的观测
                for c in (a, b):
                    for i in self.core_items[:2]:
                        if (c, i) not in self.obs:
                            self.obs[(c, i)] = self.run_eval(c, i)
                winners.append(winner_by_observations(a, b, self.obs))
            pool = winners
        return pool[0]

    def cost(self):
        return len(self.obs)
```

## 局限性

1. **方法名被渲染为 `\method`** —— 摘要中的方法名是 LaTeX 宏未展开，**这是论文的排版缺陷**，也说明摘要生成有问题
2. **「多数设置下」表述含糊** —— 4 基准 × 2 框架 = 8 个设置，具体几个更好、差距多大未给
3. **响应模型的形式未明** —— 是标准 IRT、还是更复杂的？参数怎么估（尤其条目参数固定时的估计偏差）？
4. **依赖「候选势均力敌」这一前提** —— 如果候选能力差距明显，稀疏反馈就足够，全量评测的价值也下降
5. **成对 successive halving 的统计效率依赖配对设计的正确性** —— 若不同候选的评测有系统性偏差（不同 harness、不同 seed），成对比较会有偏
6. **warm-up 成本未计入「约一半」的核算** —— 还是已包含？若包含，warm-up 的规模是关键参数，摘要未给
7. **不涉及评测噪声** —— 摘要大量讨论「信息量」和「参照」，但评测本身有随机性时，节省 50% 评测会把噪声放大
8. **4 个 benchmark 的名称未给**

## 实现建议

- **实现难度**: 中到高（响应模型实现、条目信息量计算、成对 halving 逻辑）
- **预期性能**: **多数设置下优于全量评测，评测成本减半**
- **适用场景**: **大规模 agent scaffold / prompt 演化** —— 候选多、评测昂贵、迭代次数多的场景
- **落地注意**:
  1. **先做成本画像** —— 确认你的评测瓶颈是「候选数 × 任务数」的乘积，才值得上这个框架
  2. **优先实现「共享高信息量条目」** —— 这是收益最大、实现最简单的一块，且与 selection 策略解耦
  3. **条目参数固定是关键的正确性细节** —— 搜索期随意更新 beta 会破坏跨轮可比性
  4. **注意评测噪声** —— 减半评测前，先确认你的评测重复多次是稳定的
  5. **响应模型的细节必须读正文** —— 摘要没给，IRT 形式选择（1PL/2PL/更复杂）会显著影响效果

## 我的评注

> 这篇解决的是一个很实际的问题：**agent 自动化的瓶颈正在从「生成」转移到「评测」**。你想让 agent 自己迭代改进工作流，每个候选都要跑一遍完整评测 —— 这个成本很快就压死整个循环。**把评测成本减半**在实践中是决定性的（能跑 10 轮 vs 20 轮，效果完全不同）。
>
> 最核心的洞察是 **「评测有两个角色，且需求形态不同」**：
> - 搜索阶段要的是**方向感**（哪些候选有希望）→ 稀疏反馈足够
> - 选择阶段要的是**精度**（从势均力敌的候选里挑出最好的）→ 需要可靠的成对比较
>
> 这解释了为什么一个「统一降本」的方案（如简单地随机抽 50% 任务评所有候选）会失败 —— 它把两个阶段的评测搞成了同一种东西。论文的方案是**结构化的降本**：搜索期稀疏、选择期密集，且用同一个响应模型贯穿。
>
> 「**条目参数在搜索期固定**」这个细节我很喜欢，它是那种**不看论文细节就一定会做错**的地方。响应模型里条目的难度参数如果每轮都在变，那么候选之间的分数就没有共同参照，「势均力敌的候选之间的比较」根本无从谈起。而论文用 replay 分析**实证支持**了「共享高信息量条目 + 共同评分参照」的必要性 —— 这是分析驱动的设计，不是拍脑袋。
>
> 保留意见：
> - **方法名在摘要里没渲染出来**（`\method`），这让我完全无法在摘要层面评估这个方法。这是纯粹的排版问题，但影响了可读性。
> - **「多数设置下」太含糊**。8 个设置里赢几个、赢多少，是判断这个方法能否用的关键信息。
> - **评测噪声问题完全没被处理**。减半评测意味着更大的方差，如果评测本身有噪声，节省预算可能得不偿失。论文摘要里的「信息量」「参照」等词汇都指向**确定性**评测的假设。
>
> 落地判断：先做**成本画像 + 共享高信息量条目选择**这两步，二者实现成本低、收益明确，且是完整方法的基础。
