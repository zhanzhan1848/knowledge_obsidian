# DeFT-RAG: Incrementally Decomposing Multi-Hop Questions into Self-Contained Sub-Questions with Reusable Answers

## 摘要
RAG 让 LLM 通过从大规模语料检索相关段落来回答问题，但在 multi-hop 问题上表现挣扎——这类问题需要跨越若干文档、用问题从未提及的中间实体串联事实。Graph-based RAG 只从问题点名的实体检索一次，因此极少能恢复完整证据链；iterative RAG 虽能一步步恢复，但准确性受限于它要求 LLM 承担的多重任务：规划子问题、判定其依赖关系、随答案到达改写子问题、以及追踪已知信息。本文提出 DeFT-RAG，包含三个组件。第一，它每次只从原问题与已回答的 QA 对中生成**一个自包含的子问题**，每个子问题都点名它所问的每个实体，从而免去规划、依赖追踪与改写，让 LLM 每次专注于一个细粒度任务。第二，DeFT-RAG 把剩余的 LLM 工作移出 LLM：QA 表以**规则**更新以追踪已知信息，yes/no 决策由**微调后的轻量 decision model** 做出。第三，DeFT-RAG 缓存 QA 对，当后续问题询问同义子问题时复用答案。在 MuSiQue、2WikiMultiHopQA、HotpotQA 上，以 gpt-4o-mini 与 Qwen3.6 为骨干，DeFT-RAG 在十三个基线中取得最佳准确率，同时给 LLM 的 input token 少于任何其他迭代方法；在 1,000 个 MuSiQue 问题共享 QA cache 的设定下，23.1% 的子问题由 cache 回答，LLM 调用减少 12.9% 且准确率未下降。

## 核心贡献
1. **增量式问题分解**：一次生成一个自包含子问题，输入为原问题 + 已找到的 QA 对；每个子问题点名其涉及的每个实体且不依赖任何其他子问题的答案，消除 planning / dependency / rewriting 三类错误。
2. **把细粒度任务移出 LLM**：QA 表由**规则**更新（无模型调用），yes/no 决策由微调后的轻量 **decision model (DM)** 完成（relevance / direct answer / enough facts 三类）。
3. **QA cache 跨问题复用答案**：因自包含子问题无论为哪个原问题生成都具有相同含义与相同答案。
4. **实证**：三个 multi-hop QA benchmark × 两个 backbone，13 个基线，取得最佳准确率并给出最少 LLM input token；代码与 prompts 开源（https://github.com/Dingyi-Kang/DeFT-RAG）。

## 方法与架构
**问题设定**：语料 $C$、问题 $Q$；vanilla RAG 为
```math
a = \mathrm{LLM}\big[Q, R(Q, C)\big],\qquad R_k(q,C) = \text{top-}k_{p\in C}\, s\big(e(q), e(p)\big)
```
固定 top-$k$ 相似度检索。multi-hop 需要证据链，其中 **bridge entity** 是链上的中间答案，问题本身从不点名它。

**DeFT-RAG 的三个 LLM 任务（细粒度）**：
```math
q_{t+1} = \mathrm{LLM}_{sub}(Q, F_t),\qquad a = \mathrm{LLM}_{ans}(q, P),\qquad \hat{a} = \mathrm{LLM}_{fin}(Q, F)
```
其中 $F_t = \{(q_1,a_1),\dots,(q_t,a_t)\}$ 是 QA 表，$P$ 是选中的段落集合。**子问题自包含**的定义：点名它所问的每个实体（按名字或无需再查的描述），且不依赖任何其他子问题的答案。例如当 QA 表显示莱茵河注入北海后，"Where does the North Sea meet the Atlantic?" 自包含，而 "Where does that sea meet the Atlantic?" 不自包含。

**QA 表（规则更新，无模型调用）**：$F_0=\emptyset$，每找到一个答案就
```math
F_{t+1} = F_t \cup \{(q_{t+1}, a_{t+1})\}
```
三条规则：已回答子问题的 QA 对入表；无答案的子问题被记录并展示给 $\mathrm{LLM}_{sub}$ 以免重问；新子问题与已问过的重复（比较规范化措辞）时要求 $\mathrm{LLM}_{sub}$ 另写一个。QA 表是步骤间唯一的信息载体，因此 LLM 输入始终短小。

**Decision Model（DM）**：一个参数量远小于骨干 LLM 的语言模型，被训练为以概率回答 yes/no 并针对本文决策做微调。三类决策：
- **Relevance** $D_{rel}(q,p)$：检索到的段落 $p$ 是否与问题 $q$ 相关；
- **Direct answer** $D_{direct}(Q, R_w(Q,C))$：为原问题检索的 top-$w$ 段落是否已含全部证据；
- **Enough facts** $D_{suff}(Q, F_t)$：已找到的 QA 对是否足以回答 $Q$（结束循环）。

决策规则：
```math
D(x) = \mathbb{1}\left[p_{DM}(\text{yes}\mid x) \ge \tau\right]
```
阈值：relevance 与 enough facts 用 $\tau=0.5$（"yes 比 no 更可能"）；direct answer 用更严的 $\tau=0.7$，理由是需要多步的问题被误判为可直接回答几乎必然答错，而一步能答的问题被误送进循环仍可能答对（只是多花 LLM 调用）；QA cache 的"同义"判定用 $\tau=0.8$（错误复用会把错误带入另一个问题）。

**段落选择**：
```math
\mathrm{Select}(q, R_w(q,C)) = \{p \in R_w(q,C) : D_{rel}(q,p) = 1\}
```
因为只有被选中的段落到达 LLM，$w$ 可以大于通常的 $k$ 而不把证据埋在干扰段落中。

**DM 微调**：起始权重 StartLux-Decision-4B（Qwen3.5 架构，4B 参数）；标签仅来自各 benchmark 训练划分的 gold 标注（passage 是否为 gold supporting passage；是否所有 supporting passages 都被检索到；QA 对是否覆盖 gold decomposition（MuSiQue）或 gold evidence（2Wiki）的每一步）。为让训练输入形似测试输入，训练问题按每组 1,000 题分组，每组用自己题目的 passages 构成语料。Leakage 检查：所有 1,000 个测试问题来自官方 validation split，不在训练数据中；训练问题若其 gold passage 出现在任何测试语料中则被跳过。最终 **48,036** 条训练与 **7,806** 条开发样本（开发集取自 15% 的训练问题）。LoRA（rank 16、alpha 32、dropout 0.05、作用于所有线性层；4.24B 参数中训练 32.5M），LR $10^{-4}$、5% warmup + cosine decay、1 epoch（**2,262 步**，约 **6.4 小时**，2× NVIDIA RTX A5000），micro-batch 8,192 tokens，gradient checkpointing，clip 1.0；再用开发集拟合单个概率温度（**1.08**）。same-meaning 决策**不做微调**。

**QA cache（跨问题复用）**：先按忽略大小写与标点的相同措辞查找；若无，取最相似的若干（设置表：**5** 个）已存子问题，用 DM 以 $\tau=0.8$ 判定是否同义；命中则直接复用答案，不做检索也不调用 LLM；否则正常回答并把新 QA 对存入 cache。

**回答流程（Algorithm 1）**：
```
P ← Select(Q, R_w(Q,C))
if D_direct(Q, R_w(Q,C)): return LLM_ans(Q, P)
F ← ∅
for t = 1..T:
    q ← LLM_sub(Q, F)
    a ← LLM_ans(q, Select(q, R_w(q,C)))
    if a ≠ ∅: F ← F ∪ {(q,a)}
    if D_suff(Q, F): return LLM_fin(Q, F)
P ← Select(Q, R_2w(Q,C)); return LLM_ans(Q, P)
```

## 实验设置
- **Benchmark**：MuSiQue、2WikiMultiHopQA、HotpotQA，各取 1,000 题测试集，语料为 LogicRAG 作者发布的对应 passage corpus（分别 11,656 / 6,119 / 9,811 段）。
- **基线（13 个）**：No Retrieval、Vanilla RAG；7 个 graph-based（LightRAG、PathRAG、HippoRAG、HippoRAG 2、MemGraphRAG、G3RAG、LinearRAG）；4 个 iterative（IRCoT、Self-Ask、LogicRAG、Hi-Q）。未与 REAP 比较（其 planner 与 fact extractor 是在 HotpotQA/2Wiki 轨迹上微调的 LLM，与本文统一 backbone 的设定不符）。
- **共享配置**：同一 backbone、同一 embedding 模型 Qwen3-Embedding-4B（last-token pooling，仅对 query 施加 query instruction）、temperature 0、top-$p$=1、output limit 3,072 tokens；Qwen3.6 的 reasoning mode 对所有系统关闭。基线每次检索取 top-$k=5$；DeFT-RAG 取 top-$w=2k=10$，再由 DM 筛选，每步最多保留 5 段相关段落（实测平均 2.1–2.4 段），步数上限 $T=6$。主结果**均未启用 reuse**。
- **指标**：EM、token F1、LLM-judged accuracy（主指标，SimpleQA prompt）；为避免自评，gpt-4o-mini 的结果由 Qwen3.6 评判，Qwen3.6 的结果由 gpt-4o-mini 评判；差异用配对答案上的 exact McNemar test 检验。
- **DeFT-RAG 设置（Tab. 6）**：$w=10$（retry/fallback 时 20），$T=6$，relevance $\ge 0.5$，当只有一段/无段落被判相关时保留 2/5 段，每步最多 5 段，direct answer $\ge 0.7$，enough facts $\ge 0.5$，reuse 比较 5 个已存子问题、$\ge 0.8$，段落长度上限 3,000 字符。direct answer 的 0.7 阈值是在开发阶段用部分测试题（2Wiki 与 MuSiQue 前 300 题）的存档答案上选定的，之后对所有 benchmark 与 backbone 固定；改为 0.6 或 0.8 最多改变每 benchmark 13/1,000 题的路径，准确率变化不超过 0.1 点。

DeFT-RAG 以**每题 390 词**（不到 vanilla RAG 的 870 词的一半）取得最高的 3-hop 覆盖率（46%）；Self-Ask 覆盖更多 2-hop 链（83%）但需 2,590 词，LinearRAG 覆盖 19% 的 4-hop 链需 4,110 词（约 DeFT-RAG 的十倍）。

**段落选择消融（Tab. 4，gpt-4o-mini，每 benchmark 300 题）**：关闭选择（改用 top-5 全保留）后准确率在 MuSiQue/2Wiki/HotpotQA 上分别下降 **2.3 / 3.7 / 5.3** 点（平均降 3.8 点），HotpotQA 的下降显著（$p=0.002$）。

**DM 微调效果（Tab. 5，base / fine-tuned 的 AUC）**：

| Decision | MuSiQue | 2Wiki | HotpotQA |
|---|---|---|---|
| Relevance | 0.931 / 0.979 | 0.996 / 1.000 | 0.990 / 0.997 |
| Direct answer | 0.850 / 0.933 | 0.938 / 0.997 | 0.915 / 0.995 |
| Enough facts | 0.903 / 0.904 | 0.943 / 0.959 | 0.816 / 0.845 |

端到端（MuSiQue 前 300 题，gpt-4o-mini）准确率从 0.587 提升到 0.623。

**QA cache 复用**：在全部 1,000 个 MuSiQue 问题（gpt-4o-mini，顺序作答，共享一个 cache）上，生成的所有子问题中 **23.1%** 由 cache 回答，LLM 调用数减少 **12.9%**；准确率未下降（0.642 有复用 vs 0.629 无复用，$p=0.18$）。

**开销（Tab. 7，gpt-4o-mini，每题）**：DeFT-RAG input token **1,569**（其他迭代方法 1,926–13,928），output token **33**（全方法最少），LLM 调用 **4.8**（Self-Ask 6.3、Hi-Q 6.6），但**中位延迟最高（9.9 s）**——原因是每步都要调用本地 DM 选段（MuSiQue/2Wiki/HotpotQA 每题分别 7.0/6.3/3.2 次 DM 调用，每次 1.6–1.8 s，占回答时间的 60–70%）。换成 API 版 closed decision model **Jev**（约 0.16 s/次）后，中位延迟降到 **5.0 s**，平均回答时间降到 8.2/7.7/3.6 s，准确率仅差 1.2 点以内（0.618 / 0.857 / 0.867）。索引方面，DeFT-RAG/vanilla/迭代方法只需 embedding（约 5 分钟/语料、零 LLM 调用），而 graph-based 方法需 2,100–146,555 次 LLM 调用、10.9–114.3M tokens、最长 17.9 小时建索引。

**失败模式**：2Wiki 的 bridge-comparison 问题（嵌套子问题）上，38% 的嵌套子问题得不到答案（而单关系子问题仅 4%），235 题中有 75 题达到步数上限或重复自身——这是 DeFT-RAG 在 2Wiki 上仅与 Self-Ask 持平的主因。

核心公式（LLM 三任务定义、QA 表更新、DM 决策规则与阈值、段落选择集合）已在"方法与架构"给出。论文未给出独立代码块，但完整公开了 prompts（Appendix B：写子问题（含无 QA 对/有 QA 对/无答案后追加/重复子问题后追加四种变体）、从段落作答、从 facts 作答原问题，以及 DM 的四类 yes/no 决策问题），代码与 prompts 见 https://github.com/Dingyi-Kang/DeFT-RAG。

## 局限性
论文没有独立的 Limitations 章节，但从失败分析与开销分析可读出：① 嵌套/复合子问题（"the director of X" 尚未点名时的 "the date of birth of the director of X"）会破坏自包含性，导致 2Wiki 上 38% 嵌套子问题无答案、235 题中 75 题触顶或重复，2Wiki 上仅与 Self-Ask 持平；② 中位延迟 9.9 s 为所有方法最高，主要来自本地 DM 的串行调用（换成 API DM 可降到 5.0 s）；③ direct answer 的 0.7 阈值是在**部分测试题的存档答案**上选定的（作者声明为开发阶段选择并随后固定，且对 0.6/0.8 不敏感，影响 ≤13/1,000 题、≤0.1 点准确率），但这仍是一种轻度测试集接触；④ 未与 REAP 比较；⑤ 同义复用决策未微调，只靠 prompt 与 $\tau=0.8$。

我的补充批判：① "自包含子问题"是整套方法的核心假设，但 LLM 生成的子问题并不总是自包含（论文自己给出反例），缺少一个显式的自包含性验证/重写步骤；② DM 在训练中见过 gold decomposition 的形式，而测试时 LLM 生成的子问题分布与之不同，存在训练-推理分布偏移；③ 主结果是在 1,000 题子集上、语料仅万级段落的小规模设定，与真实百万级语料下的 bridge entity 数量与检索难度差距很大；④ LLM-Acc 由对方模型判分，虽然避免了自评，但 SimpleQA 式判分本身对长答案的粒度容忍度未知；⑤ 23.1% 的 cache 命中率与 12.9% 的调用节省是在"顺序作答同一批 1,000 题"这种乐观设定下测得，真实交互式负载下命中率会低得多。

## 评估与建议
- 是否推荐深入阅读：**是**。它把 multi-hop RAG 的失败模式做了清晰分类（planning / dependency / rewriting / tracking error），并用"把细粒度任务移出 LLM"这一设计原则系统性地消解它们，是 agentic RAG 设计的高质量参考。
- 适用场景：multi-hop QA 系统、agent 的长期记忆与事实缓存设计、把 LLM 任务做细粒度拆分的通用工程实践、检索增强中的判别模型（relevance / sufficiency / answerability）设计。
- 与知识库的关联：与 graph RAG（GraphRAG、LightRAG、HippoRAG 1/2、PathRAG、MemGraphRAG、LinearRAG、G3RAG）与 iterative RAG（IRCoT、Self-Ask、LogicRAG、Hi-Q、REAP）的对比谱系完整；与 Adaptive-RAG、Self-RAG、Search-R1、R1-Searcher 的"何时检索"决策对比；与 answerability/faithfulness 判断模型、以及 agent memory 与 cache 复用设计相关。
