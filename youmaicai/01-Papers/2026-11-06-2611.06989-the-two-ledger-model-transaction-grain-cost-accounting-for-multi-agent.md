# The Two-Ledger Model: Transaction-Grain Cost Accounting for Multi-Agent AI Systems Across Clouds, Models, and Systems of Record

## 摘要
企业把业务交易跑在跨云、跨 LLM、跨编排 harness、跨记录系统的**多 agent AI 系统**上。财务只在**结算粒度（settlement grain）**收到 AI 成本，按 SKU 与计费周期聚合。业务问题（「这单/这索赔/这案子在 AI 上花了多少？」）**无法从账单数据回答**，因为供应商永远看不到企业的交易边界。**FinOps FOCUS 规范**给账单数据统一了跨供应商 schema，但**仍是结算粒度**，即便它加入了 AI token 与 requester 归因。本文形式化这一**粒度错配**，导出**七项要求**，并提出 **Two-Ledger Model（双账本模型）**：一张 **FOCUS 符合的结算账本**，联结一张建立在 **OpenTelemetry GenAI 遥测**上的**调用粒度归因账本**。**分层关联脊柱（layered correlation spine）**（trace context、A2A/MCP 元数据、业务键关联、概率匹配）把每条记录指派给它的业务交易，并记录**方法与置信度**；**版本化费率卡（versioned rate card）**近实时定价；**周期对账**把两张账本绑定。

## 核心贡献
1. 形式化 AI 成本的**粒度错配（grain mismatch）** —— 结算粒度 vs 交易粒度，并导出**七项要求**
2. 提出 **Two-Ledger Model**：FOCUS 结算账本 ⊕ OpenTelemetry GenAI **调用粒度归因账本**
3. 设计**分层关联脊柱**：trace context / A2A·MCP 元数据 / 业务键关联 / 概率匹配，每条记录记录**方法与置信度**
4. **版本化费率卡**近实时定价 + **周期对账**绑定两账本

## 方法与架构
**问题形式化**：
```math
\text{billing grain (SKU \times period)} \ne \text{transaction grain (business event)}
```
由错配导出 **7 项要求**。

**架构**：
```
结算账本 (FOCUS)  ←── 周期对账 ──→  归因账本 (OTel GenAI 调用粒度)
                         ↑
              分层关联脊柱
    trace context → A2A/MCP 元数据 → 业务键关联 → 概率匹配
    （每条记录记录关联方法 + 置信度）
                         ↓
              版本化费率卡（近实时定价）
```

## 实验结果
- 形式化**粒度错配**并导出 **7 项要求**
- 提出可实施的 **Two-Ledger Model** 架构（FOCUS + OTel GenAI 遥测）
- 分层关联脊柱的**四层方法**各自记录**方法与置信度**（可审计）

## 局限性
- 架构与规范设计为主，**缺乏真实企业部署验证**；
- **概率匹配**层引入了不确定性，需要下游接受置信度加权而非精确归因 —— 摘要未讨论其误差传播；
- 依赖 OTel GenAI 遥测的覆盖度与质量，agent 框架不接入即失效。

## 值得注意的点
**「供应商永远看不到企业的交易边界」** 是本文的起点，也是所有 FinOps-for-AI 工作的核心难点。它的解法（双账本 + 带置信度的分层关联）非常务实 —— 不追求精确归因，而是**把不确定性显式记账**。这与今日多篇「显式不确定性优于隐式精度」的主题完全一致。
