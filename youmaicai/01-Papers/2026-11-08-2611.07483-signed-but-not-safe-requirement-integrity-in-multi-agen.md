# Signed but Not Safe: Requirement Integrity in Multi-Agent LLM Handoffs

> **arXiv**: [2611.07483](https://arxiv.org/abs/2611.07483)
> **发表日期**: 2026-11-05
> **分类**: cs.CR (及交叉分类 cs.AI, cs.MA)
> **会议/期刊**: arXiv preprint (34 pages, 0 figures; 预注册研究)

## 📋 摘要

企业级 AI agent 越来越多地把用户请求拆给多个 subagent 并合并结果，而每次 handoff 都可能把某条要求**摘要掉、改变或忽略**。本文报告一项**预注册（preregistered）**研究，使用合成的、可精确评分的任务，比较三种 handoff 形式：自由文本、structured JSON 与**signed requirement-manifest**。机制上，orchestrator 把每条要求抽取为"逐字引用 + 可检查谓词"，代码用 **HMAC-SHA256** 对 manifest 签名，再由确定性代码验证 merger 的决策。在 **Qwen3-8B**（**1,440 条轨迹**、**五种威胁**）下，signed manifest 把受攻击时的 unsafe commit 从 **69.4% 降到 9.0%**（**60.4 个百分点**，**95% CI [51.4, 69.4]**），且相对 structured handoff 没有净损失 compliant commit。签名正是击破 in-transit tampering 的关键：未签名的 manifest 在 **79%** 的变异运行中提交了违规，而签名的一个是**零**。在相同轨迹上，确定性 verifier 捕获了 **78.7%** 的违规决策，而 LLM checker 只有 **59.0%**，误报率分别为 **7%** 与 **50%**。oracle manifest 消除了全部残余 unsafe commit，说明残余风险来自**签名之前的抽取错误**。一项预注册的 pre-signing injection 攻击证实了这一边界：**一行**对抗性文本把 signed-manifest 的违规率从 **14.6% 抬到 37.5%**（Qwen3-8B）、**11.1% 抬到 63.9%**（gpt-oss-20b）、**8.3% 抬到 75.0%**（GPT-5.6-luna），而此时签名反而为被污染的 manifest 背书。结论：**签名保护的是传输中的要求，而不是抽取本身；抽取步骤才是信任边界（trust boundary）**。

## 🎯 核心贡献

1. **提出 signed requirement-manifest handoff 机制**：orchestrator 将每条要求抽成"逐字引用 + 可检查谓词"，HMAC-SHA256 签名，确定性代码验证 merger 决策。
2. **给出量化的攻击面削减**：Qwen3-8B、1,440 轨迹、5 种威胁下，unsafe commit 从 **69.4% → 9.0%**（-60.4 pp，95% CI [51.4, 69.4]），且 compliant commit 无净损失。
3. **分离"签名"与"抽取"两种失效**：证明签名能击破 in-transit tampering（未签名 manifest **79%** 变异运行违规，签名后为 **0**），但 pre-signing injection 攻击可把签名变成对污染 manifest 的背书。
4. **确定性 verifier 优于 LLM checker**：相同轨迹上确定性代码捕获 **78.7%** 违规 vs LLM checker **59.0%**；误报 **7%** vs **50%**。
5. **预注册研究方法学**：合成可精确评分任务 + 预注册攻击，产出可复现的、可证伪的安全结论。

## 🔧 方法/架构

**三种 handoff 形式**

1. **Free-text handoff**：subagent 以自然语言回传要求，最易被摘要/篡改。
2. **Structured JSON handoff**：要求以结构化字段传递，可机器解析但无完整性保护。
3. **Signed requirement-manifest handoff**：

$$
m = \bigl\{\,(\text{quote}_i,\ \text{predicate}_i)\ \bigr\}_{i=1}^{n},\qquad \sigma = \text{HMAC-SHA256}_{k}(m)
$$

- orchestrator 抽取每条要求的**逐字引用** $\text{quote}_i$ 与**可检查谓词** $\text{predicate}_i$；
- 代码以密钥 $k$ 对 manifest $m$ 计算签名 $\sigma$；
- merger 提交决策后，由**确定性代码**用谓词检查合并结果，并以 $\sigma$ 校验 manifest 是否被改动。

**攻击模型（5 种威胁）**
- *In-transit tampering*：在 subagent → merger 之间修改 manifest；
- *Pre-signing injection*：在 orchestrator 抽取之前注入一行对抗性文本，污染 quote/predicate；
- 其余三类威胁与攻击面（抽取误差、合并规则失效等）在摘要中未逐项展开，详见原文。

**信任边界结论**

$$
\text{Residual risk} = \underbrace{P(\text{extraction error})}_{\text{pre-signing}} + \underbrace{P(\text{merge-rule violation})}_{\text{verified deterministically}}
$$

oracle manifest（即由人给出正确的抽取）可消除全部残余 unsafe commit，验证了残余风险完全来自抽取阶段。

## 📊 实验结果

- **主实验（Qwen3-8B，1,440 轨迹，5 种威胁）**：unsafe commit **69.4% → 9.0%**（**-60.4 pp**，95% CI **[51.4, 69.4]**），compliant commit 相对 structured handoff **无净损失**。
- **In-transit tampering**：未签名 manifest 在 **79%** 变异运行中提交违规；签名 manifest **0%**。
- **Verifier 对比（同轨迹）**：确定性 verifier 捕获违规 **78.7%**（误报 **7%**）；LLM checker 捕获 **59.0%**（误报 **50%**）。
- **Pre-signing injection（一行对抗文本）**：
  - Qwen3-8B：**14.6% → 37.5%**
  - gpt-oss-20b：**11.1% → 63.9%**
  - GPT-5.6-luna：**8.3% → 75.0%**
- **Oracle manifest**：消除全部残余 unsafe commit。
- 模型覆盖：Qwen3-8B、gpt-oss-20b、GPT-5.6-luna。

## ⚠️ 局限性

- **签名不是万能**：论文标题即"Signed but Not Safe"——pre-signing injection 能把签名变成对污染 manifest 的认证，签名反而提供了虚假的安全感。
- 任务为**合成的、可精确评分**的任务，与真实企业工作流（如多轮、有副作用的 agent 操作）存在外部效度差距。
- HMAC 依赖**对称密钥**分发与轮换，密钥管理与多 agent 身份绑定未在摘要中展开。
- 确定性 verifier 依赖"可检查谓词"的可判定性，对无法形式化的软性要求无能为力。
- 预注册 + 未同行评审；代码与任务库需向作者索取，复现门槛较高。

## 💡 建议

- 是否推荐使用：是（作为**防御设计与威胁建模的框架**）
- 适用场景：企业级多 agent 编排中需要保证"用户要求不被 subagent 摘要掉/篡改"的场景；安全评审、agent 权限与完整性设计；对"以为签了名就安全"这一误区的纠正性参考；多 agent 系统的预注册评测方法学参考。
- ⚠️ 注意：落地时必须把 **extraction 阶段**视为真正的信任边界，单独为其加上隔离、复核或双模型交叉验证，否则签名只会给出虚假保证。
