## 核心贡献

> 提出 **KnowForge** —— 严格按 job 分工的 RAG pipeline（Locator 搜 / Judge 桥接 / Deep Reader 读），在 open-domain multimodal document QA 上超越 single-agent 多工具方案。

1. **Job 严格分工**: Locator-only-search / Judge-bridge-second-hop / Reader-only-read
2. **Typed size-bounded evidence pool**: 统一各 search ranking
3. **M3DocVQA SOTA**: 自托管 Qwen3.6-35B-A3B → F1 47.5（+11.0 vs M3DocRAG）

---

## 技术方案

### 核心思想

RAG agent 普遍把 search + read 两类工具都丢给同一模型自己调度 → 调度策略不可靠。按 job 分：搜与读分离，第二跳由 deterministic code-scheduled bridge 强制。

### 关键技术

| 技术 | 说明 |
|------|------|
| Hybrid-retrieval knowledge-point index | 检索底层 |
| Locator agent (search-only) | 只能调用 search tool |
| Code-scheduled Judge | 第二跳 bridge（LLM 不自由选）|
| Typed size-bounded evidence pool | 各 search ranking merge |
| Deep Reader (read-only) | 只能读 text/image/table |
| Format checker synthesizer | 输出格式约束 |

---

## 实验结论

- **数据集**: M3DocVQA (2,441 Q / 3,368 PDF), MultiHop-RAG, MMLongBench-Doc
- **结果**:
  - M3DocVQA: **F1 47.5**（自托管 Qwen3.6-35B-A3B，+11.0 vs M3DocRAG，+7.1 vs one-shot RAG）
  - DeepSeek-V4-Flash: F1 53.5
  - MultiHop-RAG: **73.5 acc**（vs SOTA RAG/GraphRAG 71.2）
  - MMLongBench-Doc: 同模型 **34.8 → 47.0**（≈ GPT-4o reading page images 46.3）

---

## 局限性

- 多组件 pipeline 工程复杂、调试成本高
- 自托管 Qwen3.6-35B-A3B 仍需 GPU 资源
- "Per-job ablations" 揭示 gain 来源但未给组合最优比

---

## 实现建议

- **实现难度**: 高（5 组件 + 多模型协作）
- **预期性能**: open-domain multimodal DocQA SOTA 级别
- **适用场景**: 企业级多模态文档 QA、RAG-as-a-service 升级
