# EvoCodeAgent: Project-Level Code Generation via Architecture-Code Co-Evolution and Experience-Guided Repair

> **arXiv**: [2611.06328](https://arxiv.org/abs/2611.06328)
> **发表日期**: 2026-11-04
> **分类**: cs.SE
> **会议/期刊**: arXiv preprint

## 📋 摘要

项目级代码生成（project-level code generation）旨在从高层需求自动合成完整软件仓库，产出内聚的多文件系统、模块结构良好且跨文件依赖一致。尽管 LLM 在规格理解与代码合成上能力强劲，现有方法仍存在三个关键缺陷：第一，许多方法依赖**静态架构设计**，无法在迭代生成过程中自适应，导致架构与实现之间的错配（misalignment）不断累积；第二，缺乏跨迭代**积累与复用经验**的机制，造成重复性错误与效率下降；第三，常常依赖**独立的 LLM 评估**中间产物，长上下文推理下透明度有限且可靠性存疑。本文提出 EvoCodeAgent——一个以状态为中心的（state-centric）项目级代码生成框架：从结构化项目规格初始化一个**不断演化的架构状态**，并持续调和"来自架构与骨架（skeletons）的预测关系"与"从已生成代码中抽取的实际关系"。框架还利用**工具接地的验证证据**（tool-grounded verification evidence）支撑可靠的状态更新，并从既往修订尝试中**抽象出可复用的修复经验**以指导后续生成。在不同规模的项目级基准上的大量实验（含 DevBench 与 CodeProjectEval）表明 EvoCodeAgent 持续优于基线方法。

## 🎯 核心贡献

1. 提出 **EvoCodeAgent**：状态中心的项目级代码生成框架，用一个持续演化的架构状态贯穿生成循环，取代静态架构设计。
2. **架构–代码协同演化（co-evolution）**：持续调和架构/骨架层面"预测的"跨文件关系与已生成代码中"实际的"关系，从而抑制架构漂移与实现错配。
3. **工具接地的验证证据**：用可执行工具（测试/运行）产出的证据驱动状态更新，替代不可靠的独立 LLM 评审，解决长上下文下 LLM 评估透明度与可靠性不足的问题。
4. **经验引导的修复（experience-guided repair）**：从历次修订失败中抽象出可复用的修复经验，注入后续生成，抑制重复性错误、提升效率。
5. 在 **DevBench** 与 **CodeProjectEval** 上取得 SOTA，GPT-5 设定下单元测试通过率分别为 **60.48%** 与 **27.73%**，较最强基线提升幅度最高达 **53.5%**。

## 🔧 方法/架构

核心是"状态 ↔ 生成 ↔ 验证 ↔ 修复"的闭环：

- **架构状态 $\mathcal{S}$**：由结构化项目规格初始化，包含模块、接口、跨文件依赖关系等。
- **预测关系 vs 实际关系**：架构与骨架层面给出 $\mathcal{R}_{pred}$，代码抽取给出 $\mathcal{R}_{real}$，两者差异驱动状态更新：

```math
\Delta \mathcal{S} = \mathcal{S} \oplus \mathrm{Reconcile}\big(\mathcal{R}_{pred},\, \mathcal{R}_{real},\, \mathcal{E}_{verify}\big)
```

  其中 $\mathcal{E}_{verify}$ 为工具接地验证证据（单元测试、静态检查、执行反馈）。
- **验证证据来源**：执行类工具的确定性输出，替代 LLM-as-judge 的中间产物评审。
- **经验抽象**：从失败修订轨迹中提炼可复用修复模式（repair experience），作为后续生成的条件/提示资产：

```math
\mathcal{E}_{exp} \leftarrow \mathcal{E}_{exp} \cup \mathrm{Abstract}(\text{revision attempt},\ \text{failure cause})
```

## 📊 实验结果

- **DevBench（GPT-5 设定）**：单元测试通过率 **60.48%**。
- **CodeProjectEval（GPT-5 设定）**：单元测试通过率 **27.73%**。
- **相对最强基线的提升**：最高达 **53.5%**（相对提升幅度）。
- 摘要未披露其他模型的单元测试通过率与绝对数值（详见原文实验章节）；涉及基准为 DevBench、CodeProjectEval（不同规模的项目级基准）。

## ⚠️ 局限性

- 结果以 **GPT-5** 为主要设定，迁移到较小开源模型上的效果未在摘要中说明；模型成本较高。
- CodeProjectEval 上 **27.73%** 的通过率表明绝对水平仍低——项目级生成远未解决。
- **53.5%** 是"最高达"的相对提升，掩盖了不同基线/任务上的波动，稳定性需查原文表格。
- 状态演化与关系抽取带来显著的 token 与工具调用开销；摘要未给成本数据。
- 修复经验的抽象与复用方式依赖具体项目结构，跨语言/跨领域泛化性未知。
