## 核心贡献

> 评估器-执行器错配被量化：14B 模型的 20 次 rollout 不值 7B agent 自身的 2 次，且会偏好相反修复。

1. 提出并系统测量「评估器—执行器错配」：修复方法用贪心回放、更强模型、环境 oracle 或读日志的 judge 给候选修复打分，但这些评估器选出的修复未必有利于**实际执行该修复的 agent**。
2. 在固定失败轨迹与候选单步修复的前提下，用部署策略的独立 rollout 给每个候选打标签，度量各评估器选择所损失的部署价值。
3. 量化结果：贪心回放比用部署 agent 自身 rollout 选择多损失 0.08–0.13 的期望净成功率增益（ALFWorld）与 0.06–0.13 的净奖励（WebShop）；用 Qwen2.5-14B 替 Qwen2.5-7B 选修复损失高达 0.25。

## 技术方案

### 核心思想

LLM agent 失败后，修复方法要决定两件事：替换哪个动作、换成什么。现有做法用四种方式给候选修复打分：**贪心回放**（greedy replay）、**更强的模型**、**环境 oracle**、以及**读取失败日志的 judge**。

本文的提问方式非常精确：**这些评估器选出的修复，对真正要执行它的那个 agent 是否有帮助？** 换句话说，评估器与执行器之间存在错配的可能 —— 一个在评估视角下"更好"的修复，在执行视角下可能更差。

实验设计的关键在于**固定**：保持失败轨迹与候选单步修复不变，然后为每个候选打上**部署策略的独立 rollout** 标签，用这个 ground truth 衡量各评估器的选择损失了多少部署价值。这就把「评估器好不好」变成了一个可量化的损失函数。

结果非常尖锐：
- 贪心回放比用部署 agent 自身 rollout 选择多损失 **0.08–0.13** 的期望净成功率增益（ALFWorld）、**0.06–0.13** 净奖励（WebShop）
- 用 **Qwen2.5-14B** 替 **Qwen2.5-7B** 选修复，在 ALFWorld 损失 **0.25**
- **14B 模型的 20 次 rollout 不比 7B agent 自己的 2 次 rollout 更值钱**
- 新鲜 rollout 确认两个模型在分歧案例上**偏好相反的修复**
- 不同家族、相近规模的模型之间，损失在两个环境中双向出现（0.07–0.17）

最后一条尤其重要：这不是「大模型更强所以更差」的简单故事，而是**模型间不兼容**的问题。

### 关键技术

| 技术 | 说明 |
|------|------|
| 评估器—执行器错配框架 | 固定失败轨迹与候选修复，用部署策略 rollout 作为 ground truth 标签 |
| 部署价值损失度量 | 对每个评估器计算其选择相对最优选择损失的期望净成功率 / 净奖励 |
| 四类评估器对比 | 贪心回放、更强模型 rollout、环境 oracle、读日志 judge |
| 等预算对照 | 在相同 rollout 预算下比较不同规模模型的选修复能力 |
| 分歧案例复核 | 用新鲜 rollout 验证不同模型确实偏好相反的修复 |
| 修复位置标签敏感性 | 分析评分执行器如何改变修复位置标注与方法选择 |

## 实验结论

- **数据集**: ALFWorld、WebShop 两个交互环境
- **基线**: 贪心回放、更大规模模型 rollout（Qwen2.5-14B）、环境 oracle、日志 judge
- **结果**: 贪心回放损失 0.08–0.13 期望净成功率增益（ALFWorld）、0.06–0.13 净奖励（WebShop）；用 14B 替 7B 选修复在 ALFWorld 损失 0.25、WebShop 0.07；14B 的 20 次 rollout 不值 7B 自身的 2 次；跨家族同规模模型的损失在两个环境中双向出现（0.07–0.17）。

- **最有价值的一条**：14B 模型的 20 次 rollout 不比 7B agent 自己的 2 次 rollout 更值钱 —— 「用更大的模型评估」这条默认策略被证伪。
- 不同家族同规模模型偏好**相反的修复**，说明这是不兼容问题而非能力问题。
- 0.25 的 ALFWorld 损失幅度很大，说明评估器选择是 agent 修复流程中的关键瓶颈。
- 「固定轨迹 + 独立 rollout 打标签」的实验设计，使错配成为可测量的量，这是可复用的方法论。
- 评分执行器还会改变修复位置标注与方法选择，意味着评估环节的副作用不止于打分本身。

## 局限性

['固定候选单步修复，若允许多步修复或更长的修复序列，错配的形态可能不同。', '仅两个交互环境与一个模型家族，规模有限。', '论文给出诊断与量化，未直接给出改进的修复选择策略。', '部署策略 rollout 本身有方差，标签噪声会部分稀释测得的错配。']

---

## 实现建议

- **实现难度**: 中（需要环境 rollout 基础设施与候选修复枚举）
- **适用场景**: Agent 自我修复、离线评估与在线策略的匹配、模型迁移时的 agent 调试
- **建议**: **给 agent 选修复方案时，用 agent 自己的 rollout，而不是更大的模型** —— 本文证明后者不仅更贵（20 次 vs 2 次）而且更差，且会选到相反的修复。这应当成为 agent 调试的标准实践。

## 原始摘要

```
When an LLM agent fails, repair methods choose which action to replace and what to put in its place. They often score candidate repairs with greedy replay, a stronger model, an environment oracle, or a judge that reads the failed log. We ask whether these evaluators pick repairs that help the agent that will actually execute them. Holding failed trajectories and candidate single-step repairs fixed, we label every candidate with independent rollouts of the deployed policy and measure how much deployment value each evaluator's choice loses. On failures not screened for repair value, pre-specified tests show that greedy replay loses 0.08-0.13 in expected net success gain in ALFWorld and 0.06-0.13 in net reward in WebShop, relative to selection with the deployed agent's own rollouts. At an equal rollout budget, selecting repairs for Qwen2.5-7B with Qwen2.5-14B rollouts loses 0.25 in ALFWorld and 0.07 in WebShop, twenty 14B rollouts per candidate are worth no more than two of the 7B agent's own, and fresh rollouts confirm that the two models prefer opposite repairs on selected disagreement cases. Between similar-sized models from different families, the losses appear in both directions in both environments (0.07-0.17). The scoring executor also changes repair-location labels and method rankings. Repairs should be verified with the executor that will run them, and repair labels should name their executor.
```
