## 核心贡献

> 提出 **LongSearchEval**：**统一 agent 执行协议 + source-constrained 结果验证（Stage 1）+ 回溯式失败节点定位（Stage 2）** 的两阶段框架，**不需要人写 gold answer**；在 **16 个模型 × 100 个真实网页搜索任务 = 1,600 条保留运行**上产出 **6,545 个自动标记的失败节点**，人工验证 **answer-group 标签一致率 94.50%（κ=0.8989）**、**round–group 链接的 feature-correspondence 精度 98.11%（311/317）**，Answer Score / Answer Precision 与人工分的 Pearson 相关分别达 **0.9054 / 0.9132**。

1. **统一轨迹采集协议** — 16 个模型共用同一 ReAct controller 与受限工具接口 `𝒲`，逐轮记录显式 reasoning state、工具动作与观察（含搜索结果、网页正文、工具失败），保留**未成功的搜索、中间修订、最终答案里被丢弃的候选**；公式化地把完整生成过程分解为 `p(F|ℋ_T)·∏ p(h_t,a_t|ℋ_{t−1})·∏ p(o_t|a_t,s_t^web)`，使跨模型比较建立在同一交互条件上。
2. **Stage 1：source-constrained outcome verification** — 只用 **agent 自己引用的网页**核验其最终答案中的 answer groups，无需人工撰写 gold answer；输出 Answer Score（AS）、Answer Precision（AP）、Upper Score 等百分比指标，并做 **model-identity blind** 判定（judge 不知模型身份，判定后才挂 ID）。
3. **Stage 2：retrospective failure-node localization** — 在归一化的 round 上审计，把被标记的失败节点关联到 Stage 1 判为 incorrect 的 answer groups；**不需要隐藏的 chain-of-thought、不需要访问 web**，两阶段均 model-identity blind。
4. **可扩展的评测语料** — **1,600 条保留轨迹**覆盖 16 个 LLM（8 个家族）× 100 任务，含 **7,685 个 answer groups、42,658 个归一化 rounds、1,600 份存储 rubric**；轨迹采集耗时 **1,037 小时**、评测耗时 **318 小时**（累计运行时）。
5. **人类验证的可靠性证据** — 对 **946 个 answer group**（来自 200 份响应）的人工审计：**894/946 一致（94.50%）**；AS/AP 的 Pearson 95% CI 分别为 [0.8496, 0.9519] 与 [0.8595, 0.9588]，MAE 分别为 4.88 分与 4.45 pp；对 **全部 317 条保留的 round–group 链接**审计确认 **311 条（98.11%）**，CI [96.15, 99.40]；两位人工审计者之间的一致率为 160/172（93.02%，κ=0.8574）。
6. **同等答案分、不同搜索画像** — 揭示出"答案分相同但搜索工作量迥异"的模型对：DeepSeek-V3.2 与 V4-Flash 的 AS 分别为 **54.38 / 53.90**（配对差 0.48 pp，CI [−6.03, 6.95]），但前者平均只做 **13.75 次搜索、读 22.29k 字符**，后者 **21.99 次搜索、37.60k 字符**（少 37.5% 搜索、少 40.7% 文本）。

## 技术方案

### 核心思想

现有 DeepSearch 评测沿两条线走，但**彼此不接**：一条线评"最终答案是否有来源支撑"（GAIA、AssistantBench、LiveResearchBench、BrowseComp、RAGChecker、RAGTruth 等），对象主要是生成的答案及其证据；另一条线做"过程级诊断"（Let's Verify Step by Step、ProcessBench、AgentBoard、error snowballing、TELBench、DRIFT），对象是中间步骤。但两者都缺少**真实保留的交互轨迹**——要么用模拟轨迹，要么从最终答案事后重构轨迹。

LongSearchEval 的做法是把两者接起来：**在统一协议下采集真实轨迹 → 用 agent 自己引用的来源核验答案（Stage 1）→ 以 Stage 1 判定为条件，在轨迹里回溯定位与错误答案相关的证据（Stage 2）**。

关键的工程取舍是**放弃 gold answer**。Stage 1 的验证问题是"**你引用的这些页面是否支持你的每一个答案组**"，而不是"你的答案对不对"。这避免了人工标注长尾事实答案的巨大成本，也让评测能随 web 变化复用。

```
Task q ──► Shared ReAct Controller ──► rounds: (h_t, a_t, o_t)  ──► F (final response)
              │  统一工具接口 𝒲
              ▼
   Stage 1: Source-constrained verification
     用 F 中引用的 URL 取证据 → 逐 answer group 判 correct / incorrect / unverifiable
     → AS / AP / Upper Score（judge 对模型身份盲）
              │  以 F + Stage 1 判定为条件
              ▼
   Stage 2: Retrospective failure-node localization
     在归一化 rounds 上双 judge + 仲裁 → 标记 error/nonerror
     consensus-error round = failure node → 关联到 incorrect answer group
     （不访问 web、不需要隐藏 CoT）
```

### 关键技术

| 技术/方法 | 说明 |
|------|------|
| Unified ReAct controller | 16 模型共用同一 controller 与工具接口；初始化 ℋ₀=(q)，逐轮更新 ℋₜ=(q,(h_s,a_s,o_s)_{s=1}^t) |
| Weak-tool interface | 刻意"弱"的工具面，保证跨模型比较的交互条件一致 |
| Factorized trajectory likelihood | `p(τ^raw|q,T) = p(F|ℋ_T)·∏_t p(h_t,a_t|ℋ_{t−1})·∏_t p(o_t|a_t,s_{t−1}^web)` |
| Termination rule | `T = min{t : d_t = finalize 或 t = B}`，B 为最大交互预算 |
| Raw trajectory retention | 保留原始 `(h_t, a_t, o_t)` 序列 + 最终响应；不做"只保留最终答案"的合成 |
| Source-constrained verification | 只用 agent 提供的 URL 取证据；多来源冲突、不可验证目标分别处理；不需 gold answer |
| Answer-group extraction | 把最终响应切成答案组（每个组对应一条待核验要求与数量参数），7,685 组 |
| Model-identity blind judging | 两阶段 judge 均不接触模型 ID，判定后才附加 |
| Dual-judge + arbitration | 两 judge 独立判定；分歧时第三人仲裁；共同错误取并集链接与判定的归一化错误类型 |
| Failure node definition | consensus-error round = failure node（自动候选标记）；6,503/6,545 有归一化类型，42 (0.64%) 未分配 |
| Target-status filtering | 排除正确、不可验证、不存在的目标；仅对 Stage 1 判 incorrect 的组做关联 |
| Feature-correspondence criterion | 链接须共享可验证、可定位的特征（实体、URL、供给方、价格）；**仅有主题相似性不算** |
| Rubric reconstruction stability | 1,600 份存储 rubric 的字段级一致性：1,556/1,600 (97.25%)、755/1,600 (47.19%)、927/1,600 (57.94%) |
| Paired task-bootstrap CI | 10,000 次配对 task-cluster bootstrap，量化任务级不确定性（而非重复执行不确定性） |

### 实验设置

| 维度 | 规模 |
|------|------|
| 模型 | 16 个 LLM，来自 8 个家族（GPT-6.1-Sol、GPT-6-Luna-Pro、GPT-5.4、DeepSeek-V3.2、V4-Flash、GLM-5 / GLM-4.7-Flash、Grok-4.20 等） |
| 任务 | 100 个真实网页搜索任务，每任务含运行专属 rubric（按来源组成与选择性改编） |
| 运行规模 | 16 × 100 = **1,600 条保留轨迹**（重试与恢复不新增样本） |
| 语料统计 | 7,685 answer groups、42,658 归一化 rounds、14,734 条可评估记录 |
| 耗时 | 轨迹采集 **1,037 小时**、评测 **318 小时**（累计运行时） |
| 人类审计 | 946 个 answer group（来自 200 份响应，每任务抽 2 份）；第二条 round–group 链路审计覆盖 50 个随机任务的 100 次运行、全部 2,642 个归一化 rounds 中的 317 条保留链接 |
| 统计 | 10,000 次配对 task-bootstrap；95% CI |
| 运行完整性 | 1,600 次运行全部保留：1,567 直接 agent 响应、20 采集期 no-tool 综合、13 回退；1,573 份（98.31%）保存的 validity 指标为真；11 次运行带 premature-answer 标记 |

## 实验结果

| 指标 | 数值 |
|------|------|
| 最优 Answer Score | GPT-6.1-Sol：AS **68.80**、AP **68.34%**、Upper **75.35** |
| 次优 | GPT-6-Luna-Pro：AS **65.88**、AP **67.39%** |
| 最低 UGR | GPT-5.4：**3.56%** |
| 显著 vs 不显著的区分 | Sol–Luna 的 AS 差 **2.92 pp**，配对 95% CI [−5.67, 11.99]（不显著）；GLM-5–GLM-4.7-Flash 差 **14.67 pp**，CI [8.41, 20.82]（显著） |
| 搜索工作量 | 搜索次数 9.49 – 21.99 次/运行；阅读文本 4.78k – 48.02k 字符 |
| 搜索画像对比 | DeepSeek-V3.2 (AS 54.38) vs V4-Flash (AS 53.90)：13.75 vs 21.99 次搜索、22.29k vs 37.60k 字符 |
| 最终 URL 数量 | Grok-4.20 最多，**14.34 个/运行**，但结果分并不领先 |
| 失败节点 | **6,545** 个自动候选标记（其中 6,503 有归一化类型，42 未分配）；8,189 个 nonerror 标签 |

| 含链接的运行数 | **850** 次运行至少有一个已链接候选节点 |

## 局限性

- **不是"错误起点"定位**：论文明确声明 Stage 2 返回的是"与错误答案组相关的轨迹内容关联"，**支持回溯性检查，但不识别 agent 首次做出错误承诺的位置**；一次单独的"错误承诺准则"审计对所审轮次**未标出任何错误标签**，与 failure node 的自动标记形成对照，说明自动标记偏保守/偏宽松的性质需谨慎解读。
- **source-constrained 验证把"未引用"等同于"无支撑"**：答案正确但没给出来源，或引用了未被检索到的页面，都会被判为 incorrect/unverifiable；验证的分数是"引用支撑度"而非"客观真值"（这是换取"无需 gold answer"的代价）。
- **Stage 1 的误判会传导**：target-status 过滤不是语义检查，"Stage 1 的错误会影响保留的关联"，1,145 个错误组最终没有任何内容关联。
- **trajectory 内嵌的模型元信息未用于评测**：所有 1,600 条轨迹都内嵌模型元信息，但评测流程始终保持 model-identity blind。
- **成本极高**：1,037 小时采集 + 318 小时评测，对新任务集的复用成本是主要工程门槛；重复执行的不确定性未被量化（bootstrap CI 只反映任务级不确定性）。
- **运行完整性有瑕疵**：13 次回退、20 次 no-tool 综合、11 次 premature-answer 标记，作者选择"保留并原样评估"而非剔除，这虽避免幸存者偏差，但也把部分失败模式混入了模型分。

## 与知识库既有工作的关系

- 与 [[2026-10-27-2610.35188-v3ast-bench-verifiable-agent-safety]] 同属"**用可核查证据取代黑箱打分**"的一批 2026-10 下旬工作：V³AST 用可执行检查验证环境后果，LongSearchEval 用 agent 自引来源做约束验证，二者都在回答"证据从哪来、谁来判"。
- 与 [[2026-10-27-2610.34855-decoycount-visual-reasoning-misalignment-counting]] 共同指向"**把失败拆解到可定位的单元**"的方法论：DecoyCount 用预注册诱饵定位失败机制，LongSearchEval 用 answer group + 归一化 round 定位失败节点。
- 延续本库"证伪默认假设"主线：**证伪"答案分相同即搜索行为相同"**（DeepSeek-V3.2 与 V4-Flash 答案差 0.48 pp，但搜索次数少 37.5%、文本少 40.7%），主张**结果指标与交互工作量必须联合报告**。
- 与本库中的 OpenClaw / agent 相关工作共同构成"agent 评测必须看轨迹而非只看终点"这一主张的证据链。

## 建议

- **是否推荐使用**: 有条件推荐（框架设计值得借鉴；全量复现成本过高）
- **适用场景**: DeepSearch / 检索增强 agent 的结果评测与失败回溯；无 gold answer 场景下的事实性核验；多模型搜索策略画像对比
- **可借鉴要点**:
  1. **两阶段解耦框架可直接移植**（且不限于搜索）：Stage 1 = 用 agent 自己产出的证据（引用的 URL / 执行的命令 / 生成的文件）做约束验证；Stage 2 = 以 Stage 1 判定为条件做条件化的轨迹回溯关联。判定全程对模型身份盲，最后才挂 ID，避免品牌偏置。
  2. **强制"结果 + 工作量"双报告**：不要只报答案分。至少同时报搜索/调用次数、读取字符数、工具失败率、premature-answer 标记率——否则同等分数的模型会被误判为等价。LongSearchEval 的 AS/AP/Upper + 行为诊断双列式输出是一个现成模板。
  3. **链接判据用"可验证特征"而非"主题相似"**：作者用 entity / URL / provider / price 这类可定位特征来认定 round–group 关联，并把这一判据写进人工审计规程（98.11% 精度即来自它），这是让"回溯定位"可复核的关键设计。
