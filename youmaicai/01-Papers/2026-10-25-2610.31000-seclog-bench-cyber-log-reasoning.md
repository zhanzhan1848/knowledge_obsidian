## 核心贡献

> 现有网络安全日志数据集**规模有限、依赖单一来源证据、且只有二分类/多分类攻击标签而没有推理过程的稠密标注**。SecLog-Bench 用一个可扩展的**仿真平台**（覆盖 **29 个攻击场景**）生成多来源日志（审计日志 + 应用日志 + 网络流量），并为每条样本标注**必要上下文**与**结构化逐步证据链**。评测八个主流 LLM 的**事后攻击进程推理（post-detection attack-progress reasoning）**：**最好模型仅 44.44% 准确率、45.07% Macro-F1**，推理链也不可靠。

1. **可扩展的日志生成仿真平台**：覆盖 **29 个攻击场景（29 attack scenarios）**，支持**重复执行**与**集成新场景**，从而**规模化生成带攻击阶段标签（attack-stage labels）** 的网络安全日志。
2. **多来源证据（multi-source logs）**：联合使用 **audit logs、application logs、network traffic** 三类来源分析同一攻击 —— 直接针对现有数据集「依赖单来源证据」的缺陷。
3. **稠密的过程标注**：为每个样本标注 **网络安全日志推理的必要上下文（essential context）** 以及**结构化逐步证据链（structured step-by-step evidence chain）** —— 补上现有数据集缺失的推理过程监督。
4. **八个主流 LLM 的系统评测**，任务为 **post-detection attack-progress reasoning**（在已检测到入侵后判断攻击进行到哪一步）。
5. **提供「scaffolded evidence」（脚手架证据）设定**，把「模型是否具备推理能力」与「模型能否从海量日志中自己找到证据」两个变量分离。

## 技术方案

### 核心思想

**目标任务的独特性**：SecLog-Bench 不问「有没有被攻击」（那只需要二分类标签），而问 **post-detection attack-progress reasoning** —— **入侵已被发现后，攻击目前进行到了哪个阶段（kill chain 的哪一步）**。这是一个需要**推理链**而非单点判断的任务。

**为什么需要脚手架证据**：真实日志量巨大，模型失败时无法区分「不会推理」与「找不到证据」。因此数据集为每个样本标注了 **essential context**（推理必需的上下文片段），让评测可以**先给证据，再测推理**。

**三个关键设计**：

| 设计 | 解决的问题 |
|------|-----------|
| 仿真生成平台 + 29 攻击场景 + 阶段标签 | 数据**规模**与**可扩展性**（可重复执行、可持续加入新场景） |
| audit / application / network 三源日志 | **单来源证据**不足 —— 真实攻击在三类日志中留痕不同 |
| 必要上下文 + 逐步证据链标注 | 缺少**推理过程**的稠密监督 |

**Scaffolded evidence 的评测逻辑**：给定 (a) 脚手架化的证据片段，(b) 相关的上下文，模型需输出攻击所处阶段，并给出推理链。

### 关键技术

| 技术 | 说明 |
|------|------|
| **Extensible simulation platform** | 可重复执行、可接入新攻击场景的日志生成平台 |
| **29 attack scenarios** | 覆盖的攻击场景数 |
| **Attack-stage labels** | 每个样本标注攻击所处阶段，支持进程级推理评测 |
| **Multi-source log fusion** | audit logs + application logs + network traffic 联合分析 |
| **Essential context annotation** | 标出推理必需的上下文，使「推理失败」与「证据检索失败」可分离 |
| **Structured step-by-step evidence chain** | 逐步证据链，供 SRF1 等推理质量指标使用 |
| **Post-detection attack-progress reasoning** | 核心任务：检测后判断攻击进度 |
| **SRF1（Stage Reasoning F1）** | 推理质量的 F1 变体；摘要给出最高仅 **54.87%** |
| **Macro-F1** | 分类维度的宏平均 F1 |

## 关键实验结果

| 项目 | 结果 |
|------|------|
| **攻击场景数** | **29** |
| **日志来源** | **3 类**：audit logs / application logs / network traffic |
| **评测模型数** | **8 个主流 LLM** |
| **最佳模型准确率** | **44.44%** |
| **最佳模型 Macro-F1** | **45.07%** |
| **最高 Stage Reasoning F1（SRF1）** | **54.87%** |
| **核心定性发现** | 模型推理**不可靠**；**即使预测正确，推理链也可能有缺陷** |
| **另一关键发现** | **推理质量与预测准确率常常不一致（misaligned）** |

---

## 关键结论

1. **当前 LLM 在「攻击进行到哪一步」这个问题上能力有限。** 即使**已经给到脚手架证据**（即不用自己找日志），最好模型也只有 **44.44% 准确率 / 45.07% Macro-F1** —— 说明瓶颈**不只是检索，而是推理本身**。
2. **推理质量指标与准确率指标必须分开报告。** 最高 SRF1 仅 **54.87%**，低于最佳准确率 —— 说明很多「猜对」的答案是**推理链不成立的偶然命中**。只报准确率会**高估**模型在 SOC 分析师替代场景中的可用性。
3. **「答对但理由错」是普遍现象。** 摘要明确指出：**即使正确预测也可能伴随有缺陷的推理**。这对「让人审核模型推理」的部署模式是直接的风险提示 —— **审核者会被正确结论误导而忽略错误链条**。
4. **多源日志是必需的。** 单一来源（只给 audit log 或只给 network traffic）无法覆盖攻击链各阶段；这也是现有数据集的局限来源。
5. **可扩展仿真平台是这类基准可持续的关键。** 29 个场景 + 重复执行 + 可接入新场景，使基准能随威胁演化更新 —— 比一次性手工标注的数据集更有生命力。

## 局限性

- **摘要未给出样本总量** —— 29 个场景下生成了多少条样本、多少条训练/测试样本**均未说明**，「scalable」是设计属性而非已展示的规模数字。
- **SRF1 的定义未给出** —— 只给最高 54.87%，未说明是何种 F1 变体、如何计算、如何与证据链对齐。
- **未列出八个模型的名字**，也**未给出逐模型结果** —— 无法判断 44.44% 与随机基线/多数类基线之间的差距有多大。
- **任务范围收窄于 post-detection**：不测「是否被攻击」的检测阶段，因此**不能直接用来评 SOC 的告警分诊**能力。
- **仿真生成日志 vs 真实生产日志存在 domain gap** —— 仿真日志的规律性、噪声结构与真实攻击可能差异显著，44.44% 的结论**外推到真实环境需谨慎**。
- **脚手架证据的构造方式未详述** —— 谁来判定「essential context」？若由强模型或人工挑选，可能引入偏置并**抬高绝对数值**。
- **无代码/数据链接**（摘要未给）。
- **作者未在摘要中声明评测的模型代次**，无法判断是否存在更强的未测模型。

## 实现建议

- **实现难度**：高（需自建可扩展攻击仿真平台、生成多源日志、标注证据链）
- **预期性能**：以「脚手架证据 + 8 个主流 LLM」为参考，目标模型大概率为 **40%–50% 准确率、45% 上下 Macro-F1**，SRF1 上限约 **55%**
- **适用场景**：**安全运营中心的攻击进程推理 / 告警分诊**；**日志分析 LLM 的选型**；把 LLM 结果用于**人工复核流水线**时的期望值设定（因「对但理由错」比例高）
- **团队行动**：若自建安全 LLM 评测，**必须同时报告推理链指标（SRF1 类）与准确率**，否则会高估可用性 —— 这是本文最可迁移的方法论结论
