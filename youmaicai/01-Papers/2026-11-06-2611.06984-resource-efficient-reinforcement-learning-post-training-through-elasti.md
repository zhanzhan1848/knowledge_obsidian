# Resource-Efficient Reinforcement Learning Post-Training through Elastic Expert Parallelism

## 摘要
RL 后训练能提升 LLM 能力，但**生成训练响应是主要计算瓶颈**。在 MoE 模型中，**已完成自身响应分配的 worker 可能仍然被占用** —— 因为他们的专家仍被处理更长响应的 worker 需要。基线中**约三分之一的 worker 占用时间发生在本地响应生成结束之后**。本文提出 **FlexFloor**：在同步响应生成期间**允许更早释放资源**，同时保持进行中响应所需的专家计算。FlexFloor **联合调整响应调度与活跃 worker 组** —— 用历史响应长度与内存约束来指导批处理与 prompt 放置，然后**渐进释放 worker**，同时维持专家可用性与正确通信。相比 verl 基线，FlexFloor 在单位占用计算时间内生成**约 65.40% 更多响应 token**，响应生成吞吐提升 **52.74%**，且**观测到的 rollout 奖励变化很小**。

## 核心贡献
1. 定位 RL 后训练的具体浪费来源：**约 1/3 的 worker 占用时间发生在本地响应生成结束之后**（因为专家仍被更长响应的 peer 需要）
2. 提出 **FlexFloor**：同步响应生成期间的**弹性专家并行**调度，联合调整响应调度与活跃 worker 组
3. 机制：用**历史响应长度 + 内存约束**指导批处理与 prompt 放置，再**渐进释放 worker**（保持专家可用性与正确通信）
4. 效果：单位占用计算时间**多生成 65.40% 响应 token**，吞吐 **+52.74%**，rollout 奖励变化很小

## 方法与架构
**问题定位**：MoE RL 后训练中，worker 完成本地响应后仍因专家被占而无法释放 → 基线约 **1/3 占用时间浪费在生成完成之后**。

**FlexFloor 调度**：
```
1. 依据历史响应长度 + 内存约束 → 决定批处理组成与 prompt 放置
2. 响应生成进行中 → 渐进释放 worker
   （约束：被释放的 worker 的专家不得被在途响应需要；通信保持正确）
3. 联合调整「响应调度」与「活跃 worker 组」
```

**评测**：verl 基线对比；指标为单位占用计算时间的响应 token 数、响应生成吞吐、rollout 奖励。

## 实验结果
- **约 65.40% 更多响应 token / 单位占用计算时间**
- **响应生成吞吐 +52.74%**
- **rollout 奖励变化很小**（无明显质量损失）
- 基线浪费量级：**约 1/3 的 worker 占用时间在生成完成后**

## 局限性
- 依赖**历史响应长度**的统计分布，分布漂移时调度可能次优；
- 「渐进释放」的通信正确性依赖分布式专家并行实现细节，跨集群可移植性未验证；
- 仅报告吞吐与奖励，未报告 wall-clock 端到端加速（可能受其他阶段串行瓶颈限制）。

## 值得注意的点
**「1/3 的 worker 时间花在生成完成之后」** 是一个容易被忽视但极可观的系统性浪费 —— 这类优化往往比改进算法本身更划算。与今日 StrataFlux / FlashOffloading 同属「把已算力用满」的工程路线，是 RL 后训练成本控制的第一课。
