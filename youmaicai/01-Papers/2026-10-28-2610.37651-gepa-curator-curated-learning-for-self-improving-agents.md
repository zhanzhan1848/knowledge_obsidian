## 核心贡献

> **提示优化器（prompt optimizer）最大的问题不是优化得不够好，而是「喂给它学习的材料本身是垃圾」。** GEPA-Curator 通过**筛选哪些 agent 经历值得用于提示优化**来提升自改进 agent。

1. **关键论点**：现有反射式提示优化器（如 **GEPA**）从**失败的 rollout** 中学习，但 agentic 失败可能来自：
   - **提示词本身的弱点**（可学）
   - **harness（执行框架）的限制**（不可学）
   - **随机执行**（不可学）
   - **噪声判官（noisy judges）**（不可学且有害）
   - ⇒ 此类失败**可能不提供有用的学习信号，甚至有害**
   - ⇒ **必须筛选哪些任务提供给提示优化器**
2. **提出 GEPA-Curator**，两个组件：
   - **Task Curation（任务策展）**：过滤掉**可能提供噪声或不可靠学习信号**的任务
   - **Prior Success Retrieval（先验成功检索）**：为某任务**选择性检索过去的成功轨迹**，作为**额外上下文**提供给提示优化器
3. **实验结果**：
   - 在 **GoBrowse, ALFWorld, AppWorld, τ-bench** 上评测
   - 优化器模型：**Gemini 3.1 Pro** 与 **Claude Opus 5**
   - **匹配或超过两个基线的平均性能**
   - 相对 **GEPA 提升最多 20.7%**，相对 **ACE 提升最多 21.2%**

## 技术方案

### 核心思想

反思式提示优化（reflective prompt optimization）的隐含假设是：**所有失败都教得会东西**。这个假设在 agent 场景不成立 —— 很多失败是环境的随机性或判官噪声造成的，把它们喂给优化器等于**教它从噪声中学**。

GEPA-Curator 的思路是**先做数据策展，再做优化**：

```text
❌ 朴素 GEPA:
   所有失败 rollout → 优化器 → 提示更新
   （其中相当一部分失败是噪声 → 污染优化）

✅ GEPA-Curator:
   1. Task Curation:      过滤 → 只保留「失败原因可归因于提示」的任务
   2. Prior Success Retrieval: 补充该任务过去的成功轨迹作为额外上下文
   → 优化器看到的是「干净的失败 + 相关的成功」
```

### 关键技术

| 技术 | 说明 |
|------|------|
| **Task Curation** | 过滤掉学习信号可能噪声/不可靠的任务 |
| **Prior Success Retrieval** | 检索该任务的历史成功轨迹作附加上下文 |
| **GEPA** | 基础反思式提示优化器（基线也是组件基础） |
| **ACE** | 对比的另一提示优化基线 |
| **自改进 agent 循环** | 候选提示 → rollout → 反思 → 更新 |

## 公式

```math
\text{朴素 GEPA 的学习信号}:\quad
\mathcal{S}_{\text{naive}} = \big\{ \text{reflect}(\tau_i) \;\big|\; \tau_i \in \text{Rollouts}_{\text{all}} \big\}
```

```math
\text{策展后的学习信号}:\quad
\mathcal{S}_{\text{curated}} =
\underbrace{\big\{ \text{reflect}(\tau_i) \;\big|\; \tau_i \in \mathcal{F},\; \text{signal}(\tau_i) \text{ reliable} \big\}}_{\text{Task Curation}}
\;\cup\;
\underbrace{\big\{ \text{retrieve}(\tau^+) \;\big|\; \tau^+ \in \mathcal{P},\; \text{task}(\tau^+) = \text{task}(\tau) \big\}}_{\text{Prior Success Retrieval}}
```

```math
\text{策展质量判别（示意）}:\quad
\mathbb{E}\big[\Delta \text{perf} \mid \text{curated} \big] \;\ge\; \mathbb{E}\big[\Delta \text{perf} \mid \text{naive} \big]
\qquad
\text{因为 } \mathbb{E}[\text{noise contribution}]_{\text{naive}} > 0
```

## 代码片段

```python
# 概念性伪代码：GEPA-Curator
class GEPACurator:
    # 在 GEPA 之外，额外做任务策展与先验成功检索。

    def __init__(self, base_optimizer, trajectory_store, signal_reliability_fn):
        self.opt = base_optimizer                 # GEPA
        self.store = trajectory_store            # 历史成功/失败轨迹
        self.reliability = signal_reliability_fn # 判断该失败是否可学

    def curate_tasks(self, rollouts):
        # 组件 1：过滤掉学习信号可能噪声或不可靠的任务。
        return [r for r in rollouts
                if self.reliability(r)          # 排除 harness 限制 / 随机性 / 噪声判官
                and r.failure_attributable_to("prompt")]

    def retrieve_prior_success(self, task):
        # 组件 2：检索同一任务过去的成功轨迹作为额外上下文。
        past = self.store.successes_for(task)
        return pick_diverse(past, k=3)           # 相似但不同的成功范例

    def optimize(self, rollouts):
        clean = self.curate_tasks(rollouts)
        for r in clean:
            r.extra_context = self.retrieve_prior_success(r.task)
        return self.opt.optimize(clean)          # 底层的 GEPA 优化


# 可靠性判别：区分「可学的提示失败」与「不可学的环境噪声」
def signal_reliability(rollout):
    # 重跑一次，看失败是否稳定复现
    repeats = [replay(rollout.task, n=3) for _ in range(3)]
    consistency = fraction_of_same_outcome(repeats)
    if consistency < 0.8:
        return False          # 随机性 → 不可学
    if rollout.verdict_from_noisy_judge:
        return False          # 判官噪声 → 不可学且有害
    if rollout.harness_limitation:
        return False          # 框架限制 → 不可学
    return True
```

## 实验结论

- **基准**: GoBrowse, ALFWorld, AppWorld, τ-bench
- **优化器模型**: Gemini 3.1 Pro, Claude Opus 5
- **基线**: GEPA, ACE
- **结果**:

| 对比 | 提升（最多） |
|------|--------------|
| vs **GEPA** | **+20.7%** |
| vs **ACE** | **+21.2%** |

- **总体**: GEPA-Curator **匹配或超过两个基线的平均性能**

---

## 局限性

1. **策展器的实现细节未给** —— 「哪些任务的失败可归因于提示」是整个方法的核心，但摘要完全没说是怎么判别的（重跑一致性？判官？启发式？）
2. **+20.7% / +21.2% 是「最多」值** —— 平均提升可能小得多，且各基准间的方差未给
3. **可能只做了「减法」** —— 若策展器过于保守，可能只是训练集变小导致过拟合减少，这与「策展质量」是两回事
4. **先验成功检索的收益未单独消融** —— 两个组件的贡献占比不明
5. **计算开销翻倍** —— 需要重跑 rollout 判可靠性 + 检索历史轨迹
6. **与 prompt optimizer 自身能力的混淆** —— 用 Gemini 3.1 Pro / Claude Opus 5 做优化器，与强模型做优化器的效果混淆
7. **「先验成功」在分布外任务上可能有害** —— 检索到的成功可能来自不同的问题实例
8. 摘要提到 agentic 失败来源的分类很细致，但**分类本身的正确性未验证**

## 实现建议

- **实现难度**: 中（在现有 GEPA/ACE 之上加一层策展）
- **预期性能**: 相对 GEPA 最高 +20.7%（取决于策展质量）
- **适用场景**: **有大量 rollout 记录、失败原因混杂的 agent 自改进流水线** —— 长期运行的自主 agent、自动化流程代理
- **落地注意**:
  1. **先做失败归因分析** —— 本方法的前提是你能区分「提示的错」和「环境的错」。若做不到，先建这个判别能力
  2. **最省事的策展实现是「重跑一致性」** —— 跑 3 次看失败是否稳定复现，不稳定的直接排除
  3. **成本要算清** —— 判可靠性要额外 3× rollout，可能比优化本身还贵
  4. **历史轨迹存储要带上失败原因标签**，否则策展无从下手

## 我的评注

> 这篇的洞察很准，而且是对当下「自我改进 agent」热潮的一个**必要的冷水**。
>
> 现在的叙事是「agent 失败了 → 反思 → 优化提示 → 变强」，这条链子被默认是**信息增益为正**的。但本文指出：**多轮 agent 的失败里，有一大块是纯噪声** —— 环境随机性、harness 限制、判官噪声。这类失败被喂给优化器不只是「无用」，而是**主动注入错误信号**。用强化学习的语言说，这是**在奖励信号里混入对抗性噪声**。
>
> 这也解释了为什么 GEPA 的方差往往很大：优化器在拟合的信号里，有一部分根本不来自提示的质量。
>
> 我认同这个方向，但摘要里的**实现空洞**让我没法完全信服 —— 「过滤掉可能提供噪声或不可靠学习信号的任务」，具体怎么判断？摘要没写。如果判别器本身不可靠，整个方法就悬空。如果判别器很可靠（重跑一致性是个好办法），那它本身就是个工程量不小的东西，而这部分贡献摘要里也没写。
>
> 第二个组件 **Prior Success Retrieval** 我觉得更有意思，也更被低估：**把过去的成功轨迹喂给优化器**，相当于给「只学失败」的方法补上了正例。这个直觉很好 —— 反思式优化器通常只看到失败，容易过度修正（把 prompt 改成极端保守的样子）。给正例相当于告诉它「目标区域」在哪。
>
> 20.7% / 21.2% 的提升在 agent 领域算相当大了（这个领域的改进幅度通常是个位数百分比）。但「最多」的措辞 + 缺方差，让我保持谨慎。
>
> 落地判断：**思路值得抄进任何自改进流水线**，尤其是那种跑了大量 rollout、日志里失败原因五花八门的系统。而且第一步几乎零成本 —— 先做失败归因分类，看看你的失败里到底有多少是噪声。
