## 核心贡献

> 端到端最终落在一个 **closed-set decision**（如「选哪个工具」）上的 pipeline，是否一定要用大模型来问？本文系统回答两个问题：**encoder 要多小才够**，以及**它该「联合读所有选项」还是「逐个选项分别读」**。结论：**per-option scoring 优于 joint scoring**；且优势**依赖 reranker 初始化**；代价是 **5–13 倍的 encoder 前向次数**（中位延迟最多 2 倍，但均值超 4 倍）。

1. **系统化的三种子研究（three-seed study）**：在 **32M 参数**规模上，per-option scoring 在 held-out 的 **37-benchmark decision suite** 上以 **chance-corrected skill** 计**超出 joint scoring 5.8 个点**（matched optimizer steps 口径）、**2.8 个点**（approximately matched training compute 口径）。
2. **交叉实验揭示机制**：把「reader（联合 vs 逐选项）× 初始化（raw encoder vs reranker）」交叉后发现 —— **per-option 的优势需要一个 reranker 初始化**（其 query-candidate pair 输入形式恰好匹配 per-option 读取）；**从 raw encoder 出发两种 reader 无法区分**。这是本文最有价值的**机制性诊断**。
3. **六个已发布的 joint encoder 的大规模对比（17M → 1B 参数）**：其中 **68M 与 150M** 模型在 **209 个 overlap-audited System1-Arena 任务**上比 **435M 的 DeBERTa-v3 zero-shot 分类器**高 **4.9 与 5.9 个准确率点**，并在训练中未见过的 **145 个任务**上**至少打平**。
4. **延迟画像**：最小的模型在 **16 个处理线程上 14 毫秒**回答一个中位请求，对比 DeBERTa-v3 分类器的 **728 毫秒**（约 **52 倍**差距）。
5. **鲁棒性发现**：**重排选项顺序会改变 joint 模型的 12–23% 的答案**；**per-option scoring 完全不受影响（none）**。

## 技术方案

### 核心思想

很多 LLM pipeline 的最后一步其实是一个**闭集选择**（closed-set decision）：从 N 个候选（如工具、标签、答案）中选一个。用大模型 prompt 来做这件事有两个毛病：**慢**，而且**对选项顺序敏感（order-sensitive）**。

本文把问题拆成两个正交维度：

- **规模轴**：encoder 最小能到多大仍可用？
- **读取轴**：
  - **Joint scoring（联合读）**：把 query 与所有候选拼在一起，一次前向输出所有候选的分数 —— 1 次前向，但**候选间互相干扰，且顺序影响结果**。
  - **Per-option scoring（逐选项读）**：query 与每个候选**分别**配对，N 次前向独立打分 —— 天然顺序不变，但**前向次数 ×N**。

**核心发现（机制）**：per-option 的优势**不是结构性的必然**，而依赖于**初始化**：reranker 预训练的权重天然就是「query-candidate pair」形态，与 per-option 的输入格式匹配；**从 raw encoder 出发，两种 reader 表现无法区分**。这意味着**「per-option 更好」这个结论是可被训练配方改变的**，而非架构定理。

**关键评测口径**：使用 **chance-corrected skill**（校正了随机基线的能力分）而非原始准确率 —— 对闭集任务，这更公平。

### 关键技术

| 技术 | 说明 |
|------|------|
| **Joint scoring** | query 与全部候选拼接，单次前向打分所有候选；有候选干扰与顺序敏感 |
| **Per-option scoring** | query 与每个候选独立配对打分；顺序不变，但 N 次前向 |
| **Reranker initialization** | 关键初始化来源；其 pair 输入格式匹配 per-option 读取 |
| **Raw encoder initialization** | 从预训练 encoder 直接初始化时两种 reader 不可区分 |
| **Chance-corrected skill** | 校正随机基线的闭集能力度量 |
| **Matched optimizer steps / matched training compute** | 两种公平对照口径（结果差异：5.8 vs 2.8） |
| **37-benchmark decision suite** | held-out 采样用于三种子主研究 |
| **System1-Arena** | 外部评测集；**209 个 overlap-audited 任务** + **145 个训练未见任务** |
| **DeBERTa-v3 zero-shot classifier** | 435M 参数的强零样本分类器基线 |
| **Three-seed study** | 三个随机种子，用于控制方差 |
| **Order-sensitivity audit** | 重排候选顺序，统计答案翻转率 |

## 关键结论

1. **闭集决策不必用大模型，68M–150M 的 compact encoder 就够。** 68M 与 150M 的 joint encoder 比 435M 的 DeBERTa-v3 zero-shot 分类器高 **4.9 / 5.9 个准确率点**，且在 145 个未见任务上至少打平；最小模型 **14 ms vs 728 ms**。把「选工具」这一步从 LLM API 换成小 encoder，是**成本结构上的量级改变**。
2. **per-option 优于 joint，但这个结论是「有条件的」。** matched optimizer steps 下 **+5.8**、matched compute 下 **+2.8** —— **训练算力口径下收益减半**，说明部分优势来自额外训练步数而非结构本身。交叉实验进一步表明优势**依赖 reranker 初始化**，raw encoder 下二者不可区分。
3. **顺序敏感性是 joint 架构的结构性缺陷。** 重排选项改变 joint 模型 **12–23%** 的答案，而 per-option **完全不变**。对于选项来自动态生成、顺序不稳定的场景（如工具列表排序），这是**正确性级别的差异**而非精度差异。
4. **代价被中位数掩盖了。** per-option 需要 **5–13 倍**的 encoder passes；中位延迟最多 2 倍，但**均值超 4 倍** —— 意味着**存在长尾慢样本**，中位延迟会低估实际最坏情况。
5. **可复现性门槛**：作者用 three-seed、两种 compute 对照口径、六个已发布模型做交叉验证 —— 方法论密度在同规模论文中偏高。

## 局限性

- **「per-option 更好」并非普遍结论**：外部基准上**在其未见任务中差异不显著**；且优势**需要 reranker 初始化**。对于**从零训练**或只有 raw encoder 的团队，**推荐 per-option 缺乏证据支持**。
- **match 口径的收益落差明显**：5.8（matched steps）→ 2.8（matched compute），**近一半优势来自额外训练预算**。
- **延迟报告不完整**：只给了 16 线程 CPU 的中位延迟（14 ms / 728 ms），**未给 GPU 延迟、吞吐、batch 行为**；且**均值超 4 倍**这一长尾现象没有进一步分析（什么输入导致长尾？）。
- **规模上限信息缺失**：验证集中在 **32M**（主研究）与已发布的 17M–1B（对比），**1B 级别未做 per-option 的完整训练对比**。
- **System1-Arena 评测口径**依赖「overlap-audited」子集（209 任务）与「训练未见」子集（145 任务）的切分，**切分方式与 in-distribution 泄漏检查细节未在摘要说明**。
- **「至多 68M 领先同规模区间」的排行榜测试主要是 in-distribution**，外推性弱。

## 实现建议

- **实现难度**：中（标准 encoder + pairwise 训练；已有 6 个已发布 joint encoder 可直接复用）
- **预期性能**：**68M–150M** 规模在 System1-Arena 上超 435M DeBERTa-v3 **4.9–5.9 个点**；最小模型 **14 ms**（16 线程）；per-option 相对 joint **+2.8 ~ +5.8** chance-corrected skill（前提：reranker 初始化）
- **适用场景**：**工具选择 / 标签分类 / 候选排序**等闭集决策环节；**选项顺序不稳定**的动态场景（必须 per-option）；已有 DeBERTa-v3 / reranker 权重的团队（迁移成本最低）
- **避坑**：若从 raw encoder 起步，先在 32M 规模做三种子的 matched-compute 对照，再决定 reader 形式 —— 否则会误以为结构本身带来 5.8 点
