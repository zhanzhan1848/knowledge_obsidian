## 核心贡献

> 端到端分数无法区分「模型基础能力弱」与「部署方式弱」，导致诊断不可行动。本文提出一个**操作级（operation-level）测量框架**：为每个模型建立**基础画像（foundational profile，来自能力基准）** 与**操作画像（operation profile，来自交互轨迹）**，并定义 **capability realization gap** —— 实际操作表现相对于「按基础能力预测应有表现」的偏离量。

1. **提出 operation-level 测量框架**，打通「基础能力」与「agent 能力」两个长期分离的评估体系。
2. **双重画像表示**：模型 = (a) **foundational profile**（由 capability benchmarks 推导）+ (b) **operation profile**（由 interaction trajectories 推导）。
3. **定义 capability realization gap**：观测到的操作表现**相对于基于基础能力的预测**的偏差 —— 这是一个**有参照基线的残差量**，而不是绝对分数。
4. **15 个模型服务（model services）** 在 **τ²-Bench** 上的实验结论：**基础画像只能部分预测 agentic 操作**；**基础画像相近的模型在执行上可以差别很大**；且这些 gap **在不同任务子集上保持一致**。
5. **操作画像提供增量信息**，能**显著改善对任务分数的预测**。
6. **框架可定位执行偏离（execution departures）到操作级**，从而服务模型开发与 agent 评估。作者声明将发布代码与分析制品。

## 技术方案

### 核心思想

**诊断困境**：一个 agent 在 benchmark 上失败，原因可能是
- (A) 模型**基础能力**不足（不会推理、不会写代码）；
- (B) **部署方式**有问题（harness 差、工具描述不清、上下文组织不当）。

**端到端分数把 A 和 B 混在一起** —— 因而「换一个更强的模型」还是「改一改 harness」这个决策**无法做出**。

**本文的解法**：把 agent 的执行拆成**操作（operations）**层次，然后：
1. 用**能力基准**估计模型**本来应该能到多好**（基础画像 → 预测）；
2. 用**交互轨迹**测出**实际到多好**（操作画像 → 观测）；
3. **两者的差 = capability realization gap**，且这个差**由部署而非模型造成**。

**关键设计选择 —— gap 是有参照的残差**：
$$\text{realization gap}(\text{model}, \text{operation}) = \underbrace{\text{observed operation performance}}_{\text{from trajectories}} - \underbrace{\text{predicted performance from foundational profile}}_{\text{from capability benchmarks}}$$
这比「分数低」信息量大得多：**分数低可能只是模型弱；gap 大意味着模型能力没有被释放出来**。

**「gap 跨任务子集一致」是本文最重要的实证**：如果 gap 在不同子集上保持一致，说明它反映的是**模型的稳定属性**（部署适配性 / 能力-释放模式），而非任务噪声 —— 这使 gap 成为一个**可信的诊断量**。

**「操作画像能显著改善任务分数预测」** 说明操作层信息**不是基础层的冗余** —— 两者是互补的预测因子。

### 关键技术

| 技术 | 说明 |
|------|------|
| **Foundational profile** | 由能力基准（capability benchmarks）推导的模型能力表示 |
| **Operation profile** | 由交互轨迹（interaction trajectories）推导的执行表现表示 |
| **Capability realization gap** | 操作表现的观测值 − 基于基础画像的预测值 |
| **Operation-level decomposition** | 把 agent 执行拆解为可测的操作单元 |
| **Execution departure localization** | 把偏离定位到具体操作，而非只报总分 |
| **τ²-Bench** | 评测所用的 agent 基准 |
| **15 model services** | 实验覆盖的模型服务数量 |
| **Task-subset consistency analysis** | 检验 gap 是否跨任务子集稳定 |
| **Incremental predictability** | 检验操作画像对任务分数预测的增量价值 |
| **Capability vs deployment diagnosis** | 区分「基础能力弱」与「部署弱」两种失败原因 |

## 关键实验结果

| 项目 | 结果 |
|------|------|
| **实验规模** | **15 个模型服务（model services）** |
| **基准** | **τ²-Bench** |
| **基础画像的预测力** | **仅能部分预测 agentic 操作**（foundational profiles only partially predict agentic operations） |
| **相近基础画像的模型** | **执行表现可相差甚远（can differ substantially in execution）** |
| **gap 的稳定性** | **跨任务子集保持一致**（remain consistent across task subsets） |
| **操作画像的增量价值** | **添加操作画像显著改善任务分数预测**（substantially improve task-score prediction） |

## 关键结论

1. **「模型弱」和「部署弱」必须被分开测量，否则优化方向就是猜。** 基础画像**只能部分预测** agentic 操作 —— 这是一个否定性的、且很实用的结论：**直接用能力基准分数选 agent 模型是不够的**。
2. **相近的能力画像可以对应完全不同的 agent 表现。** 能力基准相近的模型**执行上相差很大** —— 意味着**能力基准排名不是 agent 部署的可靠代理指标**。
3. **gap 的跨子集一致性，使其成为可用的诊断量。** 如果 gap 随任务子集剧烈波动，它就只是噪声；**它保持一致**，说明它捕捉到的是**模型+部署组合的稳定属性**。
4. **操作层信息是能力层信息的补充而非重复。** 加入操作画像**显著改善任务分数预测** —— 意味着基础基准**遗漏了关于 agent 执行的真实信息**，这些信息只能从轨迹里捞。
5. **可操作性是本文最强的地方**：把失败**定位到具体操作**，等于给出了「改哪里」的清单 —— 这是端到端分数永远做不到的。

## 局限性

- **全部结论集中在一个基准（τ²-Bench）** —— 该基准的操作划分方式与任务特性直接决定了「操作」的粒度，**跨基准泛化未验证**。
- **「15 个模型服务」口径含糊**：可能是 15 个 API 服务、也可能是 15 个模型-版本组合；**是否含同一基座的不同 harness、是否含闭源模型、参数量分布如何，均未说明** —— 这直接影响「相近基础画像相差很大」的解读（可能是 harness 差异而非模型差异）。
- **gap 的计算方式未定义**：预测器是什么（回归？查表？）、如何避免**基础画像与操作画像之间的信息泄漏**（两者若共享数据源，gap 可能被构造性地压小）—— 这是方法上的关键未说明点。
- **「显著改善任务分数预测」无量化**：没有 R²、误差降幅、相关系数等任何数字；「substantially」是定性词。
- **「部分预测」的量化缺失**：**没有报告基础画像的预测精度**（如 R²、Spearman），因此无法判断差距的大小。
- **未验证 gap 与实际改进效果的相关性** —— 即「gap 大的模型-部署组合，经优化后收益真的更大」这一关键假设**未被实验检验**；框架的价值目前是描述性的。
- **操作划分的构建方式与成本未披露**（人工？LLM 标注？规则？）—— 这决定该框架是**可负担的评估流程**还是**只有大团队玩得起的活动**。
- **轨迹依赖性**：操作画像需要完整交互轨迹，**在生产中难以获得**（尤其多轮长任务），这限制了实用性。
- **代码与制品尚未发布**（摘要只说「will release」），**当前不可复现**。

## 实现建议

- **实现难度**：中-高（需要能力基准 + 轨迹采集 + 操作划分 + gap 建模）
- **预期性能**：定性结论 —— 基础画像**仅部分**预测 agentic 操作；相近画像的模型执行**可相差甚远**；操作画像**显著改善**任务分数预测；gap **跨子集一致**
- **适用场景**：**agent 选型**（不要只看能力基准排名）；**harness 优化**（把失败定位到操作，优先改高 gap 操作）；**模型发布后的归因分析**（是模型弱还是脚手架弱）
- **团队行动**：
  1. 选 agent 模型时，**同时记录能力基准分与轨迹级操作分**，别用前者单点决策；
  2. 建立自己的**操作分解清单**（把 agent 行为拆成 ~10–20 个操作），比追求 benchmark 分数更能指导迭代；
  3. 追踪 **gap 跨子集的稳定性**作为这个诊断量是否可信的判据 —— 若你的 gap 随任务剧烈波动，说明操作划分太粗，别据此改架构
  4. 待其**代码与制品发布后**优先复现，重点检查**基础画像与操作画像之间的信息泄漏**
