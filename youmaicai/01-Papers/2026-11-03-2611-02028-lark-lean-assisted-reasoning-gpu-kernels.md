## 核心贡献
1. **形式化验证 GPU kernel 与 PyTorch 参考实现等价**：在精确算术下证明**功能等价 + 内存行为等价**，而非仅靠测试
2. **两步分解证明策略**：先由 agent 把整个 kernel 语义**分解为更小的片段**并由 Lean 4 验证该分解（解决大 kernel 直接证明的不可解性），再由 agent 证明每个片段匹配其高层 PyTorch 对应物 —— 二者合起来给出整程序等价
3. **确立新的信任边界**：人类只需在**生成前**验证一次算子级 Lean 语义，**不必逐行检查**生成的代码

## 问题背景
高效 GPU kernel 通常是底层且硬件相关的。LLM agent 生成 kernel 的速度已超过专家验证的速度。现有方法依赖**测试**：
- 测试提供的是**证据**，不是**正确性保证**
- 测试覆盖不到的路径就成为盲区
- 人工逐行验证不可扩展

## 方法

### 信任边界重构
| 传统做法 | LARK 做法 |
|---------|-----------|
| 生成后逐行人工检查 | 生成前验证一次算子级 Lean 语义 |
| 测试作为证据 | 形式化证明作为保证 |
| 每次生成都要人看 | 人只投入一次（per target language） |

### 形式化基础
- **每种目标语言只做一次**：形式化 GPU 机器模型与每个操作的语义（Lean 4）
- 之后任何传入 kernel 的 Lean 4 语义**由这些预构建定义自动派生**

### 两步证明流程
```text
步骤 1：语义分解 + 验证
  agent 将整个 kernel 语义分解为更小片段
  → Lean 4 验证该分解本身成立
  → 解决「大型 kernel 直接证明等价」不可行的问题

步骤 2：逐片段对应证明
  agent 为每个 kernel 片段编写 Lean 证明
  → 证明该片段匹配其高层 PyTorch 对应物

合成：步骤 1 的分解 + 步骤 2 的对应 ⇒ 整程序等价
```

### 两种等价性
- **功能等价（functional）** —— 计算结果一致
- **内存行为等价（memory behavior）** —— 内存访问/越界语义一致

两者都在**精确算术**下成立。

## 实验结果
摘要中给出的结论：
- LARK 能够对 LLM 生成的 GPU kernel **形式化验证**其与 PyTorch 参考实现的等价性
- 证明自动化由 agent 承担（分解 + 写证明）
- 人类投入从「逐行检查每个 kernel」降为「生成前验证算子级 Lean 语义」

（摘要未给出具体的证明通过率、耗时或被测 kernel 数量。）

## 关键洞察
1. **"测试 vs 证明"是安全等级的分水岭，不是精度的分水岭** —— LARK 的贡献不在于让 kernel 更准，而在于把置信度从"大概率对"提升到"被机器检验过"。这对把 LLM 生成代码接入生产系统是决定性的。
2. **分解验证是形式化方法里的通用杠杆** —— "直接证明大对象不可行 → 先证明分解本身成立 → 再逐块证明"这一策略，与深度学习里的分层验证、模块化证明同构。它的价值不限于 GPU kernel。
3. **信任边界的位置比信任边界的强度更重要** —— 把人类的投入从"每次生成的每一行"移到"每种语言的算子语义一次"，这才是可扩展性的来源。
4. **"LLM 生成速度 > 人类验证速度"是当前 agent 工程的核心矛盾** —— LARK 给出了这个矛盾的一种结构性解法，而不是靠更强的模型硬扛。

## 局限性
- 依赖 **Lean 4 形式化库的规模与正确性** —— 预构建的算子语义库是瓶颈，其覆盖度摘要未说明
- **精确算术**假设排除了浮点误差，GPU kernel 的实际数值行为需另行处理
- LLM agent 生成的 Lean 证明本身是否被验证，是信任链的末端
- 摘要未给出实验规模与失败案例统计

## 适用场景
- LLM 生成 GPU kernel / CUDA / Triton 代码的 CI 流水线
- 需要"可审计正确性保证"的代码生成系统
- 研究"形式化方法 + LLM agent"的自动化证明分工模式
