# What the Middleman Delivers: Answer Behavior, Tool Permissions, and Billed Usage in LLM API Relays

> **arXiv**: [2611.07650](https://arxiv.org/abs/2611.07650)
> **发表日期**: 2026-11-05
> **分类**: cs.SE (及交叉分类 cs.AI)
> **会议/期刊**: arXiv preprint

## 📋 摘要

第三方 API 中继（relay）以更低价提供 LLM 访问，用户依赖这些服务获得模型质量、指令遵循与准确计费，然而既有研究未能说清这些中继是否能同时满足这些期望。本文测试了 **20 个**提供 **GPT-6 Astra** 与 **Claude Opus 5** 的中继服务。首先，作者将中继对知识问题的回答与批量匹配的官方响应做比较：在第一轮样本中，分析标记出 **10 个低价中继中的 7 个**、以及 **10 个同价或更高价中继中的 2 个**存在行为差异；在对 35 对中继的复测中，按原始规则有 **7 个**获得或失去标记，按匹配的纠错族（correction families）有 **6 个**。由于答案比较无法揭示所有交付问题，作者进一步检查返回内容与工具权限：在对固定的、非对抗性的代码与配置工作负载筛查的 **3,332 条响应**中**未确认任何注入**，但第一轮中有 **4 个中继**在已被指令禁用的情况下仍返回 tool call。最后，为把上报用量与真实成本对应起来，作者将输入 token 数与官方参考对比并核查余额：对相同请求，**5 个中继**比官方 API 多上报 **4,200 到 60,000** 个输入 token；在可查余额的 **6 个服务**中，收费按上报用量与标价计费，其中 **1 个服务**额外计入了那些多报出的输入 token。研究表明：**广告中的模型与价格不足以判断中继的可靠性**；无法解释的计费 token 数量与工具权限违规构成实质风险，服务评测需要**重复测量**。

## 🎯 核心贡献

1. **系统评估 20 个 LLM API 中继**：同时考察答案行为、工具权限与计费用量三个维度，覆盖 GPT-6 Astra 与 Claude Opus 5 两类模型。
2. **发现行为差异且与价格无关**：低价中继 7/10、同价或更高价中继 2/10 被标记存在行为差异——价格并非可靠性的代理指标。
3. **量化评测的不稳定性**：35 对中继复测时，原始规则下 7 个、匹配纠错族下 6 个获得或失去标记，论证了**单次测量不足以评估中继**。
4. **揭示工具权限违规**：在 3,332 条筛查响应中未确认注入，但 **4 个中继在明确禁用 tool call 的指令下仍返回 tool calls**。
5. **量化计费异常**：**5 个中继**在相同请求上比官方多上报 **4,200–60,000** 输入 token；可查余额的 6 个服务按上报用量计费，其中 1 个服务把多出的 token 计入收费。

## 🔧 方法/架构

**评测设计（四段式审计流程）**

1. **答案行为对比**：向中继与官方 API 发送同一批知识类问题，做 batch-matched 比较（同一批次、同一模型名、同一请求参数），用判定规则标记行为差异。
2. **复测与稳定性分析**：挑选 35 对中继重复测量，分别用"原始规则"和"匹配的纠错族"两套判定规则统计标记的翻转情况，量化评测噪声。
3. **内容与工具权限检查**：在固定的、非对抗性的代码与配置工作负载上筛查返回内容，共 3,332 条响应，用于检测注入迹象与"指令禁用 tool call 但仍返回 tool call"的权限违规。
4. **用量与计费核对**：将中继上报的 input token 数与官方参考值比对，并查询账户余额以核对实际扣费金额与标价的一致性。

**判定与公平性控制**
- *batch-matched*：中继与官方在同一批次、同一 prompt 集上评估，避免时间差与负载差带来的混淆。
- *correction families*：对已知会被模型纠正的答案族做匹配，区分"中继改答案"与"模型本身会纠正"。

## 📊 实验结果

- **样本规模**：20 个中继（提供 GPT-6 Astra 与 Claude Opus 5）；复测 35 对；筛查 3,332 条响应。
- **行为差异标记（第一轮）**：低价中继 **7/10**；同价或更高价中继 **2/10**。
- **复测稳定性**：原始规则下 **7 个**翻转；匹配纠错族下 **6 个**翻转。
- **工具权限**：**4 个中继**在指令禁用 tool call 时仍返回 tool calls。
- **注入检测**：3,332 条响应中**未确认注入**（该实验负载为非对抗性设计）。
- **计费异常**：**5 个中继**多上报 **4,200–60,000** 输入 token；可查余额的 **6 个服务**按上报用量计费，其中 **1 个服务**多计。

## ⚠️ 局限性

- 结论基于 **20 个中继**在特定时间点的快照，中继服务流动性高，结果随时可能变化。
- 工具权限与注入筛查使用的是**固定的、非对抗性**工作负载，因此"未确认注入"不能推广为"不存在注入"；对针对性对抗负载的行为未知。
- 行为差异的判定依赖启发式规则，存在误报/漏报（复测中 7/6 个标记翻转即为此证据）。
- 未与真实官方模型做端到端质量盲测，也未公开全部中继名单，外部可复现性受限。
- 商业服务评测通常受限于各中继的速率限制、可用模型差异与条款约束。

## 💡 建议

- 是否推荐使用：是（作为**采购与合规评估方法**推荐）
- 适用场景：企业采购第三方 LLM API 中继时的尽职调查；对计费敏感、需要工具调用权限受控的生产链路；在做第三方服务评测方法学设计时参考其"复测 + 纠错族匹配"设计。
