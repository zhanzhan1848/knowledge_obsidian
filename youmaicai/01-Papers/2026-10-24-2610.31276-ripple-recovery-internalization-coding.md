## 核心贡献

> 提出 RIPPLE —— 一个面向"恢复能力内化"的训练框架，把过程级恢复指导蒸馏进**单个自恢复策略**，并用 effect-aware credit 在反思触发、问题诊断、纠正动作三个阶段上分配 stage-specific 信用。

1. **识别 Critique-to-Action Handoff Gap**：长程编码 agent 常常能观察到失败并生成看似合理的批评，却仍沿着同一条错误轨迹继续 —— 诊断与动作之间存在断点
2. **Prefix-only teacher**：只提供证据锚定的恢复监督，**不访问未来动作与终局结果**，避免 teacher 泄漏答案或需要完整轨迹
3. **轻量蒸馏 + 分阶段 RL**：先用蒸馏把过程级指导内化，再由 RL 对"何时反思 / 如何诊断 / 如何纠正"分别分配信用
4. **Local validity gating**：用局部有效性信号 gate 轨迹 advantage，避免中间恢复决策无差别地继承终局结果
5. **部署期无辅助 critic**：最终得到的是单一策略，推理时不需要外挂价值模型

## 技术方案

### 核心思想

不要训练一个"会写批评"的模型，而要训练一个**能把批评转成正确动作**的策略。RIPPLE 把恢复能力拆成三段可归因的子目标（反思触发 → 诊断 → 纠正动作），在 RL 中按阶段给信用，并用局部有效性信号截断 terminal outcome 的错误传播。

### 关键组件

| 组件 | 说明 |
|------|------|
| Prefix-only Teacher | 仅基于已有前缀（失败现场 + 证据）产出恢复监督，看不到未来动作与终局 |
| Lightweight Distillation | 先把 teacher 的过程级指导压进基座模型 |
| Stage-specific Credit | 对 reflection triggering / diagnosis / corrective action 分别赋予信用 |
| Local Validity Gating | 局部有效性信号过滤轨迹 advantage，阻止中间决策继承终局奖励 |
| Self-recovering Policy | 单策略端到端部署，无辅助 critic |

### 关键公式

阶段级 advantage 由局部有效性门控后的终局奖励反传：

```math
A_{\text{stage}} = g_{\text{local}}(s_t) \cdot \big(R_{\text{terminal}} - V(s_t)\big)
```

其中 $g_{\text{local}}(s_t) \in [0,1]$ 为局部有效性信号：当前阶段的恢复决策被判定为"局部有效"时，终局收益才被允许回传。

三阶段信用分配可写为：

```math
\mathcal{L}_{\text{credit}} = \sum_{k \in \{\text{reflect}, \text{diagnose}, \text{correct}\}} w_k \cdot \mathcal{L}_{\text{policy}}^{(k)}
```

## 实验结论

| 指标 | RIPPLE 结果 |
|------|------------|
| 基准覆盖 | 四个 repository-level 软件工程基准 |
| 相对基座策略提升 | 算术平均 **+4.8 分** |
| 部署开销 | **无辅助 critic**（single policy） |
| 消融结论 | 受控消融证明收益来自**局部的、阶段对齐的信用分配** |
| Matched-prefix 干预 | 显示批评的**语义内容**确实影响后续纠正动作 |
| 收益分布 | 集中在 prefix 含**充分诊断证据**、且仓库状态在剩余预算内**仍可逆**的情形 |

---

## 局限性

- 恢复收益依赖 prefix 中是否有足够诊断证据 —— 证据不足或状态已不可逆时收益明显衰减
- prefix-only teacher 无未来信息，teacher 本身的上限受限于前缀可见证据，恢复质量存在天花板
- 只在四个 repository-level 编码基准上验证，跨领域（如通用工具使用、运维类 agent）泛化性未评估
- local validity signal 的定义与获取方式未在摘要中说明，可能需要额外标注或启发式规则
- 平均 +4.8 分的提升在长程任务中属于中等幅度，对高基线模型的增益可能不显著

## 实现建议

- **实现难度**: 高（需要自建 teacher 数据 + 阶段切分 + 局部有效性门控的 RL 管线）
- **适用场景**: 长程编码 agent（SWE 类仓库级任务）、会失败但不会从失败中改道的 agent 系统
- **建议起点**: 先做纯蒸馏版本（prefix-only teacher + SFT）测量"内化后能否自我纠正"，再叠加 RL 分阶段信用，观察增益是否真的来自 credit 分配而非额外数据
- **价值点**: 部署端零额外 critic 开销，能力内化进单一策略，工程上比外挂 critic 干净
