## 核心贡献

> 多 agent LLM pipeline 在软件工程任务上的增益，究竟来自 **agent 之间的类型化契约（typed contract）**，还是来自 **分解所解锁的专门化 prompt**？本文在 Requirements Engineering 上做归因研究，结论是：**F1 增益主要来自 two-call + specialized prompt 的分解本身**，typed state 带来的额外差异很小（-0.003 ~ +0.013，仅 6 组比较中的 1 组显著）。

1. **提出并执行一个清晰的归因消融**：设计三种架构 —— (a) **single-call baseline**；(b) **two-call 变体**：复用 pipeline 的 specialized prompt，但传递**未经校验的中间结果**；(c) **完整 pipeline**：带 **Pydantic 校验的 typed state**。
2. **定量结论：增益归属于分解，而非类型化契约**。相对 baseline 的 F1 增益与 **two-call、specialized-prompt 变体**相关联，最高 **+0.075**；而 **typed state 只贡献 -0.003 到 +0.013** 的小幅差异，在**六组比较中仅一组显著**。
3. **超越准确率的失效模式刻画**：typed pipeline 中存在**越界的模型输出（out-of-range model outputs）出现在 agent 边界**；而无校验变体则**在更晚处失败并直接丢掉该需求**。
4. **发现一个未解释的可复现现象**：无校验变体出现了**小幅但可复现的 inter-model MoSCoW 一致性上升**，而**其成因本文的设计无法隔离**（作者明确承认）。
5. **作者自我限定**：研究是**关联性（associative）而非因果性**的 —— 对比条件**捆绑了 prompts、调用次数与分阶段上下文**；结果来自**三个 7–8B 模型**与**单一数据集**。

## 技术方案

### 核心思想

多 agent LLM pipeline 被广泛认为能提升软件工程任务表现，但**归因不清**。本文提出一个关键区分：

- **Decomposition（分解）**：把任务拆成多次调用 + 每步专门化的 prompt。
- **Typed-state QA（类型化状态质量保证）**：agent 之间传递**经 schema 校验的结构化状态**（Pydantic）。

如果 pipeline 的收益主要来自前者，那么**类型化契约的额外投入是不划算的** —— 这对正在设计 agent 编排的工程团队是一个直接的**成本-收益判断依据**。

**三架构设计（消融矩阵）**：

| 架构 | 分解 | 专门化 prompt | 状态校验 |
|------|------|------|------|
| single-call baseline | ✗ | ✗ | ✗（无中间态） |
| two-call variant | ✓ | ✓ | ✗（未校验中间结果直传） |
| typed-state pipeline | ✓ | ✓ | ✓（Pydantic 校验） |

**任务设置**：把 requirements 分类为 **functional / non-functional**，随后用 **MoSCoW** 方法排序优先级。

**实验规模**：**18 个条件** = 3 种架构 × 3 个本地托管的小模型 × 2 种语言；数据集为 **PROMISE NFR+**，**625 条需求**。

### 关键技术

| 技术 | 说明 |
|------|------|
| **Typed agent contract** | agent 边界上以 Pydantic schema 约束结构化状态 |
| **Specialized prompts** | 每个角色（分类 / 排序）使用各自的专门化 prompt |
| **Two-call vs single-call 对照** | 分离「分解 + prompt 专门化」这一组合效应 |
| **Pydantic validation** | 运行时校验中间状态，捕获越界输出 |
| **MoSCoW prioritization** | Must-have / Should-have / Could-have / Won't-have 排序 |
| **PROMISE NFR+** | 625 条真实需求；含功能/非功能分类与优先级标注 |
| **18-condition factorial** | 3 架构 × 3 模型（7–8B，本地托管）× 2 语言 |
| **Boundary vs downstream failure analysis** | 区分「在 agent 边界被拦截」与「在下游静默失败并丢弃需求」 |
| **Inter-model consistency** | 跨模型的 MoSCoW 排序一致性度量 |

## 关键结论

1. **分解 + 专门化 prompt 才是多 agent pipeline 收益的主要来源。** 相对 baseline 的 F1 增益最高 +0.075 与 two-call 变体关联；**类型化契约只带来 -0.003 ~ +0.013 的边际差异，六组比较里只有一组显著**。这意味着：想让 pipeline 变好，**先把 prompt 分工做好**，不必先上复杂的类型化契约。
2. **类型化状态的价值在「失效模式」而非「准确率」。** typed pipeline 在边界上暴露越界输出（可观测、可拦截）；unvalidated 变体则**在下游静默丢掉整条需求** —— 对需求工程这种「漏一条就等于漏一个功能点」的场景，**静默丢失比报错更危险**。这是一个**准确率指标看不见**的价值。
3. **一个诚实的未解现象**：unvalidated 变体跨模型的 MoSCoW 一致性**小幅但可复现地更高**。作者**没有把它解释掉**，这可能提示「跳过 schema 校验」在多样性上带来某种正则化效果，值得后续单独研究。
4. **方法论警示**：这类归因研究容易掉进「把多个变化打包在一起」的陷阱 —— 本文对比条件**同时捆绑了 prompts、调用次数和分阶段上下文**，因此只能给出**关联性**结论。

## 局限性

- **作者自陈为 associational study**：对比条件**捆绑了 prompts、调用数与 staged context**，**无法严格因果分离**「分解」「专门化 prompt」「分阶段上下文」三者的贡献。
- **规模小**：仅 **3 个 7–8B 模型**、**单一数据集（PROMISE NFR+, 625 条）**、**2 种语言** —— 结论在 frontier 模型、更复杂需求域、多数据集上是否成立未知。
- **任务单一**：仅覆盖「功能/非功能分类 + MoSCoW 排序」，与真实多阶段软件工程 pipeline 的复杂度差距大。
- **交互项未完全展开**：即使 typed state 的平均增量很小，**它是否在与特定模型/语言的交互中更有价值**未被系统检验（只有一组显著差异的说明）。
- **inter-model consistency 上升的成因未隔离** —— 作者明确承认设计限制。
- **未涉及成本**：类型化 schema 会带来额外的开发与 token 开销，但摘要**未给出成本数据**，因此「收益小 → 不划算」的推论缺一半证据。
- 仅有 **Zenodo 复现包**，无 GitHub 代码仓库。

- **实现难度**：中（三个 pipeline 变体 + Pydantic 边界 + 复现包已有）
- **预期性能**：分解 + 专门化 prompt 最高 **+0.075 F1**；typed state 增量 **-0.003 ~ +0.013**（1/6 显著）；但 typed pipeline 换来**边界级越界拦截**、避免**静默丢需求**
