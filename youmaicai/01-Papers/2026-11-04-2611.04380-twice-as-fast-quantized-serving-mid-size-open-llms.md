## 核心贡献
1. **对公开证据做了一次"证据可得性"审计**，覆盖 9B–20B 段（Qwen2.5-14B、Qwen3-14B、Gemma 3 12B、Phi-4、Mistral NeMo、Ministral 3 14B、gpt-oss-20b）× 量化配方（FP8、INT8、AWQ、GPTQ、INT4、NVFP4、MXFP4）× 引擎（vLLM、SGLang）。结论：**公开记录只以碎片形式提供所需两个数字**（相对 BF16 的加速比、付出的精度代价）。
2. **明确指出证据空洞**：**只有两个 checkpoint 同时拥有 vLLM timing 和 accuracy 分数**，且都是 Gemma 3 12B 的 INT4 版本，而那个 accuracy 只覆盖**单一 MMLU 学科**——恰好是 AWQ 构建所校准的学科。batch-1 的 timing 早于当前引擎版本；**AMD 与 Intel Gaudi 在该参数段完全没有 timing**；**FP4 相对 BF16 没有任何测量**。
3. **用一条 memory-vs-compute（roofline）规则解释了全部存在的 timing**：batch-1 解码受显存带宽限制，4-bit 权重大致带来 2 倍加速（Qwen2.5-14B on A100 为 **2.12×**）；但大 batch 使 GPU 变成 compute-bound 后收益消失（Gemma 3 12B 在 batch size 256 时仅 **1.02×**），此时 **FP8 才是仍能带来收益的配方**。长 prompt 同理是 compute-bound（A100 的 INT4 收益从 2.12× 降到 1.64×）。
4. **给出一个自制的"噪声尺子"**，因为没有源报告标准误：对分数 $p$、题数 $n$，单次运行的一个标准误为 $\sqrt{p(1-p)/n}$——HumanEval ($n=164$) 约 **3.9 点**，GSM8K ($n=1319$) 约 **0.8–1.3 点**，完整 MMLU ($n=14{,}042$) 约 **0.34–0.39 点**，MMLU 哲学子集 ($n=311$) 约 **2.3 点**。对照之下，**所有 HumanEval delta 都落在基准采样噪声内**。
5. **对每条"加速 X 倍"的声明给出置信度分级**（Table 3），区分"3 源 3 GPU 中等置信"与"1 模型 1 源低置信"与"无任何测量"。
6. **提出七项量化服务报告清单**（一个 checkpoint ID + revision 同时用于 timing 与 accuracy；引擎/版本/所有非默认 flag；GPU 型号与数量；输入输出长度、batch size 或请求率、吞吐是否计入 prompt token；同栈上的 BF16 基线；harness/版本/few-shot/chat template/reasoning mode 及 $n$ 与标准误；校准数据且确认与评测集不相交）。**本文检视的所有来源无一满足全部七项**：无一声明标准误，只有 Gemma 卡片同时计时与打分它评测的 checkpoint。

## 问题背景
9B–20B 开源权重模型在 BF16 下能装进一张数据中心 GPU，量化后能装进一张消费级 GPU，因此成为自托管服务的常见选择。用 vLLM 或 SGLang 部署的团队必须为自己的 GPU 选一个量化配方，并需要两个数字：**相对 BF16 的加速比**与**付出的精度代价**。

现有工作各覆盖一部分：综述覆盖量化但不到今天的 serving stack；Zhao et al. 只 benchmark 量化算法本身的质量；Kurtic et al. 同时测精度与 vLLM 速度但只做 Llama 3.1 家族（8B/70B/405B）；Shi & Ding 在 TensorRT-LLM 上测 11 种配方但只做 Llama-2 与 CodeLlama；InferenceX 持续 benchmark vLLM 与 SGLang（NVIDIA + AMD）但**不列该参数段的模型**。

本文的独特切入点是：不是自己跑 benchmark，而是**系统性地收集并核验公开记录**，然后回答"公开记录能否回答从业者的问题"。所有数字在 2026-10-05 对照其引用源逐一核对过。

## 方法

### 1. 纳入规则

- **timing 保留条件**：来源须指明引擎、GPU、checkpoint 与 workload；
- **accuracy 保留条件**：同一来源须报告来自同一 harness 的 BF16 分数；
- 搜索范围：vLLM、SGLang、AMD ROCm、Intel Gaudi 文档；Hugging Face 模型卡（模型开发者 + 量化发布者 Red Hat AI、PyTorch、Tencent AngelSlim）；benchmark 报告；arXiv；
- 配对方式：模型名 × 配方 × 引擎，上限 2026-10-05；AI 编码助手协助收集来源与抽取数字，之后每个数字都回查原文。

### 2. Roofline 规则（解释全部 timing 的单条规则）

**batch size 1（latency-bound）**：每生成一个 token 需读一遍全部权重，解码时间由搬运字节数决定，4-bit 权重的搬运量是 BF16 的四分之一。于是**每个 INT4 配方在 batch 1 都快 1.35–2.12×**——达不到 4× 是因为反量化、attention 与 KV-cache 读取并不随之缩小。

**batch size 256（throughput/compute-bound）**：一次权重读取服务 256 条序列，matmul 变成 compute-bound；而 W4A16 **仍在 16 bit 上计算**，所以 Gemma 3 12B 只得 **1.02×**。

**长 prompt**：同样 compute-bound。A100 的 INT4 收益从 2.12×（input length 1）降到 **1.64×**（input length 30,720）。在 H20 上（其指标计入 prompt token），FP8 反超 AWQ（**1.68× vs 1.42×**），因为 Hopper 的 FP8 tensor core 速率是 BF16 的两倍。

**规则预测**：FP8 在大 batch 仍保有加速而 INT4 失去加速——但**没有任何 in-band 来源测过 batch size > 1 的 FP8**。

### 3. 配方与引擎支持

- **W4A16**（仅权重 4-bit）：GPTQ（OPTQ）用一次性二阶重构选整数；AWQ 重标定大激活通道；Marlin kernel 执行反量化后的 matmul，在 vLLM 内报告端到端最高 2.8× 加速。
- **W8A8**（权重+激活 8-bit）：LLM.int8() 把离群特征路由到 16-bit 路径；SmoothQuant 把它们迁进权重；FP8 用 E4M3 格式，激活 scale 固定（static）或逐 token 计算（dynamic）。
- **MXFP4**：32 个数共享 2 的幂 scale 的块状 4-bit 浮点；**NVFP4**：NVIDIA 的 4-bit 浮点格式，Blackwell 原生执行。
- **引擎 × GPU 依赖**：vLLM 在 Ada/Hopper/AMD 上跑 FP8 W8A8，**Ampere 上不支持**（其 Marlin kernel 仍能以 weight-only 方式服务 GPTQ/AWQ/FP8 checkpoint）；SGLang 在 AMD Instinct MI300X 及以后支持 fp8/awq/mxfp4，Marlin kernel 仅 CUDA；AMD 文档记录 vLLM 的 FP8 与 Triton AWQ。

### 4. 噪声尺子

对分数 $p$、题数 $n$，单次运行的一个标准误：

$$SE(p) = \sqrt{\frac{p(1-p)}{n}}$$

delta 的误差还取决于两次运行之间有多少答案翻转（Dutta et al. 2024），**没有任何来源报告这一项**。

## 关键洞察
1. **"提速 2 倍"这个数字本身在 batch 大小面前是无效的**。本文最有用的产出不是任何单一数字，而是这条判读规则：看到"2× 加速"必须同时问 batch size 与 prompt 长度。同一个 GPTQ-INT4 checkpoint 在 A100 上从 2.12×（bs=1, input 1）掉到 1.64×（input 30,720），而 Gemma 3 12B 在 bs=256 时只有 1.02×。**延迟敏感与吞吐敏感是两个不同的问题，需要不同配方**。
2. **精度 delta 必须先过噪声筛**。用 $\sqrt{p(1-p)/n}$ 做尺子后，很多"量化掉点"的声明消失：所有 HumanEval delta（-3.05 到 +6.10）都在噪声内，因为 HumanEval 只有 164 题，1 标准误就 3.9 点。只有 GSM8K 的两个损失（-4.17 AWQ on Qwen3-14B、-4.02 GPTQ on Mistral NeMo）超过 3 个标准误，是表中最清晰的真实损失。
3. **INT4 在大 batch 是显存方案而不是加速方案**。它的真正价值是把 14B 模型从约 28 GB 压到约 10 GB；加速在 decode-bound 之外基本不成立。要在 throughput-bound 场景拿收益，roofline 指向 FP8。
4. **同一"配方思想"在不同 harness 上的符号都可能反转**。两个 Qwen3-14B 分组用同一 W4A16 想法得到 GSM8K -1.06 与 +3.94，BF16 基线差 20.77 点。这意味着"某个量化配方掉 4 个点"这类结论若不指明 harness 与基线，几乎无信息量。
5. **BF16 基线与被评 checkpoint 必须是同一个**。全表中 accuracy 分数没有一个来自 Table 1 的 timing 运行；Gemma 的 AWQ 行更严重——那个 checkpoint 是在它被评测的 MMLU 学科上校准的，构成污染。这使得该表最常被引用的两个"同时有 timing 和 accuracy"的 checkpoint 实际上最不可用。
6. **7 项报告清单是本文最可迁移的产出**。多数证据空洞并非"没人做实验"，而是"来源省略了细节"。清单里最容易漏也最致命的三项：标准误、同一 checkpoint 的 timing+accuracy 配对、校准数据与评测集不相交。
7. **Ampere 上的特殊约束**：vLLM 在 Ampere 不支持 FP8 W8A8，FP8 checkpoint 只能以 weight-only 跑——这意味着在 A100 这类卡上，FP8 无法兑现 roofline 预测的收益，能拿到的接近 GPTQ-Int8 的 1.52× 而非 INT4 的量级。

## 局限性
- **Table 1 的各行来自不同实验**，不是一次统一 benchmark；四组各有自己的 BF16 基线，速度只能在组内比较。
- **标准误假设题目独立且单次运行**；delta 的误差还取决于两次运行间翻转的答案数，而这没有任何来源报告。
- **精度与 timing 来自不同来源、不同 checkpoint**——本文明确承认，因此"speedup 与 accuracy 给出的代价"的配对在绝大多数行上是不可得的。
- **缺失面极大**：AMD 与 Intel Gaudi 在 9B–20B 段完全没有 timing；FP4（NVFP4/MXFP4）相对 BF16 没有任何加速测量； Ministral 3 14B 无量化精度表；Qwen2.5-14B-Instruct 无 INT4 精度表；gpt-oss-20b 无 BF16 timing；大 batch 的 FP8 未测。
- **Qwen FP8 timing 用的 checkpoint 按 128 分块量化，但激活缩放方式未声明**，因此无法与 Table 2 的 static/dynamic 精度行对应。
- **所有网络来源都是厂商或项目页面**，会变动；最后核对日期为 2026-10-05。
- **Gemma 的 AWQ 行同时存在小样本与污染**（MMLU 哲学子集 311 题，AWQ 在其 30 个样本上校准），作者明确标注。
- **gpt-oss-20b 的 2.93× 是引擎对比不是配方对比**（vLLM vs SGLang），且未调优，不能当作 BF16→MXFP4 的加速。
- **未涉及多 GPU 张量并行、投机解码、prefix caching 等会显著改变 serving 成本结构的因素**，因而结论只对单卡、单请求路径成立。

## 适用场景
- **选量化配方做技术决策**：延迟敏感（bs 小）→ W4A16；吞吐敏感（bs 大）→ FP8（需 Hopper/Ada/Ampere 之外确认引擎支持）；显存受限 → W4A16 主要收益在容量。
- **写自己的 benchmark 或评审他人量化论文**：用七项清单做检查表，尤其是"标准误"与"同一 checkpoint 计时+打分"。
- **解读厂商模型卡上的量化 delta**：先算 $\sqrt{p(1-p)/n}$，落在噪声内的 delta 直接忽略。
- **评估 AMPERE 等不支持 FP8 W8A8 的平台**：roofline 预测失效，FP8 checkpoint 只能 weight-only。
- **不适合**：需要跨引擎/跨硬件的绝对速度对比（本文数据不支持）；需要"速度–精度帕累托曲线"的场景（本文证据不足以画）；把"2× 加速"当作可外推的部署承诺。
