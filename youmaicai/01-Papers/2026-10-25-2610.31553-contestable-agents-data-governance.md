## 核心贡献

> 提出 **contestable governance（可争议治理）**范式：让专业 agent 为**有争议的元数据决策**产出**带打分、带引用的论证**，由**steward（治理人）**在提交前接受 / 拒绝 / 修改 / 补充论证，而**治理记录（governance record）**永久保留**证据、人工干预与最终结果**。

1. **问题定位 —— 组织知识的两类载体被分开治**：工业组织的运营知识存在于**结构化记录**（遥测、点位清单、交易）与**非结构化来源**（手册、服务记录、沟通、检查报告）中，而**治理项目常把这两类源分开管理** —— 分类、链接与文档化高度依赖**少数具备深厚领域知识的员工**
2. **AI 提案的风险**：LLM agent 能提出元数据、引用文档、标记质量问题，但**未经审阅的提案会把错误扩散到下游系统**
3. **核心批评 —— 走过场审批（perfunctory approval）不留痕**："形式化批准"**不记录审阅者到底检查了什么** —— 这正是合规审计最缺的证据
4. **核心方案 —— 可争议治理三要素**：
   - 专业 agent 为**争议决策**产出**带分数、带引用的论证**
   - steward 可**接受、拒绝、修改或补充论证**，然后才 commit
   - **治理记录保留证据、干预与结果**
5. **版本化领域术语表（versioned domain glossary）**：向 agent 提供模型特定的术语与缩写定义 —— 应对工业领域的术语歧义
6. **分诊路径（triage path）**：**只对不确定的提案走完整论证流程**，但**无论哪条路径，commit 前都保留人工审阅**
7. **先例门（precedent gate）**：控制**哪些已验证的决策可以成为先例（precedent）** —— 防止个别决策被静默放大为组织惯例
8. **两个 HVAC 用例**：**基于 Brick Schema 类标签的点位分类**（有开放参考实现）+ 一个**说明性的保修失效模式决策**（把 claim 字段与遥测关联到服务记录与版本化公告）

## 技术方案

### 核心思想

```
传统: agent 提案 → 一键批准 → commit
      ✗ 错误静默扩散；✗ 审阅过程无证据；✗ 决策来源不可追溯

可争议治理:
  agent 提案（带打分 + 带引用论证）
      ↓
  分诊（triage）：确定性高 → 简化路径；不确定 → 完整论证路径
      ↓
  steward 审阅：accept / reject / modify / add arguments
      ↓
  commit（所有路径都需人工审阅）
      ↓
  治理记录：证据 + 人工干预 + 结果  ← 可审计
      ↓
  先例门：控制哪些决策可升格为 precedent
```

### 关键技术

| 技术 | 说明 |
|------|------|
| **Scored, cited arguments** | agent 输出论证时**同时给分并引用文档**，使分歧可被讨论而非凭直觉裁决 |
| **Steward actions** | accept / reject / modify / add arguments —— 记录**人做了什么**，而不只是最终结果 |
| **Governance record** | 保留**证据 + 干预 + 结果**三元组，是"可争议"的落地载体 |
| **Versioned domain glossary** | 向 agent 提供**模型特定**的术语与缩写定义，随领域演进版本化 |
| **Triage path** | 把完整论证留给**不确定**提案；两条路径**都在 commit 前保留审阅** |
| **Scoring model** | 提案与论证的打分模型（论文描述了 scoring 与 record 模型） |
| **Precedent gate** | 只有通过门控的已验证决策才可成为先例 |
| **Structured + unstructured 统一** | 点位清单 / 交易 与 手册 / 服务记录 / 沟通 / 检查报告在同一治理框架下 |

### 两个 HVAC 用例

| 用例 | 内容 |
|------|------|
| **点位分类** | 使用 **Brick Schema 类标签**做点位分类，有**开放参考实现**支持 |
| **保修失效模式决策（说明性）** | 把 **claim 字段与遥测**关联到**服务记录与版本化公告（revisioned bulletins）** |

## 关键实验结果

### 论文性质说明

- 这是一篇 **15 页、2 图、2 表** 的**系统 / 工作流设计论文**（cs.DB / cs.HC / cs.MA 交叉），**不是实验论文**
- 摘要中**未给出定量实验结果**（无准确率、无吞吐、无对比基线数字）
- 可验证的产出是：**工作流描述 + 分诊路径 + 打分与记录模型 + 先例门 + 开放参考实现**

### 论文描述的定性收益（作者主张）

| 主张 | 内容 |
|------|------|
| 错误控制 | 未经审阅的提案不再直接扩散到下游（改为**先争议、再提交**） |
| 可审计性 | 治理记录提供**证据 + 干预 + 结果**的可审计链 |
| 规模化治理 | 分诊路径让**确定性提案走快道**，把人的注意力集中在争议点 |
| 知识依赖缓解 | agent 承担分类/链接/文档化的初步工作，**降低对少数专家的时间依赖** |

## 关键结论 / 局限性

### 关键结论

1. **治理的关键不是"要不要人"，而是"人做了什么"**：把审批变成走过场，等于没有治理 —— **记录干预行为**是本文最有价值的洞见
2. **AI 生成的元数据需要"可争议"而非"可信"**：与其要求模型输出正确（不可保证），不如让错误**能被指出、被争论、被记录**
3. **结构化与非结构化源应统一治理**：分开治是当前工业实践的明显缺口（分类/链接/文档化本质上跨源）
4. **先例机制必须受控**：一旦决策被静默升格为先例，错误会被制度化 —— precedent gate 是必要的刹车

### 局限性

- **无定量评估**：没有用户研究、没有错误率下降的量化、没有对人工审阅耗时的测量 —— 这是一篇**设计 + 案例论文**，其主张（更安全、更可审计）**未被实证**
- **用例窄且单一行业**：仅 **HVAC** 两个用例，且一个是**明确标注为"illustrative（说明性）"**的 —— 泛化性未验证
- **评分模型未公开**：摘要只说"描述了 scoring 与 record models"，**打分的质量与校准**未讨论 —— 而打分正是"可争议"能否运转的核心
- **分诊阈值未说明**：怎样判定"确定性高/不确定"？摘要未提；这直接决定 human workload
- **steward 自身的可靠性未被讨论**：如果 steward 本身不理解领域，治理记录只会变成"走过场"的留痕版
- **与多 agent 群体动力学的风险未衔接**：[[2026-10-25-2610.31105-who-is-the-influencer-consensus-dynamics]] 表明多模型混合时大模型单点主导 —— 本文的多 agent 治理设计是否受此影响，未讨论
- **无量化 benchmark**，也不适合作为算法选型依据
