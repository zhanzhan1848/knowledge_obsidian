## 核心贡献

> 提出 **CarryoverBench** —— 首次系统性评测**跨会话持续攻击（carryover attack）**：一次性间接 prompt injection 植入持久通道后，在攻击者离开后**跨会话反复触发**。既有 prompt-injection 基准只评估注入当次会话，完全没测「埋下的载荷日后多久、以何种方式重新触发」这道闸门。

1. **12 个个人助理场景 + 101 个攻击任务**
2. **三类触发通道**：
   - **Instant**：同轮 IPI（indirect prompt injection）
   - **Autonomous**：心跳调度触发（heartbeat-scheduled），无需用户输入
   - **Latent**：记忆再次浮现（memory-resurfaced）
3. **两阶段独立评分**：植入（planting）与触发（triggering）分开打分
4. **跨 5 个前沿模型**：植入的载荷在 5 轮内**重触发且无可测量衰减**；条件在成功植入时，触发阶段往往几乎不提供额外保护
5. **跨 runtime 验证**：移植到第二 runtime（Hermes）可衰减但**不消除** → 防御需 runtime 层控制，不能只靠 prompt 层

## 技术方案

### 三条持久化通道

现代 LLM agent 跨会话保持状态有两条通道，CarryoverBench 覆盖三个触发模式：

| 通道 | 机制 | 触发类型 |
|------|------|---------|
| 长寿命记忆文件 | 静默前置到 system prompt | **Latent**（记忆浮现） |
| 调度任务 | 无用户输入唤醒 agent | **Autonomous**（心跳调度） |
| 当轮对话 | 用户/检索内容中的恶意指令 | **Instant**（同轮 IPI） |

### 评估协议

规则式验证器把攻击拆为两个独立阶段：

```math
\text{ASR} = P(\text{plant} \mid \text{attempt}) \times P(\text{trigger} \mid \text{plant})
```

- **阶段 1 植入**：载荷是否成功写入持久状态
- **阶段 2 触发**：载荷日后是否真的被重新执行

这一拆分正是既有基准缺失的部分 —— 它们只看阶段 1。

---

## 实验结论

| 发现 | 数据 |
|------|------|
| 跨会话重触发衰减 | 5 轮内**无可测量衰减** |
| 触发阶段保护力度 | 条件在植入成功时，**几乎无额外保护** |
| 跨 runtime 移植（Hermes） | 衰减但**未消除** |
| 结论 | 防御必须包含 **runtime 层控制**，prompt 层干预不够 |

---

## 局限性

- 12 场景偏个人助理，其他 agent 域（编码、运维）未覆盖
- 5 个前沿模型 —— 未验证更小/开源模型是否有相同行为
- 规则式验证器可能漏判语义等价的触发
- 仅评测攻击，未系统比较防御方案

## 实现建议

- **实践含义**: 部署持久记忆 / 调度任务型 agent 时，**prompt 层防御不足**，必须在 runtime 层做指令来源标记与执行审计
- **建议起点**: 记忆条目与调度任务携带来源可信度标记，agent 在执行来自记忆/心跳的任务时降权或要求确认
- **评估建议**: 安全回归测试应包含跨会话、多轮次的触发验证，而非仅测注入当次
