## 核心贡献
1. **把「服务行为」训练进模型本体**：在工具增强（tool-augmented）LLM agent 中，回答的「行为规范」通常写在系统提示里；NEIGHBOR 将其**微调进驱动工具的模型**，从而使行为与工具使用一致对齐。
2. **真实线上部署**：部署于**东亚某人口逾千万城市的某个区的居民服务平台**（live resident-service platform）。
3. **LoRA 微调 Qwen3-235B-A22B**：使用 **7,824 条监督微调样本**，基于公开的社区服务材料，围绕**六个服务行为目标**构建，其中包括 **commitment control（承诺管控）** 与 **human referral（转人工）**。
4. **能力配置**：适配后的模型负责**规划文档检索**与**对居民本人记录执行只读 text-to-SQL**。
5. **专家盲评结果（强显著性）**：七种配置的离线评测中，独立领域专家对 **50 条分层留出查询的全部 350 份回答**评分，NEIGHBOR 得 **7.74/10**，同 agent 跑**未调模型为 5.86**（**+1.88**；配对 Wilcoxon **$p < 10^{-8}$**；**50 条查询中 46 条更高**），且**六个评分维度全部改进**。
6. **红线的显著降低**：**没有任何工具增强的回答被标记红线**（standalone models 则有 **8–14%** 的回答被标红线）。
7. **LLM judge 与专家高度一致（但存在系统性偏差）**：LLM judge 对七种配置的排序与专家**大体一致（Spearman $\rho = 0.93$）**；但其评分标准把「参考答案中不存在的具体信息」计为**捏造（fabricated）**，因此对有工具依据的回答**低打 1–2 分**，足以**改变哪个配置排第一**。

## 问题背景
居民就维修或物业费等问题联系社区服务台时，需要的是**能直接行动的回答**：事实必须**对其个案成立**，承诺必须是**服务台能兑现的**。在工具增强的 LLM agent 中，这些事实来自文档与记录；而**服务的行事规范（conduct）**通常被写在系统提示里，依赖提示遵守而非模型内化——这在长对话、多工具、长上下文场景下极易漂移。既有研究多关注「回答是否基于检索到的证据」（groundedness），较少把**服务行为本身**（承诺控制、转人工、边界守住）作为可训练目标。此外，社区服务场景有明确的**红线**（如作出无法兑现的承诺、越权披露他人信息），需要有可量化的行为合规指标。

## 方法
### 1. 系统定位
- **把 conduct 训练进模型**，而不是只写进系统提示（"trains this conduct into the model that drives its tools"）。
- 目标：使**服务行为**与**证据使用**同时对齐。

### 2. 基座与训练
| 项目 | 配置 |
|------|------|
| 基座模型 | **Qwen3-235B-A22B**（MoE） |
| 适配方式 | **LoRA** |
| SFT 样本量 | **7,824 条** |
| 数据来源 | 基于**公开的社区服务材料**（public community-service materials）构建 |
| 行为目标数 | **6 个服务行为目标（six service-behaviour targets）** |
| 代表性目标 | **commitment control（承诺管控）**、**human referral（转人工）** |

### 3. Agent 能力
- 适配后的模型负责：
  - **规划文档检索（plans document retrieval）**；
  - 对**居民本人的记录执行只读 text-to-SQL（read-only text-to-SQL over the resident's own records）**。
- 只读限制是关键的权限设计（scope constraint），避免 agent 修改记录。

### 4. 评测协议
- **离线评测，7 种配置**（7 configurations）——包含未调模型与多种对照/变体。
- **50 条分层（stratified）留出查询**（held-out queries）。
- 每个查询由全部 7 种配置回答 → **50 × 7 = 350 份回答**。
- **独立领域专家（independent domain expert）**对全部 350 份回答评分，**专家不参与系统构建**。
- **六个评分维度**（six rated dimensions），全部维度均有改进。
- 统计检验：**配对 Wilcoxon signed-rank test**。
- 另设**红线标记（red-line flag）**机制：识别不合规回答（如捏造、越权承诺等）。
- **LLM judge** 作为低成本对照，对同样 7 种配置排序。

## 实验结果
### 专家评分主结果

| 配置 | 专家评分 |
|------|----------|
| **NEIGHBOR（LoRA 微调后）** | **7.74 / 10** |
| 同一 agent + **未调模型** | **5.86 / 10** |
| 差值 | **+1.88** |

- 配对 Wilcoxon：$p < 10^{-8}$（极显著）。
- **50 条查询中 46 条**上 NEIGHBOR 得分更高（92%）。
- **6 个评分维度全部改进**（无回退维度）。

### 红线合规

| 场景 | 被标红线比例 |
|------|--------------|
| **NEIGHBOR（工具增强）** | **0%（没有任何工具增强回答被标红线）** |
| standalone models | **8–14%** |

- 对照强度很高：工具增强 + 行为训练把红线率从 8–14% 压到 0。

### LLM judge 与专家的一致性

| 指标 | 数值 |
|------|------|
| LLM judge vs 专家的七配置排序一致性 | **Spearman $\rho = 0.93$** |

- **重要偏差**：judge 的评分标准把**参考（ground-truth）答案中缺失的具体信息判为捏造（fabricated）**。
- 后果：judge 给**工具依据型回答低打 1–2 分**，这一偏差**足以改变哪个配置排名第一**。
- 含义：LLM judge 在**排序**上与专家高度一致（ρ=0.93），但在**绝对分数**上系统性惩罚「有据可查的额外具体信息」——这是评测器幻觉（judge hallucination）的典型案例。

### 部署
- 线上平台：东亚 >1000 万人口城市的某区居民服务平台的真实部署。

### 摘要未给出的定量信息
- 7 种配置的具体清单与各自得分；
- 6 个评分维度的名称与逐维度数值；
- LoRA 超参（rank、alpha、目标模块）、训练数据在各行为目标上的分布、训练/验证划分；
- 50 条分层查询的分层依据；
- 专家评分者人数与背景、盲评协议细节；
- 红线的具体判定定义与判定者；
- 线上部署后的效果（如工单解决率、居民满意度）——摘要未给出线上指标。

## 关键洞察
1. **「服务行为」是比「检索更准」更可训练、也更影响体验的目标**：+1.88 分、92% 查询改善、六维度全升、红线清零，且**工具保持不变**（tools held fixed）——说明增益来自行为本身被内化，而非工具能力变化。这与把行为写进系统提示的做法形成直接对比。
2. **专家评测与 LLM judge 的「排序一致但打分不一致」是重要方法论警告**：ρ=0.93 让人放心地用 judge 替代专家，但 judge 的绝对分数因「把参考答案外的具体信息判为捏造」而系统性偏低，**足以翻转排名**。这意味着：LLM judge 可用于**排序/筛选**，但不能用于**绝对分数比较与阈值判定**，尤其在工具增强场景中。
3. **工具增强本身是降低红线率的主要因素，模型调优是第二层保险**：standalone 模型 8–14% 红线 vs 工具增强 0%——说明「有据可查」本身就在抑制编造承诺。但两者结合才同时得到高质量与零红线。
4. **承诺管控与转人工是最有价值的行为目标**：这类「行为」无法通过更好的检索解决——只有把「我不能保证」与「这事该找谁」内化为模型默认行为，才能真正降低居民被误导的风险。
5. **社区服务是 LLM 行为的理想试验场**：有真实用户、明确红线、可验证的私域记录（只读 text-to-SQL），且错误代价直接落在居民身上——比通用助手基准更接近落地约束。

## 局限性
- 摘要未给出：7 种配置的构成、6 个维度的定义与数值、LoRA 与数据细节、专家人数与盲评细节、红线定义与判定方式。
- **单一城市、单一区、单一语言环境**（东亚某市某区）→ 地域与制度特异性明显；跨地区、跨制度（如欧盟、中国大陆不同城市）泛化未知。
- **专家仅一位**（"an independent domain expert"）→ 评分的方差与可复现性无法评估；虽配对 Wilcoxon 极显著，但评者效应未处理。
- **50 条查询、350 份回答**规模有限；分层策略未说明，离线评测与线上真实分布的差距未量化。
- **无上线 A/B 或前后对照的线上指标**（摘要只提到部署，未给线上收益），因此「+1.88 专家分」是否转化为居民体验改善仍属推断。
- 评测在离线环境进行，工具检索结果与线上库一致性与时效性未讨论。
- 承诺管控、转人工的**触发策略**与误报/漏报代价未做成本分析（例如过度转人工会削弱自动化收益）。
- 只读 text-to-SQL 的注入与越权防护细节未说明。

## 适用场景
- 面向居民/客户的政务与社区服务台 LLM agent 部署。
- 需要把「不可承诺什么、该转人工」内化为模型默认行为的落地系统。
- 工具增强 agent 的行为合规评测方法（专家评分 + 红线标记 + judge 对照）。
- 研究「系统提示规范 vs 微调内化」哪种更可靠地维持长程行为一致性。
