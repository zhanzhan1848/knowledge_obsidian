## 核心贡献
1. **量化了长上下文的真实成本**：token 生成延迟与显存占用随上下文长度增长。在开源前沿模型上，**在 256K 而非 16K 的上下文窗口服务，每生成 token 的成本高 3.6×（GLM 5.2）、5.6×（Kimi K2.6）、7×（Qwen 3 Coder Next）**。这个幅度**超过或等同于许多正交的优化方法**（激进量化、结构化稀疏化）。该成本差异对终端用户往往被隐藏，因为零售 token 价格按每 1M tokens 固定报价，不区分输入上下文长度。
2. **通过频繁 compaction 回答 RQ1（长程任务）**：跨 6 个长程基准，**频繁 compaction 保持上下文短的同时基本维持任务准确率**。SWE-bench Verified 上相对基线的准确率变化在 48K/32K/24K/16K 限制下分别为 +3.6 / +2.0 / +4.8 / **-1.2** 个百分点，对应成本节省 3.2× / 4.3× / 6.0× / 6.7×。
3. **通过选择性输入读取回答 RQ2（长输入任务）**：7 个长输入基准上，**选择性输入读取 + compaction 作为回退，在几乎所有情况下匹配或超过全输入基线**，同时保持 live context 远低于基线对话长度。**压缩次数的中位数接近零**，且**对话长度随文档大小增长近似恒定**——这支持了核心直觉：尽管任务提供了长输入，实际所需信息量很低。
4. **通过每动作单次上下文回答 RQ3（极端 compaction）**：SAC（Single-Action Compaction）下**每个上下文只做一个动作**，只保留紧凑语义状态。
   - **Claude Opus 4.5**：SWE-bench Verified **70.2**（基线 70.0）、Terminal-Bench 2.1 **51.8**（基线 47.2，**+4.6**）
   - **GPT 5.6 Sol**：SWE-bench Verified **82.4**（基线 84.4，-2.0）、Terminal-Bench **84.3**（基线 87.6，-3.3；89 题中解出 75 题）
   - **peak live context 中位数仅 7–9K token，最大值从 130–200K 降到 15–37K**
5. **提出 Semantic State Space Models（SSSMs）概念**：一个被后训练为 (1) 理解会话状态的输入语言描述、(2) 推理下一个适当动作或任务、(3) 执行动作、(4) 登记其结果、(5) **以推理结论、动作决策与动作结果更新会话状态的语言描述**，使得**另一个推理实例**能继续会话。与经典 SSM 相对照：**SSM 在 token 生成之间维护黑盒神经状态；SSSM 维护可解释的自然语言状态**。
6. **提出对长上下文范式的根本质疑**：论文自问"**为什么要训练全历史累积的模型？**"（"we see no reason why SSSMs could not match the performance of full-history-accumulating models, which begs the question: Why train full-history-accumulating models in the first place?"）

## 问题背景

**并非所有 token 都等价。** token 生成延迟与显存占用都随上下文中的 token 数增长，源于生成一个 token 的计算成本与其在上下文中的深度之间固有的**线性**关系。

在云 GPU 上以始终较短的上下文服务模型有显著的经济收益。这一事实常被终端用户忽视，因为零售 token 价格按每 1M tokens 固定报价 regardless of 输入上下文长度。**成本降幅 3.6×–7× 与激进量化或结构化稀疏化等许多其他正交优化方法相当甚至更大。**

问题在于：既然保持输入上下文短有可观的成本优势，人们会期望主流 LM 自然演化到只在必要时使用短上下文。**事实恰恰相反**（Table 1）：模型上下文窗口尺寸已远超许多有影响力的著作——《老人与海》约 37K token，而 MiniMax M2.7 的上下文窗口是 200K；《战争与和平》约 753K token，而 GLM 5.2 是 1M；GPT 5.6 Sol 达 1.05M。**模型似乎在演化以容纳越来越大的可能输入，而非最大化效率。**

论文把长上下文的来源分解为两类工作负载：

- **LCW1（长程任务）**：需要许多动作才能完成，且随模型推进上下文不断累积。
- **LCW2（长输入任务）**：需要操作大量输入信息。

关键观察：**LCW1 的整个对话历史并不需要在长程操作的每一步都被考虑**；同样 **LCW2 的长输入并不需要总是一次性摄入**。而且 **LCW2 总可以被归约为 LCW1**——把长输入存为资源并给 LM 一个选择性读取的工具。

由此提出三个研究问题：**RQ1** 长程任务能在无长上下文下完成吗？**RQ2** 长输入任务能在无长上下文下完成吗？**RQ3** 长程任务能在每个上下文至多一个动作下完成吗？

论文还有一个精彩的收尾论证：**可计算性的定义本身就建立在"任何可计算之物都可通过每次只理解有界的输入量并只维护有限心智状态来计算"这一假设之上**。

## 方法

### 1. 术语定义（关键，因为"context"被严重重载）

- **Inference step**：一次 LLM 调用产生输出。在 agentic 工作流中通常对应一个 agent turn。
- **Input context**：某次推理步提供给 LLM 的完整 token 序列（可能含系统指令、任务输入、此前模型输出、工具结果等）。
- **Output context**：某次推理步中 LLM 生成的完整 token 序列。
- **Context**：input context、input + 关联的 output context、或 input + 为可能 output 预留的 token 空间。
- **Context window / context window size**：LM 在任一时刻能理解的 token 空间；**context window size 是某 LM endpoint 一次调用能处理的最大 token 数**（由模型上下文窗口或服务配置收窄）。
- **Long context**：长度接近多数当代前沿模型上下文窗口尺寸的显著比例（研究时点约 **256K token 或更多**）。**Short context**：长度更接近零而非上下文窗口尺寸（本文强调的运行区间通常限于 **16K–50K token**）。论文特别注明"short"是**相对于常见上下文窗口尺寸**而言，绝对语言意义上并不小。
- **Long-input task**：伴随一个长输入的任务（若直接摄入则构成长上下文）。**"long input" 指的是可用任务输入的规模**，无论 harness 是一次性放入还是通过选择性读取暴露。
- **Long-horizon task**：完成需要许多顺序模型动作，后续动作依赖前面的观察、产物或决策的任务。

### 2. 三种上下文管理范式

**FHA（Full-History Accumulation）**：基线。追加每一条模型消息、工具调用、工具响应、中间决策到不断增长的历史中。

**EoCC（End-of-Conversation Compaction）**：遵循完整的 ReAct 循环直到达到 compaction 阈值，然后注入一个 **compaction nudge**，让模型把对话压缩成一段 **semantic state**（自然语言摘要），然后**开启一个新对话**（携带压缩后的状态）。

**SAC（Single-Action Compaction）**：维护一个紧凑语义状态、几乎无对话历史。每个对话接收任务与当前语义状态，**执行恰好一个环境动作**，观察结果，更新语义状态；harness 随后丢弃该对话并为下一动作开启全新对话。

**成本核算**：FHA 的上下文长度是该次执行的对话长度；EoCC 与 SAC 的总长度是最终对话与各压缩对话长度之和。

### 3. 基准与模型

**长程任务基准**：SWE-bench Verified（500 个真实 GitHub issue 修复任务）、SWE-bench Multilingual（300 个任务，跨 9 种语言）、Terminal-Bench 2.1（89 个沙箱容器中的真实命令行任务）、FRAMES（824 个多跳问题，需组合 2–15 篇 Wikipedia 文章）、τ²-bench（184 任务的 golden set，跨零售/航空/电信，与模拟用户对话并操作领域工具）、BFCLv3（200 个长上下文多轮工具使用 episode）。

**长输入任务基准**：LongBench v2（503 道选择题，输入 8K–约 2M 词）、LOONG（1,600 题多文档金融/法律/学术）、AA-LCR（100 个人工构造问题，平均约 100K 输入 token）、Needle in a Haystack（125 实例网格，16K–约 500K）、RULER（13 个合成任务，在 256K 与 500K 评测）、Counting-Stars（192 题，4K–128K，含需区分最终值与干扰项的推理变体）、BABILong（550 题，10 种任务类型，64K–1M）。

**模型**：
- **闭源大模型（主实验的 worker）**：**Claude Opus 4.5** 与 **GPT 5.6 Sol**。选它们是因为它们是编码、工具使用等长程工作流中使用的强通用模型代表；**使用独立开发的模型家族也降低了观察到的 compaction 效应是某一供应商特定效应或后训练配方特定效应的风险**。
- **开源大模型**：GLM 5.2（至 1M 上下文）、Kimi K2.6（至 256K）、Qwen 3 Coder Next（至 256K）用于云吞吐研究；Qwen 3.6 27B、Qwen 3 Coder Next（80B 总/3B 激活 MoE）、Gemma 4 31B、Step 3.7 Flash（198B A11B）、MiniMax M2.7（230B 总/10B 激活 MoE）部署在 **NVIDIA DGX Spark**（128GB 统一内存，约 109GB 可用于本地服务）上做端侧测量。

**架构多样性**（论文强调）：混合 linear/softmax attention、交错的滑动窗口/全局注意力栈、门控 GQA、传统全 GQA softmax attention——用于检验"短上下文足够"的结论在不同注意力机制与后训练特性上的普适性。

### 4. Harness

两个紧密相关的基座 harness，都实现极简 **ReAct 循环**：任务在初始 user message 中给出，模型一次发出一个 **Bash 动作**，每个动作及其结果被追加到对话。软件工程与终端任务用 **mini-swe-agent**（只需环境集成），其余用 **mini-agent**（mini-swe-agent 的一般化）。

## 实验结果

- **Dataset/Task**: 13 个基准（6 个长程 + 7 个长输入）；2 个闭源主模型 + 5 个端侧开源模型；3 种上下文管理范式（FHA / EoCC / SAC）。

- **Main results**:

  **长上下文成本（Figure 1，on-demand H100 价格 $3.85/GPU-hour，Nebius, 2026 年 9 月）**：

| 模型 | 256K vs 16K 每 token 成本倍数 | 精度配置 |
|------|-------------------------------|---------|
| GLM 5.2 | **3.6×** | INT4 权重 + BF16 激活 |
| Kimi K2.6 | **5.6×** | INT4 权重 + BF16 激活 |
| Qwen 3 Coder Next | **7×** | BF16 |

  **SAC vs FHA vs EoCC（Table 2）**：

| 基准 | mini 基线 | 最佳 EoCC | SAC | peak 上下文（K，中位/最大） mini → EoCC → SAC |
|------|----------|----------|-----|------|
| **Claude Opus 4.5** | | | | |
| SWE-bench Verified | 70.0 | 74.8 (24K/18K) | **70.2** | 32/200 → 19/22 → **8/16** |
| Terminal-Bench (2.1) | 47.2 | 52.8 (32K/24K) | **51.8** | 27/130 → 24/31 → **9/19** |
| **GPT 5.6 Sol** | | | | |
| SWE-bench Verified | 84.4 | 88.8 (48K/36K) | **82.4** | 18/173 → 22/35 → **7/15** |
| Terminal-Bench (2.1) | 87.6 | 88.8 (48K/36K) | **84.3** | 17/133 → 23/40 → **8/37** |

  **长输入任务（Figure 6，Δ准确率 vs 成本节省）**：LongBench v2 在 16K 下 **-0.4** pp、1× 成本节省下 **+1.8** pp、2× 下 **0.0** pp；LOONG 平均分在 48K 下 **+9.7** pp、32K 下 **+10.1** pp、16K 下 **+9.2** pp（成本节省 7.4× / 10.2× / 13.6×）；AA-LCR 在 48K/32K/16K 下分别 **+15.0 / +19.0 / +1.0** pp。

  **长程任务 EoCC（Figure 5，Δ准确率 pp）**：SWE-bench Verified 在 48K/32K/24K/16K 分别为 **+3.6 / +2.0 / +4.8 / -1.2** pp，对应成本节省 **3.2× / 4.3× / 6.0× / 6.7×**。

- **Ablations**: (1) **逐级降低总上下文限制 + compaction 阈值**（SWE-bench 等用 48K/36K、32K/24K、24K/18K、16K/12K；BFCLv3 用 24K/18K、16K/12K、12K/8K；τ²-bench 用 16K/12K、12K/8K、8K/6K）——直接给出准确率–成本曲线；(2) **全输入基线 vs 选择性读取**（长输入任务中基线接收全部输入，compacting harness 用 Bash 工具从环境文件系统选择性读取）；(3) **三种 compaction 频率**（FHA / EoCC / SAC）；(4) **两个不同家族的闭源模型**互为对照，降低供应商特异性风险；(5) **五个架构多样的开源模型**做端侧测量与互补的 task-level 实验；(6) **模型级成本比拟合**（从吞吐测量拟合 context-cost ratio，定义 RQ1 优化零售成本估计）。

## 关键洞察

1. **长上下文的成本被"每 1M tokens 固定定价"的商业惯例系统性隐藏了**。3.6×–7× 的真实差距意味着**同等工作量下，用 16K 上下文服务比 256K 便宜近一个数量级**——这与量化/稀疏化等正交优化处于同一量级，但常被完全忽视。
2. **"长输入"与"长上下文"是两回事**：论文最锋利的观察是 **LCW2 总可归约为 LCW1**（长输入存为资源 + 给模型选择性读取工具）。这在架构上把"需要长上下文"的主张解构成"需要检索能力"的主张——后者远为廉价且更成熟。
3. **SAC 的结果令人震惊**：把每次交互压缩到**一个动作**、只携带一段紧凑语义状态，Claude Opus 4.5 在 SWE-bench Verified 上**持平**基线、在 Terminal-Bench 上**提升 4.6 点**，peak 上下文从 130–200K 降到 15–37K。GPT 5.6 Sol 付出 2.0–3.3 点的代价换取 20× 以上的上下文缩减。**这不是"模型仍需要上下文"，而是"模型其实不太用得着那么多上下文"。**
4. **压缩次数的中位数接近零、对话长度随文档大小近似恒定**——这是比准确率数字更有说服力的证据：它表明**任务真正需要的信息量与输入规模无关**，因此"输入长 ⇒ 需要长上下文"这个推理链是断裂的。
5. **语义状态（自然语言）可以替代对话历史**：SSSM 与经典 SSM 的对照点极具启发——**SSM 维护黑盒神经状态，SSSM 维护可解释的自然语言状态**。后者可审计、可编辑、可被人类检查，这在 agent 场景中是额外收益（不只是成本）。
6. **论文提出的"为什么要训练全历史累积的模型？"是一个应当被认真对待的产业问题**：如果 compaction 几乎无损，那么上下文窗口尺寸这个长期以来的军备竞赛可能是在优化一个不必要的维度。论文的措辞很克制——"我们不排除存在长上下文有益的任务，也不证明每个任务都能用短上下文解决"，但**它确实证明了标准论据（长输入 + 长对话视界）是不充分的**。
7. **"数据效率"的推测**：论文进一步推测 SSSM 的训练**数据效率显著更高**，因为不必教模型"关注此前上下文中合适的片段"。这与 2611.04313（稀疏注意力）指向同一个方向：**上下文的价值在于稀疏检索，而非稠密驻留**。
8. **方法论上的严谨**：论文使用两个独立模型家族以降低供应商特异性风险，并用五个架构多样的开源模型做交叉验证，结论不依赖单一架构。

## 局限性

- **论文明确承认未证明所有任务都能用短上下文**："我们的证据不排除存在长上下文有益的任务的存在，也不证明每个可能的任务都能用短上下文解决。"这是必要的自我限定。
- **compaction 依赖一个"nudge"**：EoCC/SAC 需要模型自己把对话压缩成语义状态。这要求模型具备该能力——对于未被后训练过此行为的模型，效果未知。论文提议的 SSSM 正是把这一能力做成后训练目标，但**论文本身并未训练 SSSM**，只是提出概念。
- **GPT 5.6 Sol 在 SAC 下有 2.0–3.3 点的准确率损失**，说明"几乎无损"并非普遍成立，至少对某些模型/任务组合并非如此。
- **成本节省是估计值**：论文明确说明"估计的成本节省"（estimated cost savings），基于拟合的 context-cost ratio，而非实际账单。
- **单次 compaction 的语义状态是有损的**：论文未系统刻画信息损失发生在哪些任务类型上（虽然"长输入"与"长程"两组基准覆盖了主要形态）。
- **未测试超长上下文的上限**：所有实验在 16K–48K 的总限制下进行，没有测试"极短上下文（<8K）"的边界。
- **端侧 DGX Spark 测量的是延迟/吞吐/显存，不是任务准确率**；准确率实验全部在闭源大模型上。
- **compaction 的开销被计入吗**：EoCC 与 SAC 都多了一次生成（压缩本身）。论文的上下文长度统计把压缩对话计入总长度，但**压缩生成本身的额外 token 消耗与延迟成本**是否被完整计入成本节省估算，摘要与正文未明确。
- **SSSM 完全是概念性的**：没有原型、没有训练、没有评测。论文自己把 SSSM 定位为"我们提出的概念"，其"数据效率更高"的推测是 surmise 而非发现。
- **基准选择的影响**：所选基准（SWE-bench、Terminal-Bench、LongBench v2、RULER 等）都是当下主流 agent 基准，可能本身就不需要完整长上下文——这既是结论也是潜在偏差（"任务本来就不需要长上下文"与"长上下文无用"是两回事，论文用 RQ0 的措辞处理了这点）。
- **成本模型基于 H100 与特定价格**，2026 年 9 月的 Nebius 价格；其他硬件（尤其 TPU、消费级 GPU）与价格下比例可能不同。
- **论文由 NVIDIA 撰写**（版权归 NVIDIA），其对"NVIDIA 有动机支持短上下文"这一潜在利益的披露未见明确说明。

## 适用场景

**适用**：
- **云端 LLM 服务的成本优化**：若你的工作负载是长程 agent 或长输入问答，把上下文从 256K 压到 16K–48K 可带来 3.6×–7× 的直接成本节省——这是本文最直接的应用。
- **端侧 / 边缘推理**（DGX Spark 级设备）：本文给出的延迟与显存数据说明端侧尤其受益于短上下文。
- **Agent harness 设计**（如 SWE-agent 类工具）：EoCC 与 SAC 是可直接实现的两种上下文管理模式，且 SAC 几乎不损失准确率。
- **长文档问答 / RAG 系统**：选择性读取 + compaction 作为回退的范式可直接复用。
- **研究上下文效率**：SSSM 概念为"可解释语义状态"提供了一个具体的模型设计目标。
- **做 SSSM 或状态管理模型训练的研究者**：本文提供了基准、harness 范式与评估协议。

**不适用**：
- **真正需要全局信息的任务**（如对 500K 文档的全局一致性检查、跨全文的严格推理）——这类任务是否需要长上下文本文未排除。
- **不能容忍准确率下降的模型 × 任务组合**（GPT 5.6 Sol 的 SAC 结果）。
- **不支持 compaction 的模型**（未针对此行为后训练过的模型）。
- **需要跨轮精确复现历史细节的任务**：语义状态是有损摘要，而 FHA 保留一切。
