# Raincheck: Deferred Multimodal Prefill for Efficient Multi-Turn MLLM Inference

## 摘要
多轮 MLLM 交互会复用输入上下文，但长多模态输入推高 TTFT。已有的 query-aware **hard pruning** 通过减少 prefill token 降低 TTFT，却**永久丢弃**了后续问题可能需要的视觉 token。作者提出 **Raincheck**：一种 **deferred multimodal prefill** 框架，把"初始 token 选择"与"后续信息可用性"解耦——已有剪枝方法选出的重要 token 用于初始 prefill，未选中的 token 按源顺序保留，并在 decode 期间用空闲算力逐步 prefill；若答案返回时仍未完成，则在请求间隔的调度空隙中继续。在 Qwen3-VL-8B（full attention）与 Qwen3.5-9B（hybrid Gated DeltaNet）上、30% 初始多模态 token 保留率下，Raincheck 平均恢复了 hard pruning 所损失质量的 **77.7%（MultiVerse）** 与 **60.4%（ConvBench）**；在 MultiVerse 上其 SGLang 实现把首轮平均 TTFT 最多降低 **24.1%**（相对 full prefill），而平均 TPOT 增幅 **< 0.5%**。

## 核心贡献
1. **识别 hard pruning 的结构性缺陷**：一次性剪枝丢弃的 token 可能在生成中或后续轮次有用。实测 MMTok 在 30% 保留率下，第一问的选择平均遗漏了第二问所需选择的 **19.34%（Qwen3-VL-8B）/ 17.32%（Qwen3.5-9B）**。
2. **Deferred multimodal prefill 机制**：初始 prefill 处理重要 token + 全部文本/控制/特殊 token；未选 token 按源序分块在 decode 期间 prefill；未完成的在答案返回后继续。
3. **两类架构的上下文更新**：full-attention 层用 **attention visibility control**（deferred chunk 读 prefix，chunk 内因果，排除尾随输入与已生成 token）；hybrid GDN 层用 **affine state mapping** 修正 recurrent state。
4. **Fused prefill-decode 执行**：co-located executor 把 deferred chunk 与 decode token 合并为一次 decoder 前向，共享权重访问（减重复权重读取）；SGLang 实现用固定形状 CUDA graph（7/15/31 deferred + 1 decode = 8/16/32 行）。

## 方法与架构
**符号**：$K$ = 重要 token，$D$ = 延迟 token，$T_{tail}$ = 中间输入 token，$Y$ = 已处理输出 token，$S_{prefix}$ = prefix 状态，$S_{live}$ = live 状态，$P_{tail}$ = 尾随转移矩阵；状态形状 $d_k\times d_v$，映射 $d_k\times d_k$。

**执行流程**：初始 prefill 处理 $K$ 与全部 text/control/special token，产出首个输出 token；decode 期间按源序 prefill $D$ 的连续块；每个完成的块立即对进行中的回答和后续轮次可用；生成沿用 KV cache 与更新后的 recurrent state 而不重算序列。

**Full-attention 可见性**：deferred chunk 读取已处理 prefix，块内因果注意力，排除 $T_{tail}$ 与 $Y$；decode token 读取迄今全部输入与生成历史。新 deferred KV 条目插入到已处理后缀之前，既有条目保留缓存，待处理 deferred slot 保持不可见。

**GDN state mapping**（Qwen3.5 的 Gated DeltaNet 层）：$S_{prefix}$ 为恢复边界状态，$S_{live}$ 为经过 $T_{tail}$ 与 $Y$ 后的状态。记录的 GDN 更新复合为对输入状态的仿射变换：

```math
S_{live} = P_{tail}S_{prefix} + B_{tail},\qquad P_{tail} = P_Y P_{T_{tail}}
```
```math
S'_{live} = S_{live} + P_{tail}\left(S'_{prefix} - S_{prefix}\right)
```

$'$ 表示同一后缀端点处的 deferred 更新。由于 live state 已包含加性项 $B_{tail}$，修正只需 $P_{tail}$ 与 prefix-state 差，无需重跑整个后缀。每个 token 对转移矩阵施加标量衰减与 rank-1 修正，每 head 需 $O(d_k^2)$ 算术；state correction 复用已记录的后缀因子，是对扩展输入下完整重跑的近似（Qwen3.5 还需 short-convolution boundary repair）。

**PD 分离式状态 join**（附录 G.2）：decode worker 保留生成 token 的 KV $P_Y\in\mathbb{R}^{d_k\times d_k}$ 与紧凑状态：

```math
KV_{reuse} = [KV_{I_0}\ |\ KV_D\ |\ KV_Y],\qquad
S_{reuse} = S^{compact}_{live} + P_Y\left(S^{complete}_{prefix} - S^{compact}_{prefix}\right)
```

**动机数据**：ShareChat 的 102 个多模态消息间隔中，**72.5%** 至少 1 分钟，中位数约 **101 s**；TraceLab 的 tool call 中 **61.3%** 在 1 秒内完成。TPOT 随 deferred token 数上升：每步 31 个 deferred token 时，Qwen3-VL 从 6.15 → **7.33 ms**，Qwen3.5 从 6.43 → **7.88 ms**。

## 实验设置
- **模型**：Qwen3-VL-8B（full attention）、Qwen3.5-9B（hybrid GDN）。
- **对比策略**：Full（完整 prefill）、Hard（已有剪枝方法不做恢复）、Ours（同一初始选择 + deferred prefill）。适配的剪枝方法：**MMTok、HiPrune、DivPrune、VisionZip-Select**；每个 Hard/Ours 对使用相同输入、选择设置与采样种子。
- **保留率**：主实验 30% 初始多模态 token 保留；消融覆盖多档保留率与 chunk size $c\in\{7,15,31,63\}$。
- **数据集**：MultiVerse（647 段图像对话、2,536 个计分轮，DeepSeek-V4.1-Flash 按 checklist 与答案质量打分）、ConvBench（577 段三轮图像对话，DeepSeek-V4-Flash-FP8 双序比较打分）、MT-Video-Bench（119 个视频的 902 段对话，六类别等权平均）。
- **后端与硬件**：质量比较用 **Transformers**，恢复块 31 token；延迟比较用 **SGLang**，每 worker 一张 **NVIDIA H20 GPU**，单并发请求，每步至多 31 个 deferred token。
- **计时协议**：MMTok，每数据集 48 段对话，重放相同输出 token trace（MultiVerse 512-token trace；MT-Video-Bench 用模型自身 Full trace）；测 request-to-first-token TTFT、request-average TPOT、到最后一个输出 token 的 E2E 延迟（不含响应后恢复）。

| Qwen3.5-9B | — | Full | 44.90 | 44.57 |

| | HiPrune | Hard → Ours | 41.59 → **44.05** | 40.47 → **43.07** |

| | VisionZip-Select | Hard → Ours | 41.28 → **43.42** | 40.87 → **43.33** |

八个模型×剪枝组合中 Ours 全部优于对应 Hard，平均恢复 **77.7%（MultiVerse）/ 60.4%（ConvBench）** 的 Full→Hard 质量损失；ConvBench 平均提升 0.75–8.26 分。分轮看，MMTok 的 T1 增益为 **13.19 / 16.93** 分（Qwen3-VL / Qwen3.5），T2 增益 **6.47 / 6.65** 分。个别轮次会回退（Qwen3-VL + HiPrune 的 T3：Ours 58.39 < Hard 58.52）。

**视频（Table 3，MT-Video-Bench，MMTok）**：Qwen3-VL Overall 50.68（Hard）→ **51.73**（Ours），接近 Full 53.15；Qwen3.5 42.87 → **44.13**，接近 Full 44.28。

视频上 Ours 的 TTFT 降 **13.06% / 11.91%**，但平均 TPOT 增 **19.93% / 14.92%**，E2E 相对 Full 仍降 **4.83% / 6.56%**。注意 Ours 与 Hard 的配对 TTFT 区间包含零（附录 E.1），即 Ours 相对 Hard 的 TTFT 优势不显著。

**恢复完成情况（Table 5）**：MultiVerse 全部 288 个请求在答案完成前恢复完毕（0/288）；视频上 Qwen3-VL **120/288（41.67%）**、Qwen3.5 **198/288（68.75%）** 需要响应后完成，post-response 平均耗时 **74.0 ms / 162.8 ms**（P95 357.7 / 371.8 ms）。恢复期间 TPOT 均值 7.201 / 7.882 ms（MultiVerse）、8.685 / 8.064 ms（视频）。

**消融**：保留率越高可恢复的损失越少（Qwen3-VL 视频 sweep 中 50% 保留的增益大于 30%，呈非单调）；chunk size $c\in\{7,15,31,63\}$ 下质量增益稳定，MultiVerse 上 Ours 相对 Hard 提升 **2.73–6.23 分**（8 个组合，6 个配对置信区间高于零），视频上跨度仅 0.54 / 0.85 分。

**存储（Table 7）**：恢复后 KV token 数与 Full 相同；相对 Hard 需额外 $|D|b_{KV}$ 字节（$b_{KV}=2s_{KV}\sum_{\ell\in L_{attn}} h_{KV,\ell}d_{head,\ell}\cdot\text{bytes}$，因子 2 对应 key 与 value）；GDN 层存 recurrent state 而非 per-token KV；映射存储每层 2 MiB（一个 128×128 FP32）。

## 局限性
- 作者自述：单请求（batch size 1）评估，未涵盖并发 serving、其他 recurrent 架构、batched execution 与 speculative decoding；**并发与 state-mapping 假设仍是开放问题**（附录 G.1）。state correction 是基于"记录因子"的近似（附录 B.5 分析），不是精确等价于完整重跑。
- 我的批判性意见：① **Ours vs Hard 的 TTFT 差异不显著**（配对区间含零），即 deferred prefill 本身的 TTFT 收益主要由"初始只 prefill 30%"贡献，而 Ours 相对 Hard 的额外代价是 TPOT（视频上 +19.9%）与恢复期间的额外计算——这削弱了"deferred 优于 hard"在延迟维度的论证；② 视频场景 41.67%/68.75% 的请求需响应后恢复，而 post-response 时间（P95 达 371.8 ms）意味着若用户快速追问，前缀不可用、需等待 completion barrier，交互体验可能受损；③ 质量评分依赖 LLM judge（DeepSeek-V4 系列），质量恢复幅度（77.7% / 60.4%）会受 judge 偏好影响；④ GDN 状态修正的近似性质在长序列上误差可能累积，论文未给出误差上界；⑤ ConvBench 上 Ours 相对 Full 仍有 −1.8% 至 −9.8% 的差距，说明 deferred 恢复并不等价于完整 prefill。

## 评估与建议
- 是否推荐深入阅读：**是**（多模态推理效率与 KV/状态管理的工程深度高）
- 适用场景：多轮多模态对话服务（图像/视频问答）的 TTFT 优化；视觉 token 剪枝方法的后处理增强；hybrid recurrent MLLM（GDN 类）部署
- 与知识库的关联：与视觉 token 剪枝（MMTok、HiPrune、DivPrune、VisionZip）、prefill-decode fusion（Sarathi / SARATHI-Serve、POD-Attention）、KV cache 压缩（DeepSeek-V4）直接相关；适合作为"推理系统效率"主题的核心文献
