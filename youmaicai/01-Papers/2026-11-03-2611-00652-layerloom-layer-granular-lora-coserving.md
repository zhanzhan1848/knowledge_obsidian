## 核心贡献
1. **核心观察**：LoRA microbatch 的**反向传播可分解为逐层任务**，且这些任务作用在**与推理前向所访问的相同权重**上——因此反向工作可以按**层（layer）粒度**而非**迭代（iteration）粒度**调度。
2. **LayerLoom**：把**同层的反向任务挂到推理前向**上，并在每层只运行**当前在飞请求的延迟松弛（latency slack）所允许的**那么多反向任务。
3. **wavefront 机制**：维持一组**跨层错开（staggered across layers）**的 LoRA microbatch，形成 ready task 在每一层都存在的"波前"。
4. **激活显存控制**：把 microbatch 状态**卸载到主机内存（host memory）**，并**预取（prefetch）**到调度器计划使用它的那一层之前，界定 wavefront 的激活内存开销。
5. **融合 kernel**：用**单次权重读取**同时服务配对的**前向与反向 GEMM**。
6. **结果**：RTX 4090 上跑 Llama-3.1-8B、在突发（bursty）生产 trace 下，联合 SLO 达成率比已有工作**提升 13.5–21.8 个百分点**，同时微调吞吐**持平或最高高出 12%**，并达到**相同的训练损失**。

## 问题背景
在**同一批 GPU** 上同时做 LLM 推理服务与微调，可以把推理突发之间的**空闲容量**转化为**训练进展**；而 **LoRA** 让这种共置变得廉价，因为两个工作负载都只读**同一份冻结的基础权重**（无需复制模型副本、无需梯度同步基础权重）。真正的难点在**微调的反向传播**——推理侧没有对应物。现有的共置系统按**服务迭代（serving iteration）**调度反向工作：每个迭代携带**固定的反向预算**，其间到达的请求必须**等待该反向完成**，因此**一旦负载尖峰，微调就直接决定了推理延迟**。也就是说，粗粒度的反向调度把两种本可互补的资源争抢变成了串行瓶颈。

## 方法

### 关键观察：反向传播的层级分解
LoRA 的反向传播按 microbatch 进行，但每个 microbatch 的反向计算可以**分解为逐层的任务**，且这些任务作用的权重正是推理前向要访问的那些权重。因此：

```text
推理前向（按层）:  layer_1 → layer_2 → ... → layer_L
LoRA 反向（按层）:  layer_1 → layer_2 → ... → layer_L   ← 同一层权重，可对齐
```

这打破了"一个微反向 pass 必须整体完成"的约束，使调度器可以在**层内**做细粒度的取舍。

### LayerLoom 调度机制
1. **挂载（attach）**：把同层的反向任务挂到推理前向的对应层上。
2. **松弛驱动的执行量控制**：在每层，**只运行当前在飞（in-flight）请求的延迟松弛所允许的**那么多反向任务。即反向工作量不是固定的，而是**由推理侧实时的延迟预算动态决定**。
3. **Wavefront**：为保证每一层都至少有一个 ready 的反向任务，维护一组**跨层错开**的 LoRA microbatch——某个 microbatch 在低层做反向的同时，另一个已在高层就绪，从而形成向前推进的"波前"。

### 激活内存管理
wavefront 会同时保持多个 microbatch 在飞，导致激活显存上升。LayerLoom 的做法是：
- 将 microbatch 状态**卸载到主机内存**；
- **预取**到调度器计划使用它的那一层之前（即在到达该层之前就把状态搬回 GPU），从而把 wavefront 的 GPU 侧激活内存开销限定住。

### 融合 kernel
一个**融合 kernel** 用**单次基础权重读取**同时服务配对的**前向 GEMM 与反向 GEMM**。由于反向工作被移到与前向相同的层、且共享同一权重读取，这个融合带来两部分收益：省一次权重读（带宽），以及省掉反复搬运权重。

### 延迟性质
因为一个迭代的全部反向工作**在其前向内部完成**，新到达的请求可以像**连续批处理（continuous batching）**那样加入**下一个**迭代——推理侧不会被微调阻塞。这正是标题"Inference First, Training Underneath" 的含义。

## 实验结果

### 主要设置
| 维度 | 设置 |
|------|------|
| 硬件 | **单张 RTX 4090 GPU** |
| 模型 | **Llama-3.1-8B** |
| 负载 | 突发（bursty）生产 trace |
| 适配方法 | LoRA（与推理共享冻结基础权重） |

### 核心结果
| 指标 | 结果 |
|------|------|
| 联合 SLO 达成率 | 比已有工作提升 **13.5–21.8 个百分点** |
| 微调吞吐 | 与已有工作**持平或最高高出 12%** |
| 训练损失 | 达到**相同的训练损失**（same training losses） |
| 推理延迟 | 反向工作不再跨迭代阻塞推理，新请求在下一迭代加入（连续批处理语义） |

摘要未给出：基线系统的具体名称、所用 LoRA rank/目标模块、batch size、trace 的具体来源、吞吐的绝对数值（tokens/s）、SLO 的具体定义与阈值，以及不同负载水平下的扩展曲线。

## 关键洞察
1. **"反向任务可按层分解"是本文的可迁移核心洞察**：它不依赖 LayerLoom 的具体实现，而是揭示了 LoRA 微调在**梯度检查点语义下的层级可切分性**。任何做推理—训练共置的系统都可以利用这一点，把训练从"迭代级抢占"改为"层级挂载"。
2. **延迟松弛（latency slack）作为调度信号，比固定反向预算更合理**：固定预算在负载尖峰时必然损害推理延迟，而"只用还剩多少松弛就做多少训练"自动实现了训练吞吐与推理 SLO 的**自适应权衡**——这解释了为何联合 SLO 提升 13.5–21.8 点的同时训练吞吐还不降反升最多 12%。
3. **训练损失相同 + 吞吐更高 + SLO 更高，三个指标同时改善**，说明先前方法的代价主要来自**调度粒度**而非计算量本身——这是一个"零和权衡其实不必零和"的典型案例。
4. **融合 kernel 的价值依赖于"前向与反向共享同一层权重"这一调度设计**：调度决策与 kernel 设计是**耦合**的，不能分开评估——单独看 kernel 或单独看调度都会低估收益。

## 局限性
- **单机单卡评测**（1× RTX 4090），跨多卡/多机扩展性未验证；跨节点通信对"层粒度调度"的影响是未知的开放问题。
- **仅 Llama-3.1-8B**：更深的模型（层数多 → wavefront 更长）、MoE 架构、以及需要 LoRA 之外优化器状态（如全参微调、Adam 状态）的场景是否适用未说明。
- **wavefront 的主机内存卸载**代价未量化：PCIe 传输延迟、主机内存容量需求、以及预取是否总能在层到达前完成（若不能，会有 bubble）。
- **"延迟松弛"依赖准确的延迟模型/在飞请求跟踪**，在请求长度方差大时松弛估计可能失准。
- 未给出与 vLLM/TGI 等具体 serving 系统的集成细节、也未报告端到端能耗或吞吐绝对值，仅给出相对提升。
- 摘要未说明 SLO 的具体形式（TTFT / TPOT / E2E 的组合）与达成率的统计显著性。

## 适用场景
- **同一批 GPU 同时做服务与微调**的团队（自建推理平台 + 周期性微调）。
- **推理负载突发性强**的生产系统——空闲窗口正是训练时间。
- **LoRA/QLoRA 等参数高效微调**的资源受限环境。
- **单机单卡、8B 量级模型**的中小规模自托管场景。
