# A.S.E 2.0: Understanding How Repository Context Impacts the Security of LLM-Generated Code

> **arXiv**: [2611.06294](https://arxiv.org/abs/2611.06294)
> **发表日期**: 2026-11-04
> **分类**: cs.SE (及交叉分类 cs.CR, cs.AI)
> **会议/期刊**: arXiv preprint

## 📋 摘要

LLM 编码助手与 coding agent 在生成代码前都会构建"仓库上下文"（repository context）。对安全敏感代码而言，这个上下文决定了模型看到的是项目的安全防护措施（如授权检查）还是可供模仿的不安全代码。然而现有上下文构建方法几乎完全为功能正确性而设计，安全代码基准也把上下文视为固定不变，因此仓库上下文如何影响生成代码的安全性一直不清楚。作者构建了 CASE-Bench 基准，包含来自 51 个项目真实 CVE 的 145 个仓库级任务；每个任务运行在 Docker 中，配有功能测试以及双向验证的 proof-of-concept 利用程序，并标注了维护或破坏其安全性的仓库代码。基于 CASE-Bench，作者比较了 13 种上下文构建方法与 6 组对照、测试了 6 个 LLM、单点编辑上下文元素，并分析了 coding agent 的执行轨迹。主要发现：面向功能性的上下文最多提升功能通过率 8.2 个百分点（pp），但安全通过率最多只提升 3.7 pp；隐去一项安全防护会使安全通过率最多下降 8.1 pp，而插入一个不安全范例则使"正确但可被利用"的代码增加 6.3 pp；coding agent 在仅有 27–36% 的轨迹中观察到了相关安全防护。

## 🎯 核心贡献

1. **CASE-Bench**：首个面向仓库级的 LLM 安全代码生成基准——145 个源自 51 个项目真实 CVE 的任务，双向验证的 PoC 利用程序 + 功能测试，并细粒度标注"维护安全性的代码"与"破坏安全性的代码"。
2. **系统性上下文消融实验**：首次在受控设置下量化"上下文构建方式"与"生成代码安全性"的因果关系，比较 13 种上下文构建方法、6 组对照、6 个 LLM，并做单元素编辑（移除防护 / 插入不安全范例）。
3. **关键定量结论**：功能性上下文的功能收益（+8.2 pp）显著大于其安全收益（+3.7 pp）；缺失防护的代价（−8.1 pp）与不安全范例的污染效应（+6.3 pp "correct-but-exploitable"）均大于安全收益，说明当前上下文构建存在**安全赤字**。
4. **coding agent 轨迹分析**：量化了 agent 实际"看见"安全防护的比例仅 27–36%，揭示了代理在长程执行中系统性遗漏安全约束的问题。

## 🔧 方法/架构

- **基准构建**：从 51 个项目的真实 CVE 出发构建 145 个仓库级任务；每个任务封装为 Docker 环境，同时提供功能测试（functional test）与 PoC 利用程序，且 PoC 做**双向验证**（exploit 能击穿修复后的代码，修复后能挡住 exploit），确保任务的通过/失败判定无歧义。
- **任务标注**：对每个任务标注仓库中"执行安全约束的代码"（如授权检查）与"削弱安全性的代码"，作为上下文干预（context intervention）的操作对象。
- **上下文构建方法族**：13 种方法 + 6 组对照（control），跨 6 个 LLM 评测；采用**单元素编辑**（single-element editing）做因果归因——即只改动上下文中的一个元素（删除某个 safeguard / 插入一个 insecure exemplar），观察指标变化。
- **评测指标**：
  - Functional Pass Rate（功能通过率）
  - Secure Pass Rate（安全通过率）
  - Correct-but-Exploitable Rate（功能正确但存在漏洞的代码占比）
- **代理轨迹分析**：对 coding agent 的执行轨迹做序列挖掘，统计关键安全防护在上下文窗口中被 agent 实际检索/观察到的比例。

## 📊 实验结果

- 功能通过率 vs 安全通过率（功能导向上下文）：functional pass rate 最多 **+8.2 pp**，secure pass rate 最多仅 **+3.7 pp**
- 隐去单个 safeguard：secure pass rate 最多 **−8.1 pp**
- 插入 1 个 insecure exemplar：correct-but-exploitable code **+6.3 pp**
- coding agent 轨迹中观察到相关 safeguard 的比例：**27–36%**
- 规模：13 种上下文构建方法 × 6 组对照 × 6 个 LLM；145 个任务 / 51 个项目

## ⚠️ 局限性

- 基准仅覆盖 51 个项目、145 个任务，且依赖真实 CVE，样本对"特定漏洞类型"可能存在偏置，跨项目/跨语言泛化性需进一步验证。
- 安全通过率依赖 PoC 的完备性，双向验证能减少误判，但 PoC 未覆盖的漏洞路径仍可能被计为"安全"。
- 六个 LLM 的规模与家族未在摘要中披露，对更大规模模型的行为是否单调成立尚不明确。
- 27–36% 的 safeguard 观察率结论与 agent 框架、上下文长度预算强相关，可能不适用于所有 agent 形态。

## 💡 建议

- 是否推荐使用：**是**（做安全代码生成 / coding agent 评测必读）
