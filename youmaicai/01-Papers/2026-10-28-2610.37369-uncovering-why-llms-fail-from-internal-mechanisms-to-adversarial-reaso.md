## 核心贡献

> **用一个白盒诊断框架，把「LLM 为什么失败」拆解为「支撑（support）→ 承诺（commitment）→ 验证（verification）」三阶段的内部机制演化** —— 并证明普通推理失败与对抗性诱导失败**可用同一套内部坐标刻画**。

1. **批评现有评测**：LLM 通常只按**最终输出的正确性或安全性**评估，但**端点标签无法揭示失败在整个推理过程中如何发展**。
2. **提出 CauTrace**，三个基础检查：
   - **① Functional States（功能状态）**：定义 **7 个功能状态**，表征 LLM 中的**支撑处理（support）**与**约束处理（constraint）**
   - **② Propagation of Representation（表示传播）**：度量这 7 个状态之间的变化**如何持续跨越后续 Transformer block**
   - **③ Temporal-State Coordination & Reasoning Trajectory（时序-状态协调与推理轨迹）**：刻画**承诺（commitment）与验证（verification）相对支撑发生的时机**，以及**主导状态序列在整个推理过程中的演化**
3. **核心实证发现**（Qwen 与 LLaMA 家族）：
   - 失败轨迹表现出**更弱的 Attention-MLP agreement（注意力-MLP 一致性）** 于支撑状态更新
   - **验证活动相对于承诺更少**
   - 但**具体的表示层签名与时序偏移随架构而变**
4. **操作性验证**：留出（held-out）的**修复与 steering 测试**显示过程指标确实呈现与论断一致的可操作信号；**对齐的 steering 产生了预测的方向性变化**

## 技术方案

### 核心思想

把一次推理看成一条**状态序列**。模型在每层每 token 上处于 7 个功能状态之一，不同状态对应不同的「信息处理职能」。失败不是终点的一个标签，而是**状态序列走偏的过程**。

```text
支撑 support ──▶ 承诺 commitment ──▶ 验证 verification
   │                  │                    │
   │  弱 Attention-MLP 一致性  │   验证活动偏少  │
   └──────────────────┴────────────────────┘
              = 失败轨迹的典型特征

正常:  support(多) ─▶ commit ─▶ verify(充分) ─▶ ✓
失败:  support(少/弱) ─▶ commit(早/急) ─▶ verify(不足) ─▶ ✗
```

### 关键技术

| 技术 | 说明 |
|------|------|
| **7 个功能状态** | 表征 support（支撑）与 constraint（约束）处理 |
| **表示传播度量** | 状态变化在后续 block 中的持续性 |
| **Attention-MLP agreement** | 注意力子层与 MLP 子层对支撑状态更新的一致程度 —— 失败时**减弱** |
| **时序-状态协调** | commitment / verification 相对 support 的时机关系 |
| **轨迹拓扑** | 主导状态序列的演化结构 |
| **对抗配对分析** | 同一问题的 clean 失败 vs 对抗扰动失败，用同一坐标对照 |
| **留出修复 / steering** | 用过程指标预测干预效果，验证指标有因果意义而非事后归因 |

## 公式

```math
\text{Attention-MLP agreement（在层 } \ell \text{）}:\quad
A_{\ell} \;=\; \frac{\langle \Delta H_{\ell}^{\text{attn}},\; \Delta H_{\ell}^{\text{mlp}} \rangle}
{\|\Delta H_{\ell}^{\text{attn}}\| \,\|\Delta H_{\ell}^{\text{mlp}}\|}
```

```math
\text{表示传播强度}:\quad
P_{\ell \to \ell+k} \;=\; \frac{\| H_{\ell+k} - H_{\ell} \|_F}{\| H_{\ell+k} \|_F}
\qquad
\text{（衡量状态变化能否跨 block 持续）}
```

```math
\text{时序协调比}:\quad
\tau \;=\; \frac{\text{pos}(\text{verification onset})}{\text{pos}(\text{commitment onset})}
\;\;\text{—— 失败轨迹中 } \tau \text{ 更大（验证更晚/更少）}
```

## 代码片段

```python
# 概念性伪代码：CauTrace 的轨迹分析
import torch

FUNCTIONAL_STATES = ["support_query", "support_retrieve", "support_integrate",
                     "constraint_parse", "constraint_apply",
                     "commit", "verify"]

def trace_cau_trace(model, tokenizer, prompt, adversarial_prompt=None):
    # 提取一次推理的功能状态序列与过程指标。
    hs = model.forward_with_hidden_states(prompt)   # 每层 hidden states
    seq = classify_states(hs)                       # → 每 (layer, token) 的 7 态序列

    metrics = {
        # ① Attention-MLP agreement：注意力与 MLP 对支撑更新的方向一致性
        "attn_mlp_agreement": mean_cosine(
            deltas(hs, "attn", layer_range=last_4),
            deltas(hs, "mlp",  layer_range=last_4)),

        # ② 表示传播：支撑状态变化能否跨 block 持续
        "propagation": propagation_strength(hs, states=seq, support_states=[0,1,2]),

        # ③ 时序-状态协调：承诺与验证的时机关系
        "commit_pos": first_onset(seq, "commit"),
        "verify_pos": first_onset(seq, "verify"),
    }
    metrics["tau"] = metrics["verify_pos"] / max(metrics["commit_pos"], 1)

    # 对抗配对：同一问题在扰动下的轨迹差异
    if adversarial_prompt:
        adv = trace_cau_trace(model, tokenizer, adversarial_prompt)
        metrics["adversarial_delta"] = compare(seq, adv["seq"])
    return metrics
```

## 实验结论

- **模型**: Qwen 家族, LLaMA 家族
- **评测**: clean 推理失败 + **配对的对抗扰动**
- **发现**:
  - 失败轨迹 → **Attention-MLP agreement 更弱**（支撑状态更新处）
  - **验证活动相对承诺更少**
  - **表示层签名与时序偏移因架构而异**（不能跨架构直接迁移）
- **干预验证**（留出修复 + steering）:
  - 过程指标**给出一致的可操作信号**
  - **对齐的 steering 产生了预测的方向性变化**（说明指标有方向性因果意义）

## 局限性

1. **7 个功能状态是「创造性地定义」的** —— 摘要原文即用 "creatively defined"，说明这**不是从既有理论推导出来的**，而是事后构造的框架。**构造出来的状态分类很难证伪**
2. **跨架构不可迁移** —— 作者自己指出签名与时序随架构变化，这直接削弱了框架的普适性主张
3. **干预验证仅在「特定模型与特定设置」下与论断一致** —— 摘要用的是 "for certain models and specific settings" 这种限定语，说明**并非普适成立**
4. **对抗分析仅是配对比较** —— 未说明扰动强度、是否覆盖多种攻击类型
5. **白盒依赖** —— 只能用于有访问权限的模型，闭源 API 模型无法应用
6. **计算成本未提** —— 需要逐层 hidden states 与中间激活，诊断开销不小
7. **7 态 → 失败 的映射可能有冗余/共线** —— 状态与过程指标的相关性分析未见

## 实现建议

- **实现难度**: 高（需要逐层激活捕获 + 状态分类器 + 对抗扰动构造）
- **预期性能**: 作为**诊断工具**有启发性，但不宜作为决策依据
- **适用场景**:
  - **白盒模型的失败归因研究**（自研模型、开放权重模型）
  - **为 steering / 修复干预提供候选信号**
- **落地注意**:
  1. **不要把 7 态分类当作 ground truth** —— 它是框架的一部分，不是发现的一部分
  2. **最实用的部分是 Attention-MLP agreement 这个指标** —— 它定义清晰、可计算、与失败相关，且与 steering 有方向性关联
  3. **跨模型要用各自的基线归一化** —— 作者明说签名因架构而异
  4. **注意这属于「解释性研究」范畴**：产出的是假设，不是可即刻落地的优化手段

## 我的评注

> 我欣赏这篇的**问题意识**：端点正确性是 LLM 评估最贫瘠的信号 —— 一个 50 步推理链里第 7 步走偏了，端点标签完全看不出。这对 agent 场景尤其致命，因为 agent 的失败往往是**渐进式的偏航**而非某一刻的崩溃。
>
> 但方法论上有硬伤：**7 个功能状态是「创造性地定义」的**。这是论文自己写的词。事后构造一个状态分类，再证明「失败轨迹在这些状态上呈现某种模式」，很容易变成**不可证伪的叙事**。真正的验证应该包括：状态分类的**独立标注一致性**、以及在**新任务/新模型上的预测性**（而非事后解释性）。
>
> 作者其实自己给出了最诚实的限定：*"for certain models and specific settings"*。翻译过来就是「在某些模型和特定设置下成立」。配上「签名随架构变化」，这个框架目前更像**一套可用的分析仪器**，而不是**一个理论**。
>
> 真正有价值的部分我认为有两个：(1) **Attention-MLP agreement** 这个指标本身 —— 定义清晰、跨层可算、与失败稳健相关；(2) **用干预验证过程指标的方向性**（aligned steering 产生预测的变化）。后者是把「解释」升格为「可操作诊断」的关键一步。可惜摘要里它只是顺带一提。
>
> 结论：当作**工具箱的一个新探针**来用，别当作**LLM 失败的解释理论**。
