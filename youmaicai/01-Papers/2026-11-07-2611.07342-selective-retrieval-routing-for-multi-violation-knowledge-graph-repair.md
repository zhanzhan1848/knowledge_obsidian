# Selective Retrieval Routing for Multi-Violation Knowledge Graph Repair

### 核心贡献
1. 提出 **迭代式知识图谱修复中的「选择性检索」框架**：一个 LLM repair agent 负责探索与编辑图谱，一个 **router** 决定是否放行 agent 去调用一个负责从外部语料检索证据的 researcher agent。
2. 扩展 **violation-injection 框架**，生成含 **多个互相兼容的 violation** 且带 **已知参考修复** 的测试样例；agent 在这些样例上的修复结果被用作训练 **部署特定（deployment-specific）router** 的监督信号。
3. 实证发现：外部检索对某些 violation 有帮助、对另一些反而有害，且效果 **因部署而异**；router 相比「始终开启检索」在全部 **6 个评测套件**上使用更少的修复期 token，相比「始终关闭检索」在 **6 个套件中的 5 个**上取得更高的修复 **F₁**。

### 技术方案
**核心思想**: schema validation 只能告诉你图谱有错，却不能告诉你多个合法修复里哪个才是本意；外部语料能提供证据但检索昂贵且不总成功。因此不应「一律检索」或「一律不检索」，而应训练一个 **按部署定制的路由器**，只在检索真正会带来修复收益时才放行 researcher agent。

| 技术 | 说明 |
|------|------|
| LLM repair agent | 负责在知识图谱上探索并执行编辑（repair），产出修复轨迹/结果 |
| Researcher agent | 专门负责从外部语料中检索证据，为 repair agent 提供判定「本意修复」的依据 |
| Router | 控制 repair agent 是否可以访问 researcher agent；用部署特定的修复结果监督训练，以在「检索成本」与「修复收益」之间做决策 |
| Violation-injection 扩展 | 扩展已有框架以生成 **多 violation 且兼容** 的样例，并附带 **ground-truth reference repair**，这正是训练 router 所需的监督来源 |
| 部署特定（deployment-specific）router | router 的训练绑定到具体部署/数据集，因此能捕捉「某部署下检索有益、另一部署下有害」的结构性差异 |

### 实验结果
- **数据集**: 2 个 building-automation（楼宇自动化）知识图谱数据集；共 **6 个评测套件**
- **基线**: always-on access（始终允许检索）、always-off access（始终禁止检索）两种极端策略
- **结果**: 检索对部分 violation 有益、对另部分有害，效应跨部署不同；router 在 **6/6** 套件上 token 用量少于 always-on，在 **5/6** 套件上修复 F₁ 高于 always-off

### 局限性
- 领域窄：仅在 **building-automation** 知识图谱上验证，迁移到其他 KG 领域摘要未说明
- router 需要 **部署特定训练**，无法零样本泛化到新部署（摘要未说明是否有 zero-shot 迁移能力）
- 摘要未给出具体 F₁ 数值与 token 节省比例
- 多 violation 样例由 violation-injection 合成而来，与真实数据分布的差距未量化

### 关键洞见
> 「透明即好」在 agentic pipeline 里并不成立：外部检索对同一批错误而言，有的被治好有的被治坏，方向甚至在不同部署间相反。因此检索本身应被当成一个需要 **学习路由策略的可学习动作**，而不是默认开启的上下文扩展。
