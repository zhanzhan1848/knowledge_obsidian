## 核心贡献
1. **OntoDoc**：一个**多智能体（multi-agent）框架**，为任意 **IRI（Internationalized Resource Identifier）**——只要它位于某个 **SPARQL 端点**或 **RDF 文件**中——自动生成自然语言描述。
2. **四阶段流水线**：
   - **Database Context agent**：通过 **SPARQL 自适应探索**知识图谱，收集关于目标 IRI 的**语义信息丰富**的三元组；
   - **Web Context agent**：从 **Wikipedia 与开放网络**检索并**重排序（re-rank）**百科性背景知识；
   - **Assumption Generation agent**：把两个上下文合成为**结构化、证据接地的中间假设列表**；
   - **Description Generation agent**：基于这些接地假设产出最终自然语言描述。
3. **评测**：在 **3 个知识图谱**（**生物医学、农业、跨领域**）上评测，兼用 **LLM 自动打分**与 **11 名标注者的人工评测**。
4. **主要结论**：在**准确性（accuracy）**上持续**匹配或超过**朴素 LLM 基线与模板化本体描述器（ontology verbalizer）；在**完整性（completeness）**上**大幅超越**两个基线——相对朴素基线**平均提升 12%**，相对本体描述器在 **5 分制**上最多提升 **2.8 分**。

## 问题背景
知识图谱与本体是**结构化、机器可读**知识表示的骨干，但**本体术语常常缺少自然语言描述**，这限制了它们对人类与其它系统的**可访问性与复用性**（例如搜索引擎、LLM、跨本体对齐都无法基于定义文本理解一个术语）。现有的**本体语言化（ontology verbalization）**方法大多依赖**规则驱动或模板驱动**的技术，且只作用于**严格的、形式化的 schema 公理**——结果是**僵硬的描述**，无法传达更丰富的**上下文语义**。也就是说：一个用 OWL 公理拼出来的描述通常只能说"X 是 Y 的子类，且具有属性 Z"，而说不出"X 在实际业务中指什么、有什么典型用途"。

## 方法

### 四阶段多智能体流水线

```
目标 IRI
   ↓
┌──────────────────────────────────────────────┐
│ [1] Database Context agent                   │
│     自适应 SPARQL 探索 KG                    │
│     → 语义信息丰富的三元组                     │
└──────────────────────────────────────────────┘
   ↓
┌──────────────────────────────────────────────┐
│ [2] Web Context agent                        │
│     Wikipedia + 开放网络检索 → 重排序         │
│     → 百科性背景知识                          │
└──────────────────────────────────────────────┘
   ↓
┌──────────────────────────────────────────────┐
│ [3] Assumption Generation agent              │
│     合成两个上下文 → 结构化、证据接地的假设列表 │
└──────────────────────────────────────────────┘
   ↓
┌──────────────────────────────────────────────┐
│ [4] Description Generation agent             │
│     从接地假设 → 最终自然语言描述              │
└──────────────────────────────────────────────┘
```

### 各阶段设计要点

**[1] Database Context agent — 自适应 SPARQL 探索**
不是执行固定查询模板，而是**自适应地探索**知识图谱，围绕目标 IRI 收集**语义信息丰富**的三元组。这是与"模板化 verbalizer"的核心分野：前者靠**图上的邻域探索**取得证据，后者靠**公理模式匹配**。

**[2] Web Context agent — 检索 + 重排序**
从 **Wikipedia 与开放网络**取回百科性背景知识，并做**重排序（re-ranking）**。重排序这一步是必要的：直接拼接 web 检索结果会把噪声带入后续假设合成，破坏"证据接地"。

**[3] Assumption Generation agent — 中间假设层**
这是本文最有设计感的部分：它**不直接生成描述**，而是先把两个上下文合成为一份**结构化的、证据接地的中间假设列表**。作用有三：
- 把"检索"与"写作"解耦，检索的噪声不会直接污染最终文本；
- 每条假设都**可追溯到证据**，因而最终描述的可核验性更高；
- 结构化假设为描述生成阶段提供了显式的"写作提纲"。

**[4] Description Generation agent**
以接地假设为输入生成最终描述。

## 实验结果

### 评测设置
| 维度 | 设置 |
|------|------|
| 知识图谱 | **3 个**：生物医学、农业、跨领域 |
| 自动评测 | **LLM 打分** |
| 人工评测 | **11 名标注者** |
| 基线 | (a) 朴素 LLM 基线；(b) 模板化本体 verbalizer |

### 结果
| 指标 | 结果 |
|------|------|
| 准确性（accuracy） | 在所有领域**匹配或超过**两个基线 |
| 完整性（completeness），vs 朴素 LLM 基线 | **平均提升 12%** |
| 完整性（completeness），vs 本体 verbalizer | 在 **5 分制**上最多提升 **2.8 分** |

摘要未给出：三个知识图谱的具体名称与规模、描述数量、LLM 打分所用的模型与提示、准确性的具体数值、以及人工评测的标注者间一致性（IAA）。

## 关键洞察
1. **"准确性打平、完整性大幅领先"是一个有意义的非对称结果**：OntoDoc 并未在"说得对"上超越朴素 LLM——它守住了准确性（基线的天花板本就不低），而在**"说得全"**上拉开 12% 的差距。这说明真正的痛点是**覆盖度**而非正确性，而"两个上下文 + 中间假设"的组合正是补齐上下文语义（而非形式公理）的有效途径。
2. **中间假设层是本文真正的架构贡献**：把检索证据转成显式、带证据的结构化假设，再交给描述器写作。这一"先立论、后成文"的分解，既抑制了 web 检索噪声，也天然产生**可溯源**的描述——这正是本体描述在跨本体对齐、术语消歧等下游任务中最需要的属性（摘要未强调溯源，但结构本身支持这一点）。
3. **多上下文互补是必需的**：KG 给的是结构化、精确但贫乏的语义，Web 给的是丰富但不可靠的背景。第三阶段的合成正是处理这种"一个太干、一个太湿"的张力——这解释了为何单上下文方案（朴素 LLM 直接问、或只做 KG verbalization）都拿不到完整性的提升。
4. **基于 SPARQL 端点的通用性是该框架最大的部署优势**：只需一个 SPARQL 端点或 RDF 文件即可运行，无需针对每个本体编写规则/模板——这与需要大量人工模板的既有 verbalizer 形成鲜明对比。

## 局限性
- **准确性上没有超越朴素 LLM**：意味着当朴素 LLM 已经知道该 IRI 时，OntoDoc 的复杂度换来的收益有限；在长尾（不常见术语）上的优势才更可能体现，但摘要未做长尾/头部拆分。
- **LLM 自动打分作为评测之一**存在循环性风险（用 LLM 评 LLM 生成的内容），虽然配了人工评测，但人工评测的规模与一致性未披露。
- **依赖 LLM 自主决定 SPARQL 查询**会带来执行开销与失败模式（无效查询、查询爆炸），摘要未讨论查询成本与健壮性。
- **Web 检索引入时效性与幻觉风险**：摘要未说明如何处理开放网络上的错误信息、如何保证最终描述与本体事实一致（即 grounding 的度量）。
- **三个知识图谱不足以覆盖本体多样性**：尤其缺少超大型医学本体（如 SNOMED、UMLS）、多语言本体、以及含大量实例级数据的情形。
- 未与 LLM 时代的其它 LLM-based verbalizer 直接比较，基线偏弱（朴素 LLM / 模板方法），这削弱了"全面超越基线"的结论强度。
- 未讨论描述的可维护性（本体变更后描述如何增量更新）——这是本体维护流程中的实际痛点。

## 适用场景
- **本体/KG 的术语描述补全**：自动化填充缺失的 `rdfs:comment`、`skos:definition` 等注释属性。
- **跨本体对齐与术语消歧**：为需要文本语义的对齐算法提供描述输入。
- **SPARQL 端点上的语义检索**：让 LLM/RAG 系统能以自然语言方式检索本体资源。
- **领域知识库建设**：生物医学、农业等垂直领域的知识图谱文档化与可读性提升。
