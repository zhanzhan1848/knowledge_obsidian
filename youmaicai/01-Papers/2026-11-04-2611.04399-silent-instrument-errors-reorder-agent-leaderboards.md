## 核心贡献
1. **揭示了一个公共 agent 榜单上的"通用性代价"结论是评分器伪影**：在 HAL（Holistic Agent Leaderboard）的 TAU-bench Airline 上，通用 agent（Generalist scaffold）落后针对该基准定制的 Tool-Calling scaffold 13 分。根因是 TAU-bench 只在 episode **正式结束时**计算奖励，而 Generalist 常以不触发结束事件的方式收尾，导致**只有约一半 episode 被评分，其余被直接存为失败**。
2. **离线补评未评分的一半即可抹平差距，无需重跑任何 agent**：Generalist 在那 41 个任务的池化准确率从 **0.30 升到 0.43**，Tool-Calling 几乎不动（其 episode 本已全部评分），13 分的公开差距变成平局；在数据库写入类任务上 Generalist 也从 **0.28 升到 0.33**。Tool-Calling 被评分比例 **98%**，Generalist 仅 **51%**。
3. **审计了两个公共榜单（HAL 与 τ²-bench）仅凭已发布产物，额外发现三处 instrument error**：① **成本列把嵌套模型调用重复计数**——134 次有日志的运行中 **70 次精确是 2×**，46 次是 1×；44/94 个可匹配的榜单行在归档的 results 字段中带双倍成本。② **归档轨迹把 grader 写的动作记成了 agent 的动作**——**2,334 条 airline 记录中 68% 存在**。③ **用更新的评估器重新评分本身就是一次新的测量**——τ²-bench 一次有文档的 re-grade 把某个模型从第 9 名移到并列第 5。
4. **最危险的一例：一个 mode check 误读 4 个文件，把它们的分数压低 59 到 82 分，却不打印任何错误**。每个 case 都产生了一个"看起来合理"的数字——跳过一集的 grader 返回 0，看起来像失败；重复计数的成本聚合器返回一个落在其他行区间内的美元数；静默丢弃部分环境的 re-grade 返回一个 0 到 1 之间的通过率。
5. **HAL 维护者在五周内确认了三处 HAL 错误并给榜单加了披露说明**（但归档数字保持不变）。作者两次把审计结果发布在 HAL 讨论页上，第二次是为修正第一次审计规则（漏掉了 73 个只在记录中部注入 gold 动作的 Generalist episode）。
6. **提出四项廉价检查以暴露 instrument**：报告 **graded fraction**（被评分比例）、从 **root spans** 汇总成本、给每条记录的动作打上 **provenance**（来源）标签、用**已发布的 re-grade diff** 钉住评估器版本。

## 问题背景
agent 评估的"测量工具"——即负责评分、日志、回放、版本管理的代码——本身是测量的一部分，但它**静默失败**：每个错误都产生一个落在合理区间内的数字，而不是报错。因此分数与排名可以在**没有任何可见征兆**的情况下移动。

静态基准暴露面小得多：QA 基准把一个字符串与参考比较一次，在一个函数里完成，评分代码很少依赖模型回答之前做过什么。而 agent 评估有四个独特的暴露点：

1. **评分由 agent 行为触发**：交互式基准中 grader 在 episode 结束时运行，而 episode 的结束取决于 agent 或模拟用户做了某个特定的事（调用终止工具、发出 stop token）。以不同方式结束对话的 scaffold 因此能改变评分是否发生，而**缺失的评分通常被存为失败**。
2. **日志有多层**：一次模型调用穿过 scaffold、wrapper 库与 provider client，现代 tracing 工具给每一层都建 span。成本/token 总量对不对取决于聚合器加总了哪些层——这个选择在总量里不可见，且随每次运行恰好走的 client 路径而变。
3. **回放会写入记录**：有状态的 grader 常把 gold 动作通过 agent 用过的同一个环境对象回放以判断是否到达正确末态。回放期间环境记录的一切都落在与 agent 自己的动作相同的列表与日志里，轨迹归档因此继承了它们。
4. **评估器与归档以不同速度演进**：基准发布新的评分代码与新的任务标准，而旧结果仍留在榜单上、旧轨迹仍留在存储里。用新代码重新评分一条保存的轨迹被当作保持可比性的手段，但它**是一次新的测量**，其正确性取决于新代码能否正确理解旧文件。

HAL 正是为回应 Kapoor et al. 关于"agent 基准应同时报告成本与准确率、评估实践缺乏标准化"的呼吁而建的共享 harness，还完整释放了全部轨迹供人检查。**如果 instrument 在这里能静默失败，粗心就不是解释**——错误藏在 agent 评估流水线的组装方式里，而别的流水线也是这么搭的。

## 方法
### 1. 审计范围与方法
作者**仅从已发布产物重新推导**两个公共榜单的运行时 instrument：HAL 在 Hugging Face 上的加密轨迹归档（用其自己公开的脚本解密）与 τ²-bench 的榜单和仓库轨迹。**未运行任何 agent，未调用任何模型**。HAL 数字用独立编写的代码二次重算，每个数字都能从发布脚本复现。

### 2. 区分 grader 动作与 agent 动作
从归档中记录每个 episode 是否被评分的方法：
1. 从日志中的模型输出解析 **agent 自己的 tool calls**；
2. 按 tool 名与参数**顺序对齐**到记录的动作列表；
3. **无对应 agent 调用的记录动作即属于 grader**。
一个 episode 记为"已评分"，当且仅当其记录中**任何位置**含有这样一份注入的 gold 动作副本，或其记录的 reward 为正。

第一次审计（2026 年 9 月发布在 HAL 讨论页）用的是更简单的规则——只把 gold 动作构成记录结尾的 episode 记为已评分——该规则**漏掉了 73 个唯一注入副本位于记录中部的 Generalist episode**。论文中的数字取代了那份报告。

### 3. 交叉验证
- 在每个记录到的结束事件处用记录内嵌的 gold 重跑 grader，**全部 1,951 条已评分记录复现出记录的 reward**。
- 只回放 agent 自己的动作于已评分 episode：Tool-Calling 复现 **97%**、Few-Shot **97%**、Generalist **84%** 的记录 reward；且 Generalist 的分歧几乎全是"grader 判过、离线回放判不过"的 episode——因此离线补评未评分 episode 若有偏，也是**低估** Generalist。
- HAL 从一个 fork 安装 agent，其 airline gold 在 50 个任务中的 3 个上与 pinned commit 不同，因此每次 re-grade 也针对记录内嵌的 gold 运行，池化数字不变。
- 对 τ²-bench：并排安装 4 个 build（0.2.0、1.0.0、1.0.1 之前的 commit、1.0.1），在每个 build 下重新评分公开轨迹文件，独立地变化评估器代码与任务数据。**保真度检查是精确的**：对 claude-opus-4-5 在 banking 上的 1.0.1 re-grade 得到通过率 **0.2474**，官方数字是 **24.74%**。Banking 在 5 个所有 build 都能解析的榜单文件上重新评分，17-submission 的数字来自仓库自身的前后提交文件。

## 实验结果
- **Dataset/Task**: HAL 归档（TAU-bench Airline，50 任务中 41 个 gold 至少查询或修改数据库的任务）+ τ²-bench 公开轨迹；10 个模型 × 3 个 scaffold（Generalist / Tool-Calling / Few-Shot，后者因测试集泄漏已被 HAL 撤回）。
- **Main results** — 四类 instrument error：

| Case | 分数声称了什么 | instrument 实际做了什么 | 移动幅度 |
|------|--------------|----------------------|---------|
| HAL cost | agent 一次运行花的美元数 | 对 wrapper span 及其子 span（携带同一 response）求 usage 之和 | 134 次有日志运行中 **恰好 2×** 达 70 次，1× 达 46 次 |
| HAL Generalist grading | Generalist scaffold 的准确率 | 只评分 agent 转接或模拟用户关闭的 episode，其余存为失败 | **0.30 → 0.43**，抹平 13 分差距至与 Tool-Calling 平局 |
| HAL trajectories | agent 采取的动作 | 把 grader 的 gold 回放写进了 agent 的动作列表 | 2,334 条 airline 记录中 **68%** 存在 |
| τ²-bench re-grade | 同一条轨迹被再次评分 | 应用新标准或重建环境时没有用户的工具 | airline **−7 到 +2.5 分**，telecom 最高 **−82 分** |

逐模型 TAU-bench Airline 准确率（HAL，gold 含至少一个非终止动作的任务，池化各模型多次运行）：

| Model | records | Generalist (published) | Tool-Calling | Generalist (all graded) | Few-Shot (withdrawn) |
|-------|---------|----------------------|-------------|------------------------|----------------------|
| claude-3.7-sonnet | 81 | 0.49 | 0.52 | 0.60 | 0.46 |
| claude-opus-4 | 82 | n/a | 0.41 | 0.50 | 0.57 |
| claude-opus-4.1 | 82 | 0.51 | 0.37 | 0.50 | 0.55 |
| deepseek-r1 | 41 | 0.31 | 0.10 | 0.24 | 0.24 |
| deepseek-v3 | 41 | 0.38 | 0.17 | 0.37 | 0.22 |
| gemini-2.0-flash | 41 | 0.22 | 0.20 | 0.32 | 0.32 |
| gpt-4.1 | 41 | 0.29 | 0.20 | 0.27 | 0.51 |
| gpt-5 | 82 | 0.44 | 0.34 | 0.43 | 0.50 |
| o3 | 40 | 0.49 | 0.20 | 0.38 | 0.46 |
| o4-mini | 82 | 0.41 | 0.18 | 0.38 | 0.49 |

- **Ablations / 细节**:
  - Tool-Calling 与 Few-Shot 的分数在 re-grade 后基本不变（Tool-Calling 只有 claude-3.7-sonnet 从 0.48 变、gpt-4.1 从 0.27 变），说明**未评分 episode 的比例正是差距的来源**。
  - 未评分 episode 的中位动作数为 9，远低于任何 step limit——它们确实"正常结束"了，只是结束方式不触发评分。
  - 一部分补评增益不能靠"什么都不做"获得：池化增益大部分来自 gold 只读数据库的任务（benchmark 规则在 episode 未改动数据库时一律通过，正如它对另一 scaffold 的已评分 episode 那样）；但在 gold 要求写数据库的任务上，未被触碰的数据库会失败，Generalist 仍从 0.28 升到 0.33。
  - 成本双计的分布依赖 client 路径，取决于 scaffold 与模型 provider：**SciCode 上全部 10 次 zero-shot 运行是干净的，而另外两个 scaffold 的大多数运行约为成本的两倍**——一个基准的成本轴混合了双计与未双计的行。
  - 一个具体的不可见性例子：Tool-Calling scaffold + Claude Opus 4.1（high reasoning）被标为 **$149.98**，而其 root-span 成本是 **$74.99**。两个数字都是 50 个 airline 任务的合理价格，行里没有任何东西告诉读者哪个是真的。
  - HAL 论文在为自己的日志分析准备 transcript 时**移除**了"任何与 weave logging 相关的冗余调用"——重复问题在一个环节被处理、在计算成本列的环节没有被处理。
  - 榜单排名层面的影响：把 Few-Shot 的撤回轨迹算在内，Generalist 在 10 个模型中的 9 个位列三 scaffold 之末；全部评分后，末位降到 6 个，但 Generalist 在 claude-3.7-sonnet 上为第一，在 gemini-2.0-flash 上与 Few-Shot 并列第一，在 deepseek-r1 上与 Few-Shot 并列末位，在 deepseek-v3 上第二。
  - τ²-bench 一次**有文档且已公告的正确修复**本身就会重排榜单：把某个模型从第 9 名移到并列第 5。

## 关键洞察
1. **"通用性有代价"这个流行结论可能只是评分触发机制的伪影**：一个 agent 常以不触发评分的方式结束对话，其一半的 episode 被记为失败。这提醒我们：任何跨 scaffold 的 agent 对比，必须先检查"被评分的比例"是否可比。
2. **评分缺失被存为失败是一种"静默的零"**：它与"真的失败了"在数据中不可区分，因此在聚合后表现为准确率差异——一种最危险的错误形态，因为它的产出看起来完全正常。
3. **不均匀的系统性误差比均匀误差更有害**：成本列若整体乘 2 只是缩放坐标轴；但由于双计随 client 路径而变，HAL 赖以存在的"成本–准确率前沿"的形状被改变了。类似的逻辑适用于任何聚合层。
4. **归档轨迹的可信度本身需要审计**：68% 的 airline 记录里混有 grader 写的动作，意味着任何"从归档轨迹重放/再训练/做行为分析"的下游工作都在用被污染的数据。
5. **re-grade 不是一个中性的维护操作，而是一次新测量**：它的正确性取决于新评估器能否理解旧文件格式与旧环境语义。把"重跑一遍"当作"修复"是危险的——这正是 telecom 上 −82 分的来源。
6. **发布数字但不发布 instrument 的审计接口，等于让读者无法判断数字**：本文提出的四项检查（graded fraction、root-span 成本聚合、动作 provenance 标签、版本钉住的 re-grade diff）本质上是"让 instrument 可被读者独立审计"，是把测量工具本身纳入可复现性讨论。
7. **审计可以在不重跑 agent 的前提下完成**：全部结论仅凭公开产物得出，这把 agent 评估审计的成本压到了极低——这是该工作最具实践价值的方法论贡献。

## 局限性
- **只审计了两个特定榜单**：HAL 与 τ²-bench；结论虽具普适性论证，但样本仅两例，无法覆盖所有 agent 评估流水线的构造方式。
- **τ²-bench 的 re-grade 幅度范围很宽**（airline −7 到 +2.5 分，telecom 最高 −82 分），部分归因不明确；作者未逐一拆解每个任务差异的贡献。
- **离线 re-grade 的正确性依赖"用记录内嵌的 gold"这一约定**：在 gold 与环境不一致时（例如 HAL 从 fork 安装、gold 在 3/50 任务上与 pinned commit 不同），结论可能偏移。
- **Generalist 未评分 episode 的补评可能高估也可能低估**：作者论证它"若有任何偏则是低估"（因为 grader 判过而离线回放判不过的 episode 占分歧的几乎全部），但这是间接论证，不是直接测量。
- **审计本身第一次做错了**：第一次审计漏掉 73 个 episode，规则在讨论页被修正后才给出最终数字。这说明这类审计对规则设计极为敏感——同一份数据、不同规则可得差很大的结论。
- **未提出自动化的审计工具**：给出的是四项"廉价检查"的建议，未提供实现；也未验证这些检查能捕获所有类型的 instrument error。
- **成本双计的检测依赖 tracing span 结构**：论文依赖特定 tracing 库的父子 span 语义，对其他日志栈的适用性未验证。
- **未涉及多模态、多 agent、工具选择等更复杂 agent 形态**；四个暴露点的分析主要基于单 agent + 工具调用 + 模拟用户的 TAU-bench 范式。
- **HAL 维护者的响应"是最好的披露"，但归档数字未变**——即读者看到的仍是旧分数，披露与修复之间存在滞后。

## 适用场景
- **搭建或审阅 agent 榜单/评测 harness 时**：应实现"graded fraction"上报，并保证被评分的 episode 比例在所有 scaffold 间可比。
- **解读任何 agent 榜单的分数前**：先检查"该 scaffold 的 episode 是否总能触发评分"，否则跨 scaffold 比较无意义。
- **从归档轨迹做二次分析或再训练前**：先剥离 grader 注入的动作（68% 的记录受影响），否则下游结论被污染。
- **发布或消费成本–准确率权衡数据时**：成本必须从 root spans 汇总，否则嵌套调用会被重复计数。
- **维护正在演进版本的评测流水线时**：用版本钉住 + re-grade diff 代替"重跑一遍"。

**不适用于**：不提供新的 benchmark 或新方法；不适用于非 agent 的静态基准（暴露面小得多）；也不适用于对已撤回分数做因果解释——本文只能证明 instrument 出错，不能证明哪一方更"好"。
