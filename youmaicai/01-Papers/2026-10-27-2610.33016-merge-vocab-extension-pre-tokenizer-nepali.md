## 核心贡献

> **发现问题**：多语言 LLM 的分词低效瓶颈不在 BPE merge 阶段，而在**预分词正则**阶段 —— 因此靠「扩词表」无法根治。

1. **定位真正的瓶颈**：Llama-3 / Qwen3 的预分词正则其 word 类**只接受 Unicode 字母**；天城文（Devanagari）元音符号是组合标记（combining marks），因此每个元音符号处都会**切断尼泊尔语单词**。
2. **量化代价**：受影响模型在尼泊尔语上的 token 消耗是同等英文文本的 **2.6–5.8 倍**。
3. **证明 merge 扩展的天花板**：对 Llama-3 与 Qwen3，**无论增加多少新 merge，都无法把该溢价降到约 2.2 以下**；已发布的 10 个扩词表方案都已收敛到这个 pre-token 下限的 **4% 以内**。
4. **给出工程修复**：对**已部署的正则做一次小改动**，可**可证明地**保持所有「不含组合标记、不含天城文字符」的文本的 token id 不变。
5. **在持续预训练中验证**：32,000 个新 merge 把尼泊尔语 token 数降到英文的 **1.01 倍**，比标准扩展**少约 54%** 的尼泊尔语 token。

## 技术方案

### 核心思想

**分词效率问题的层级定位**。社区惯常做法是「加 merge」（扩展 BPE 词表），但 merge 只能合并**已被正则切开的片段**。如果切分发生在 merge 之前（预分词阶段），后续任何 merge 努力都只能在碎片上做局部缝合，无法消除根因。

```
文本
 └── 预分词正则 (根因所在)  ← Llama-3/Qwen3: word 类仅接受 Unicode 字母
      │                      天城文元音符号 = 组合标记 → 每个元音处断开
      └── 片段流
           └── BPE merge (社区惯常修法，但已太晚)
                └── 最终 token
```

### 关键数字

| 指标 | 数值 |
|------|------|
| 尼泊尔语 token 溢价（原始 tokenizer） | **2.6–5.8×** 英文 |
| merge 扩展的**不可突破下限** | 约 **2.2×** |
| 已发布 10 个扩展方案收敛程度 | 距下限 **< 4%** |
| 正则修复 + 32,000 merges 后 | **1.01×** 英文 |
| 相对标准扩展节省的尼泊尔语 token | **约 54%** |
| 修复的**可证明安全性** | 不含组合标记/天城字符的文本，token id **完全不变** |

### 可证明性论证

修复是对正则的**小改动**：让 word 类同时接纳组合标记。
- 对**不含**组合标记与天城字符的文本 → 正则行为不变 → token id 逐字节相同（英文因此零风险）
- 对**含**天城文的文本 → 切分点从「每个元音符号」变为「每个真实词」→ token 数大幅下降

### 持续预训练实验

| 设置 | 结果 |
|------|------|
| 模型 | Llama-3.2-1B, Qwen3-0.6B |
| 预算 | 小预算持续预训练 |
| 原始 tokenizer | 在**所有测试配方**下 held-out 尼泊尔语 **bits per byte 最低** |
| 修复 tokenizer（训练步数对齐标准扩展） | Qwen 上**反超**原始 tokenizer；Llama 上**未反超** |
| 数据重复 | 需约 **35%** 数据重复 |

## 实验结论

- **数据集**: 尼泊尔语 + 英文对照
- **基线**: Llama-3 / Qwen3 原始 tokenizer、10 个已发布扩词表方案、标准 merge 扩展
- **结果**:
  - 原始 tokenizer 在所有配方下 bits/byte 最低（即使 token 数最多）
  - 训练步数对齐 + 35% 数据重复后，Qwen 上顺序反转，Llama 上**未**反转
  - **token 节省是否转化为延迟与生成质量的正向权衡 —— 尚未测试**

---

## 局限性

作者自陈的关键空白：

1. **bits per byte 与 token 数背离**：原始 tokenizer 虽 token 数最多，却给出最低 held-out bits/byte。这提示**压缩率本身不是唯一目标**，压缩引入的分布偏移可能损害模型。
2. **跨模型不一致**：修复方案在 Qwen 上有效、在 Llama 上无效 —— 机制尚未解释清楚。
3. **端到端收益未验证**：token 节省对**推理延迟**和**生成质量**的实际影响完全未测。这是本文最重要的未竟问题。

## 实现建议

- **实现难度**: 低（改一行正则 + 标准扩词表流程，代码已开源）
- **预期性能**: 尼泊尔语 token 数降约 54%，理论吞吐收益显著；但**须先自测延迟与质量**
- **适用场景**: 多语言 LLM 的分词器补救 —— 成本极低、收益明确，英文零风险
- **落地注意**: 扩词表后**必须重跑基线对比**，因为本文显示 bits/byte 与 token 数的最优解可能不同

## 我的评注

> 这篇最漂亮的贡献是**「证明某些努力注定无效」**。社区把大量精力投入扩词表，本文用「无论加多少 merge 都降不到 2.2 以下」这一硬下界，把问题从「优化 merge」重新定位到「改预分词器」—— 这是一个**问题重述**级别的贡献，价值高于又一个 5% 的提升。
>
> 但论文自己给出了一个值得警惕的反直觉：**token 数最少的方案 bits/byte 反而最差**。这提醒我们：分词压缩率不能单独作为优化目标。复现时务必两个指标一起看。
>
> 与 [[AdaptTok-Indic]] 是同一问题的两条互补路径：本篇是「零成本的工程修复」，那篇是「学习式的分词器训练」。两篇同批次出现，说明 Indic 分词低效已成独立研究热点。
