## 核心贡献
1. **刻画了 looped transformer KV cache 的三条独有性质**（在 Ouro-1.4B 上实测）：(P1) 量化敏感度取决于 **(loop, layer) 单元格**而非仅仅 layer——72 个 cell 中前 19 个占据总损伤的一半，各 cell 损伤近似可加（14 个方案上 cell 损伤之和与实测 KL 的相关系数 0.98，Spearman 秩相关 0.95）；(P2) **靠后的 loop 对 KV 共享更宽容**（loop 3 的 24 层中有 21 层共享末 loop KV 的损伤比存 INT2 更小，loop 2 中 6 层如此，loop 1 中 0 层）；(P3) **误差沿 loop 累积**——Quest 式 page dropping 在 Ouro-1.4B 四个 loop 全开时造成 1.82× 单 loop 损伤之和，而普通模型（Qwen2.5/Qwen3）仅 0.95–1.17×。
2. **LoopKV 设计：把每条性质转成一个机制。** C1 = 按 cell 混合精度分配；C2 = 跨 loop KV 共享作为 per-cell 选项（规划器自行决定谁共享）；C3 = 读取时注意力感知的 V 精度。三者由**单个 fused CUDA kernel** 执行，整个 decode step 作为一个 CUDA graph 重放，把 LoopKV-M 的 host launch 从 **504 降到 17**。
3. **离线规划器**：以每个 cell 的 KL 损伤 profile 为输入，解一个带双资源约束（损伤预算 ε、存储预算 M）的**多重选择背包**，精确求解（字节代价均为 0.5 KiB 倍数，可动态规划精确解出）。产出两个端点方案：LoopKV-R（读优化，损伤预算 1.19×KL_share，无存储约束）与 LoopKV-M（内存优化，损伤预算 2.0×KL_share，存储预算 156 KiB/token）。
4. **C3 的关键洞察**：LoopKV 总是完整读取 K（attention 本来就要读），因此在读 V 之前就已经知道每个 token 的 attention score，**无需预测器、无需额外 pass、无需额外字节**就能决定哪些 token 的低 2 bit plane 需要读取。其规则为"$s_j < m - \tau\ln 2$ 则判冷"（$\tau=14$），冷 token 只读高 2 bit 并解码到桶中点 $\hat c = 4hi + 1.5$。
5. **同等字节下显著优于 skip 策略**：LoopKV 式读取（低注意力 value 用 2 bit 读而非跳过）比 Quest 式跳过造成的损伤小 **4.7×**（两者都读 85% 的远端字节）。
6. **服务性能**：Ouro-1.4B / 2.6B / Dory-4B 上，LoopKV-M 在 16K 上下文、16K 上达到 vLLM BF16 cache 解码吞吐的 **1.13–4.44×**；单张 RTX PRO 6000 上 LoopKV-M 达 BF16 goodput 的 **8.0×**、KIVI-4 的 **2.0×**；相对 KIVI-4（同一 fused kernel + CUDA graph）少存 **35%** KV，goodput 达 **1.7–2.2×**。
7. **精度无损**：六个公开 suite（RULER-16K/32K、LongBench、MATH500、GSM8K、AIME+MATH-L5）上，LoopKV 任何平均分**均未显著低于 BF16**（差值下界 > −3pp 为非劣判据）；反向的 naive baseline（loops 1–3 统一 INT2、末 loop KV 全局复用）则显著掉分——末 loop 复用甚至让 RULER-16K 从 71.44 掉到 **4.14**，MATH500 从 84.5 掉到 **47.0**。

## 问题背景
Looped transformer 把同一层块对每个 token 反复应用 $T$ 次，用参数量换等效深度。Oouro-1.4B 用 $T=4$、$L=24$、16 个 128 维 KV head、无 GQA，每 token 存 **768 KiB** BF16 KV，是同层数 dense 模型的 4 倍；每个 decode step 还要把 2.5 GB 权重重读 4 遍。Huginn-3.5B 把 4 层核心迭代 $r=32$ 次，计算量等效 50B 模型；Mixture-of-Recursions 让每个 token 自选 loop 次数。

问题出在内存带宽的"两难"：更大的 batch 能摊薄权重重读，但 batch 上限由 KV 池除以每请求存储量决定。在 BF16 峰值吞吐下（Ouro-1.4B，8K 上下文），**KV cache 占每 decode step 读取字节的 84%**。因此压缩 KV 同时抬升 batch size 和解码速度，是提升 goodput 的关键。

已有工作的问题：FP8、KIVI、KVQuant、rotation 系列都把每个 loop 当成"又一层"，用同样的比特数；专门针对 looped 结构的两篇并发工作（FlashLoop、ResidualQuant）虽然利用了 loop 结构，但都是**按 loop 分配精度**，把 loop 内所有层一视同仁。而实测显示 loop 内不同层敏感度差异巨大（Ouro 上 4 个中间层 7、8、10、11 的敏感度平均是其他层的 4.9×，占据总损伤一半）。此外，looped 结构还带来两个新问题：靠后 loop 的 KV 是否收敛到可以共享？以及一个 loop 引入的误差会不会被后续 loop 放大？论文的回答是二者都是，且答案必须 per-cell 给出。

## 方法
### 1. 解码内存模型
looped transformer 的 decode step 时间：

$$t(B) = t_{\text{fix}} + \frac{W_T + B \cdot D_{\text{read}}}{BW}$$

其中 $W_T$ 是每步重读 $T$ 遍的权重字节，$D_{\text{read}}$ 是单请求每步读取的 KV 字节，$BW$ 为有效带宽。batch 受 $B \le (\text{KV pool})/D_{\text{stored}}$ 限制。关键在于**"存储量"与"读取量"是两个可分离的优化目标**——共享、残差编码、V 精度都让二者脱钩。在 RTX PRO 6000 上 $W_T = 10.07$ GB，线性拟合得 $BW = 1.29$ TB/s、$t_{\text{fix}} = 6.84$ ms，该公式能预测被测量化格式峰值吞吐的 ±3%。

### 2. 损伤度量与 C1：per-cell 混合精度分配
损伤用精确模型与策略模型间的 KL 散度度量，单位为 $KL_{\text{share}}$（最廉价的整 loop 共享所产生的 KL）。sink（32 token）与近期窗口（256 token）始终保持 BF16。所有测量在 fp32 激活下进行（BF16 舍入噪声本身已产生约 $KL_{\text{share}}$ 一半的 KL，会掩盖 cell 间差异）。

对每个 cell $c=(t,\ell)$，profile 测三种选项 $o$ 的单 cell 损伤 $d_{c,o} = KL(p_{\text{exact}} \| p_{c\leftarrow o})$：4-bit 码、2-bit 码、指向末 loop 的 KV 指针（其余 cell 保持精确）。Oouro-1.4B 上 72 个 cell × 3 选项 + 24 个源 cell，约 **3 GPU 小时**完成 profile；16 篇文档的两半给出的 cell 排序秩相关 0.985（profile 稳定）。

分配问题：

$$\min_x \sum_{c,o} x_{c,o} r_o \quad \text{s.t.} \quad \sum_{c,o} x_{c,o} d_{c,o} \le \varepsilon, \qquad \sum_{c,o} x_{c,o} s_o \le M$$

其中 $r_o, s_o$ 为选项 $o$ 的读/存字节，$x_{c,o}\in\{0,1\}$，$\sum_o x_{c,o}=1$。KIVI 风格编码（key 按通道、value 按 token 分组 32，带 fp16 scale 与 zero point）的 own INT4 存/读 2.5 KiB per token per layer，own INT2 为 1.5 KiB。loop 4 固定为 INT4（单独把它降到 INT2 就已经花掉 $5.8 \times KL_{\text{share}}$），故其成本在所有方案中是常数。

### 3. C2：跨 loop KV 共享作为 per-cell 选项
共享 cell $(t,\ell)$ 用**自己的 query** 去 attend 末 loop 同 layer 的历史。其 descriptor 指向末 loop 的 pool，因此不存自己的副本，但 sink 与 window 仍归自己且保持精确。当一个 32-token page 离开窗口，cell 释放自己的副本，转而读取末 loop 对应位置的 page。共享节省存储但不节省读取，因此只有在存储预算成为约束时背包才会选中它。

实测细节：共享在靠后的 loop 便宜（loop 3 有 21/24 层共享比 INT2 更少改变预测；loop 1 每个 cell 共享比 loop 3 大约改变 4 倍预测）。这不能靠"对齐 loops"挽回——它们的 key 范数几乎相等但方向不同，MiniCache 式范数校正只恢复 2.7% 的共享 KL。

### 4. C3：注意力感知的 V 精度
**位平面布局**：key 总是完整读取，保持单平面；INT4 cell 的 value 码 $c\in\{0,\dots,15\}$ 存成两个连续 2-bit 平面 $hi=\lfloor c/4\rfloor$ 与 $lo = c \bmod 4$，后接 scale 与 zero point。存储字节数与普通 INT4 相同；跳过某 token 的 lo 平面每 token per layer 省 0.5 KiB 读取。

**读取时决策**：kernel 先读所有 key code，因此到达 value 时已经知道该 query 在该 loop 下对每个 token 的 score $s_j$，无需任何 predictor、额外 pass 或额外字节。理想规则为 token $j$ 冷当且仅当 $s_j < s_{\max}-\tau\ln 2$；由于 $s_{\max}$ 在整行完成前不可知，kernel 流式扫描整行并与运行最大值 $m \le s_{\max}$ 比较（种子 $m_0$ 取自 sink 精确 key 的最大 score，near block 本来就要算；因为它只是行最大值的下界，只会降低阈值，故流式规则绝不会把理想规则判热的 token 误判为冷）。

**误差界（Proposition 1）**：设 $a_j$ 为某行某 head 的归一化注意力权重，$C$ 为被判冷的 token 集合，$\sigma_j$ 为 token $j$ 通道组的 V scale，则相对"读取所有双平面的 INT4 reader"：

$$\|\Delta o\|_\infty \le 1.5 \sum_{j \in C} a_j \sigma_j \le 1.5 \sigma_{\max} |C| 2^{-\tau} a_{\max}$$

**looped 结构特有的机会**：LoopKV 把每个 value 只存一次完整 INT4，由每个 loop 在**读取时**自行决定读多少位。若预先固定精度，就必须让任何 loop 判热的 token 都保持全精度——Ouro-1.4B 上 loop 3 与 loop 4 判热的 token 只有 **83% 重叠**，四个 loop 全局固定精度会读 **1.6×** 的 lo 平面字节。在两个方案中，V 精度把每 loop 的历史 V 读取的 17–22% 保持在全精度，并把每 token 读取量削减 13–14%（LoopKV-R 215→186 KiB，LoopKV-M 220→189 KiB）。$\tau=14$ 时只把 KIVI-4 在 Ouro-1.4B 上的 fp32 KL 改变 1.016 倍；$\tau=10$ 时已是 1.35 倍。

### 5. 统一 kernel
一个 page 存某 cell 的 32 个 token。INT4 page 的 key 为交错 4-bit 码，value 为原 V 矩阵的两个位平面；INT2 page 存自己的 2-bit 码；共享 cell 不存 page，descriptor 指向末 loop 的对应 page。每 cell 一个 descriptor（载入 plan 时构建，常驻 device memory），携带三项设计信息：读哪个 pool（C2）、存多少 bit（C1）、是否读 lo 平面（C3）。

CUDA launch grid 每 decode row 最多 8 个 near thread block + 64 个 far thread block。near block 对 sink 与 window 算精确 BF16 attention，发布部分结果与 sink 最大值；far block 通过 descriptor 读自己的 history page 份额，用发布的最大值作为 V 精度种子。为避免长等待，far block 只在 4 μs 内收到时采用发布最大值，否则种子设为 $-\infty$（此时所有 token 判热，故假阳性不造成精度损失）。行内最后一个 block 用 log-sum-exp 精确合并所有部分结果（这给出精确 softmax），因此**一次 launch 取代每层最多 4 次调用**。因 descriptor 与所有 buffer 地址固定，整个 decode-only step（含四个 loop 的 96 次 attention launch）作为一个 CUDA graph 重放；窗口退出量化（page 列表依赖数据）在重放前执行。

### 6. vLLM 集成
LoopKV 是 vLLM 0.26 的插件，不改引擎本体。每个 loop 拥有独立 KV-cache group，从 vLLM 的 KV 预算中划出 history pool，载入时把 plan 表转成 96 个 descriptor。page 离开窗口时，Triton KIVI codec 将其量化进对应 cell 的 pool 并释放 BF16 block。history reader 以 1.59–1.63 TB/s 流式读取 KV 码，与 FlashAttention-2 在同 GPU 上读 BF16 相当；带 V 精度时 reader 比普通 INT4 reader 快 1.12–1.17×。

## 实验结果
- **Dataset/Task**: 服务质量在六个公开 suite 上评测——RULER-16K 与 RULER-32K（官方 RULER，13 个任务各 100 项）、LongBench v1（16 个英文与代码子集）、MATH500（前 200 项，greedy，8K 输出上限）、GSM8K（1,319 项，3-shot）、AIME + MATH level 5 采样长推理。服务性能在 Ouro-1.4B / Ouro-2.6B / Dory-4B 上测，Huginn-3.5B 用于规划结果。GPU：NVIDIA RTX PRO 6000 / RTX PRO 4500 / A100-80 / H100 SXM 80GB。
- **Main results**:
  - 吞吐（RTX PRO 6000）：LoopKV-M 在 8K/16K 上解码 **575.9 / 301.9 tok/s**，为 BF16 的 **3.37× / 3.39×**；LoopKV-R 在 8K 达 **550.2 tok/s**（3.22× BF16）。A100-80 上 LoopKV-M 相对 BF16 为 2.2×（8K）、2.2×（16K）、4.7×（32K），相对 uniform INT4 为 1.21–1.30×。H100 上 LoopKV-M 相对 BF16 为 2.69×（8K 与 16K），KIVI-4 为 2.27×/1.96×，FP8 为 2.08×/2.05×。
  - Goodput（SLO：TTFT ≤ 10 s，TPOT ≤ 3$\tau_0$，$\tau_0=18.60$ ms）：LoopKV-M 相对 KIVI-4 为 **2.00× / 1.72× / 2.20×**（三次运行）；相对 KIVI-4+V 为 1.60×/1.72×/1.83×；相对 BF16 达 8.0×、相对 FP8 达 2.5×。LoopKV-R 相对 KIVI-4 为 1.3–1.6×。
  - 存储：LoopKV-M 比 KIVI-4 少存 **35%** KV（155 vs 约 240 KiB/token）；16K 上下文下峰值 batch 24 vs KIVI-4+V 的 14。
  - 精度（Ouro-1.4B，Table 1）：

    | 方法 | RULER-16K | RULER-32K | LongBench | MATH500 | GSM8K | AIME+MATH-L5 |
    |------|-----------|-----------|-----------|---------|-------|---------------|
    | BF16 | 71.44 | 54.04 | 25.29 | 84.5 | 76.6 | 70.6 |
    | LoopKV-M | 72.12 | 53.63 | 25.19 | 86.0 | 77.1 | 71.1 |
    | LoopKV-R | 72.49 | 53.86 | 25.32 | 84.5 | 76.6 | 70.3 |
    | KIVI-4 + V | 71.37 | 54.57 | 25.25 | 84.5 | 76.9 | 72.0 |
    | INT2, loops 1–3 | 65.50 | — | 24.43 | 86.0 | 77.0 | 69.3 |

- **Ablations**:
  - 三个贡献各自买什么：C1（分配）削减 **10%** 读取（KL 从 0.46× 升到 0.87× $KL_{\text{share}}$）；C2（共享）在更大损伤预算下削减 **28%** 存储、resident batch 从 36 升到 48；C3（V 精度）在 KL 不变下削减 **14%** 读取。融合 + graph 主要买延迟而非峰值吞吐：host launch 504 → 17，batch-1 解码加速 1.07–1.19×（8K/16K），峰值处仅 0.5–2.5%。
  - 限制背包每层只一个选项（layer-wise allocator 的做法）在同等字节下 KL 升高 **1.52×**（read-optimized 字节点）与 **1.43×**（memory-optimized 字节点）。
  - 手做的最优 per-loop 方案与 LoopKV-R 相比：KL 低 **42%**、吞吐高 5%；LoopKV-M 再少存 14%、再快 6%。
  - 同等存储下手工方案（LoopKV-M 存储量）的 fp32 KL 是其 **2.3×**（4.21 vs 1.80）。
  - 与 codec 基线比较：读取少于 216 KiB 的方法中（TurboQuant-3.5、KVQuant-3b）没有一个能在该实现下达到 read-optimized 方案（LoopKV-R）的 KL。
  - H100 上 V 精度**不加速**（reader 受延迟与指令数而非带宽限制，读取字节少 17% 但速度不变）——这是一个重要的可移植性负面结果。
  - FlashLoop 官方代码在 H100 上对同批 RULER-16K 项比其 dense 路径掉 **12.75 分**，主要在 variable tracking 与 multi-key needles 上。
  - 32 GB RTX PRO 4500、32K 上下文：LoopKV-M 常驻 4 个请求 vs uniform INT4 的 2 个，比 KIVI-4+V 快 29%（等 batch 下仅 3–4%）。

## 关键洞察
1. **"按 loop 分配精度"是错的粒度，必须按 (loop, layer) 单元格。** 这是本文最有复用价值的洞察：不只循环结构，量化/剪枝/缓存策略的分配粒度应当对齐"真正会独立放大误差的最小单元"。约束限制粒度会让 KL 升高 1.43–1.52×。
2. **cell 损伤近似可加（相关系数 0.98）**，这使得"一次性离线 profile + 背包规划"成为可行工程路线——不需要搜索联合方案，一次 profile 就能预测任意方案的总损伤。这条经验规律（可加性 → 可预测 → 可规划）可以推广到任何"多组件独立退化"的系统。
3. **"谁最敏感"是模型特定的，不能跨模型迁移规则**：Oouro 上 loop 1 最敏感，Dory 与 Huginn 上却是最后一个 loop 最敏感。因此任何"按 loop 序号"的启发式都需要 per-model 校准。
4. **读全部 K、只裁剪 V 的位平面，是把"注意力稀疏"变成免费带宽节省的通用技巧。** 因为 attention 本来就要读 K，score 免费得到，从而可以在读 V 之前精确决定精度——这与所有需要 predictor/额外 pass 的近似重要性估计方法形成对比。其误差还有干净的闭式界（Proposition 1）。
5. **looped 结构天然适合"运行期按读取方决定精度"**：不同 loop 关注不同 token（loop 3 与 4 的 attention Jaccard 仅 0.83），只有 83% 的 hot token 重叠；这在非循环模型里不存在，是循环结构独有的带宽红利（固定精度方案要读 1.6× 的 lo 字节）。
6. **在 looped 模型上，"跳过低注意力值"比"低精度读取"差得多**（同等字节下损伤 4.7×），原因是每个 loop 重复注入近似相同的误差并跨 loop 累积。这是"重复计算结构"改变稀疏注意力最优策略的一个反直觉结论。
7. **省下来的 KV 存储本身就是吞吐**：机制分析显示增益主要来自"能多常驻几个请求"（16K 下 batch 24 vs 14），而非单请求读取更快。这提示评估 KV 压缩方法时必须同时报告吞吐与 SLO goodput 两个口径。
8. **工程上"单 fused kernel + 整 step CUDA graph"的收益主要在延迟而非峰值吞吐**（batch-1 加速 1.07–1.19×，峰值仅 0.5–2.5%），但它使 SLO goodput 成为可达目标。

## 局限性
- 依赖具体架构假设：共享仅在"末 loop"上验证过，循环数 $T>4$（如 Huginn 的 $r=32$）时 plan 的规模与 profile 成本（3 GPU 小时 / 72 cell）线性膨胀，论文未给出 Huginn 的服务结果。
- profile 需要 fp32 激活下跑 16 篇模型自身的长生成，约 3 GPU 小时；对需要频繁换模型或改 loop 数的部署流程不可行；且 profile 只在自身生成分布上有效，分布漂移后的预测力未验证。
- H100 上 V 精度（C3）完全无加速收益，说明该机制在带宽充裕但延迟/指令受限的 GPU 上可能白做——对不同硬件的迁移性存疑。
- 精度评测全部在 ≤32K 上下文、Ouro/Dory/Huginn 这类 looped 模型上做；未验证在标准（非 looped）模型上退化后的行为，也未验证极长上下文（>32K）。
- "非劣于 BF16"的判据是 suite 平均值下界 > −3pp，是聚合口径；LoopKV-R 在 MATH500 上的区间达到 −4.0 点（200 项），尾部风险被平均掩盖。
- 端到端收益高度依赖内存是否成为瓶颈：在 32 GB 卡上等 batch 下优势仅 3–4%；在非 looped 模型上收益结构会不同。
- 与 FlashLoop / ResidualQuant 的比较主要在质量与每 token 存储字节上做，因为两者无 vLLM 实现；其吞吐/延迟特性无法直接比较。
- 融合 kernel 与 graph replay 的正确性只在"decode-only step"上验证；prefill、多步交互的路径未系统评测。

## 适用场景
- **适合**：部署 looped transformer（Ouro、Mixture-of-Recursions 风格、Huginn 式循环核心）时的 KV cache 压缩，尤其在 GPU 显存紧张、需要最大化常驻 batch 与 SLO goodput 的场景；模型固定、可承受一次性离线 profile 的生产环境；需要在质量与吞吐之间做可控权衡的服务（LoopKV-R 保长上下文追踪能力，LoopKV-M 压存储）。
- **不适合**：非 looped 的标准 dense/MoE 模型（本文的三条性质与三条机制均不适用）；模型或 loop 结构频繁变动的场景（profile 成本摊不薄）；H100 类"带宽充裕但延迟受限"的硬件（V 精度无收益）；要求逐样本零质量损失且不能接受 −3pp 聚合口径的合规场景。
