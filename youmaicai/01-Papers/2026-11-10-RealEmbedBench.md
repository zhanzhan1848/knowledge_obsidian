## 核心贡献

> 推出 **RealEmbedBench**：一个覆盖 5,142 个样本的**应用层**嵌入式软件基准，聚焦现有基准普遍忽略的三类能力——真实项目上下文中的代码生成与补全、跨表征的状态机建模与实现、以及跨操作系统（RTOS）代码翻译。

1. **三类任务**（共 5,142 样本）：① 上下文感知的代码生成（1,426）与代码补全（3,026）；② 状态机建模与实现（80，跨自然语言规格 ↔ PlantUML 模型 ↔ 可执行代码三种表征）；③ 跨 OS 代码翻译（610，覆盖 6 个嵌入式 OS、26 个有向翻译对）。
2. **六大 LLM 系统评测**：CodeGen 的 CodeBLEU 分数从 **0.4823 到 0.7076**，CodeComp 从 **0.4756 到 0.6915**——模型选择影响巨大。
3. **三条关键发现**：(a) 项目上下文（尤其局部代码窗口）对生成与补全有显著影响；(b) 模型"会建模状态机但不会把它变成可执行代码"；(c) 跨 OS 翻译存在**强方向依赖**，Harmony → RT-Thread 方向平均通过率仅 **0.1667**。
4. **面向从业者的可操作结论**：用 LLM 写嵌入式代码必须提供本地代码上下文；跨 OS 翻译要按方向选模型；模型训练方应补充真实的状态机实现数据。

## 技术方案

### 核心思想
既有嵌入式基准（如 EmbedAgent）主要做硬件在环的仿真验证，几乎不触及硬件抽象层之上的应用层软件，而这正是嵌入式开发的主要工作量。RealEmbedBench 的构建遵循"从真实项目采样"的思路。**代码生成/补全**部分：先从真实嵌入式项目中提取函数池，做函数级分层抽样（按 LOC 分五个区间，目标比例 20%/30%/30%/15%/5%，配额不足时按比例重分配），再为每个函数抽取上下文——因为静态分析会漏掉宏、条件编译与项目特定构建配置引入的依赖，作者安排两名评审**人工复核**，补回 320+ 处被静态分析遗漏的上下文项、移除 130+ 个样板函数；随后用 DeepSeek-v3.2 基于函数与上下文生成功能性意图描述得到 1,426 条生成样本；补全任务则施加两级遮蔽（token 级用于短程补全、block 级用于较大语义单元），遮蔽位置随机，得到 3,026 条样本。**状态机**部分：先用启发式静态分析搜索符合常见状态机实现模式（如含显式主循环）的代码片段，再人工确认；把样本拆成"主循环代码"与其"单层依赖上下文"，然后用 DeepSeek-v3.2 **反向**推导对应的 PlantUML 模型与自然语言需求；两名评审核对三种模态的对应关系并修正（模型-需求不一致、缺失边界条件等），修订后**三模态一致性超过 98%**。**跨 OS 翻译**部分：先调查社区讨论统计出最常被提及的六个 OS（FreeRTOS 18 次、Unix 13 次、Zephyr 15 次、RT-Thread 11 次、NuttX 9 次、HarmonyOS 7 次），再构建平行语料；为每个翻译对用 DeepSeek-V3.2 生成测试输入，在 Ceedling 环境中**实际执行**源实现与译文，以动态检查而非语法相似度来判定语义等价。

### 关键公式
```math
\text{CodeGen/CodeComp: } \mathrm{CodeBLEU}=\frac{1}{4}\big(\mathrm{BLEU}+\mathrm{ngram}+\mathrm{SF}+\mathrm{ES}\big)
\quad\text{(四个子指标等权)}

\text{Token-level completion: }\ \mathrm{EM}(\hat{t}, t)=\mathbb{I}[\hat{t}=t]
\quad\text{(短预测不适用 CodeBLEU)}

\text{State machine metrics: }\ \mathrm{Syntactic\ Validity},\ \
\mathrm{State\ Coverage}=\frac{|\text{正确覆盖状态}|}{|\text{参考状态}|},\
\mathrm{Transition\ Coverage}=\frac{|\text{正确覆盖转移}|}{|\text{参考转移}|}
```

### 关键组件
- **三类任务形式化**：代码生成 $c=\arg\max_c P(c\mid d, \mathcal{C})$ 与补全（两级遮蔽）；状态机跨表征变换（NL ↔ PlantUML ↔ code）；跨 OS 语义等价翻译（带可执行测试用例）。
- **函数级分层抽样**：按 LOC 五区间 20%/30%/30%/15%/5% 配额，配额不足按比例再分配。
- **人工依赖复核**：两名评审补回 320+ 遗漏依赖、移除 130+ 样板函数——静态分析不可替代的部分。
- **DeepSeek-v3.2 作为数据构造器**：生成函数意图描述、反向推导 PlantUML 与自然语言需求、生成翻译测试输入。
- **三模态一致性校验**：两名评审核对源码/PlantUML/自然语言需求的一致性，修订后一致性 > 98%。
- **动态可执行验证**：Ceedding 环境执行源与译文实现做语义等价判定。
- **六个被测 LLM**：DeepSeek-V3.2（671B）、Qwen3-235B-A22B-Instruct、GPT-5.2 等五个大规模通用模型 + 一个（论文另列）模型。
- **评测设置**：temperature 0.95，最大上下文窗口 8192 token，任务特定 prompt 模板随代码发布。

## 实验结果

| 基准/指标 | 结果 |
|-----------|------|
| 数据集总量 | **5,142** 样本（1,426 生成 + 3,026 补全 + 80 状态机 + 610 跨 OS 翻译） |
| 代码生成 CodeBLEU 区间 | **0.4823 ~ 0.7076**（六模型跨度） |
| 代码补全 CodeBLEU 区间 | **0.4756 ~ 0.6915**（六模型跨度） |
| 代码平均长度 | 56 LOC；平均 4.93 个调用依赖、3.91 个全局变量依赖、3.98 个类型依赖 |
| 状态机样本特征 | 平均 **7.73 个状态**、**14.05 条转移** |
| 跨 OS 覆盖 | 6 个嵌入式 OS、**26 个有向翻译对** |
| 最差翻译方向 | Harmony → RT-Thread，平均通过率 **0.1667** |
| 三模态一致性 | **> 98%**（人工复核后） |
| 状态机任务 | 模型在"建模"上表现尚可，但从模型转成可执行代码时明显不足；最佳结果分散在不同模型，无单一模型全面占优 |
| 跨 OS 错误模式 | 语义粒度不匹配、参数解释错误、遗漏目标侧隐式行为约束（API 行为、参数用法、返回条件）——代码表面合理但行为错误 |
| 上下文消融 | 邻近代码上下文带来最一致的收益；项目上下文（尤其局部代码窗口与调用链信息）对生成与补全影响显著 |

## 局限性

- 状态机样本仅 80 条，统计功效有限；跨 OS 翻译 610 条覆盖 26 个方向，单方向样本量不大。
- 代码生成/补全基于**函数级**任务，无法评估跨文件、跨模块的长程重构能力。
- 依赖 DeepSeek-v3.2 构造意图描述、PlantUML 模型与需求规格，构造模型自身的偏置会传导进基准。
- 静态分析 + 人工复核的依赖抽取仍有覆盖不足风险（宏、条件编译场景）。
- 被测模型中包含闭源前沿模型，其版本漂移会使历史分数不可复现。
- 跨 OS 任务仅覆盖 6 个 RTOS，未包含裸机、Linux 嵌入式或 .NET/嵌入式等生态。
- 评测只用 CodeBLEU 与 EM，未引入编译通过率或功能测试来评估生成与补全（与状态机/翻译任务的严格程度不一致）。

## 建议

- **是否推荐使用**：是（作为嵌入式 LLM 能力的评测基准与选型参考）
- **适用场景**：嵌入式/RTOS 开发中评估与选型 LLM；设计"上下文增强"提示策略；构造嵌入式领域 SFT/RLVR 数据（尤其是状态机实现数据）；跨 OS 迁移项目的模型选型。
- **值得复现**：是（数据与代码公开，构造流程完整可复现；是少见的覆盖"应用层嵌入式"的 LLM 基准）
