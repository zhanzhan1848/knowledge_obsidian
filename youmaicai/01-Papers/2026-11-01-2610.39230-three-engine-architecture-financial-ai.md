# Beyond LLM Wrappers: Context Engineering and the Three-Engine Architecture for Reliable Financial AI

## 摘要
本文提出面向金融决策 AI 的 **三引擎架构（three-engine architecture）**：财务知识图谱（持久化企业记忆、关系、provenance、时态状态）、确定性优化引擎（可复现的付款排程、现金分配、供应商优先级、折扣捕获计算）、多智能体 LLM 层（意图解析、任务形式化、解释生成、对结构化 ground truth 的校验）。论文的核心创新不是三个引擎本身，而是把三者协调起来的 **context engineering** 层：为每个查询选择、排序、组装、校验并**预算**来自异构数据源、工具、租户和决策目标的上下文。作者基于 **15 个生产部署、约 11 个月**的经验报告：单智能体 pipeline 的幻觉率约 **7–9%**（按查询类型 5–10%），迁移到图谱支撑的多智能体校验后降到 **1% 以下**；ERP 数据质量与租户异质性是实施的主要成本；从项目启动到上线的时间由约 **6 周**降到约 **2 周**。

## 核心贡献
1. **三引擎架构**：把"确定性计算"与"结构化事实"从 LLM 中外置，明确划定各引擎的职责边界（LLM 决定算什么，确定性引擎负责算）。
2. **context engineering 概念**：区别于标准 RAG 的领域特定协调层，覆盖实体解析、子图选择、时态过滤、租户适配、上下文预算、校验与审计。
3. **生产证据**：15 个部署、11 个月的可观测指标（幻觉率从 ~7–9% → <1%，部署周期 6 周 → 2 周）。
4. **四层审计轨迹**：data lineage、process provenance、decision rationale、temporal validity。

## 方法与架构
**四类需求分析**（决定了单引擎方案必然失败）：① 对关系的 contextual reasoning；② 确定性计算；③ 自然语言交互；④ 可审计性。能力矩阵：

| Engine / System | Contextual Reasoning | Deterministic Math | Persistent Context | Natural Language |
|---|---|---|---|---|
| LLM alone | ✓ | × | × | ✓ |
| Knowledge graph alone | × | × | ✓ | × |
| Optimization solver alone | × | ✓ | × | × |
| Rules-based system | × | ✓ | × | × |
| **Three-engine architecture** | ✓ | ✓ | ✓ | ✓ |

**引擎 1：财务知识图谱**。节点包括组织、法人实体、业务单元、供应商、客户、发票、付款、采购订单、合同、税负、银行账户、日记账、用户；关系包括 "issued by"、"owed to"、"paid by"、"matched to"、"governed by"、"belongs to entity"、"has tax code"、"depends on"、"part of customer group"。每个节点/关系带属性、时间戳、源元数据与转换历史。提供三项能力：多跳推理（如 vendor → invoice → PO → goods receipt → dispute）、时态上下文、source attribution。图谱设计必须 **LLM-aware**（如关系标签用 `HAS_OPEN_INVOICE` 而非隐晦的 join 表名；vendor 节点带 normalized name、aliases、criticality、payment behavior summary、source identifiers）。

**引擎 2：确定性优化层**。接收图谱与租户配置的结构化输入，构造决策变量、目标函数与约束，返回可复现结果。solver 可为 OR-Tools、Gurobi、CPLEX；**部署中主要使用 OR-Tools**。典型问题：付款排程（在现金可用性、到期日、payroll reserve、税负、战略供应商约束、政策规则下最大化折扣捕获与供应商可靠性）、催收优先级排序、现金流情景分配。

**引擎 3：多智能体 LLM 层**。五类专责 agent：query analysis（分类意图、识别实体、检测隐式时间窗、决定需要哪些引擎）、context assembly（图谱检索、选遍历深度、过滤、生成模型可读证据）、optimization invocation（构造 solver 输入）、response generation（生成面向用户的解释）、validation（对照结构化 ground truth 校验断言）。校验必须是具体的：entity validation、numerical validation、temporal validation、constraint validation、source validation、feasibility validation——"这看起来对吗"式的模型批评不够。

**Context engineering 的定义**：给定用户查询、租户配置、财务知识图谱、可用计算引擎、适用政策约束与上下文窗口预算，产出一个 **context package 与 execution plan**，在准确性、完整性、时效性、访问控制与预算约束下最大化决策相关信息。context package 可含图谱记录、关系路径、聚合指标、历史快照、source 引用、solver 输出、租户政策参数、校验结果与响应约束；execution plan 可规定"先解析实体 → 再检索未付发票 → 再跑优化模型 → 再对选定发票与 solver 结果校验生成解释"。

**查询类型分类**：lookup / explanation / optimization / scenario / hybrid，决定引擎路由。相关性是多维的：金额、紧迫度、合规风险、关系重要性、运营依赖、时态状态、政策优先级——语义相似的发票若已支付、属其他法人、超出时间窗或无权访问，则不相关。

**端到端示例**："Can we pay the critical vendors due this week without touching payroll reserve?" → 分类为受限付款优化 → 抽取时间窗，识别 "critical vendors" 为租户政策类别、"payroll reserve" 为流动性约束 → 检索未付发票、供应商关键度、折扣窗口、银行余额、payroll reserve 政策、税负、近期付款冻结 → 构造付款决策变量、现金与 reserve 约束、平衡逾期风险/折扣捕获/供应商关键度的目标 → solver 返回可行排程或不可行说明 → response agent 解释 → validation agent 逐项核对金额、供应商、发票、到期日、约束 → 全链路写入审计轨迹。

## 实验设置
本文为**架构 + 生产观察**研究，非受控实验。设置：
- **部署规模**：从 150+ 客户基数中选出的 **15 个生产部署**，跨度约 **11 个月**，行业覆盖制造、SaaS、服务、电商、贸易。
- **ERP 集成**：Zoho、Tally、QuickBooks、Acumatica。
- **规模**：每次优化查询涉及约 **50–500 张发票**；图谱规模从数万到超过一百万节点。
- **LLM provider**：生产部署主要使用 **Gemini**，架构同时针对开源模型评测过；架构声明 model-agnostic。
- **幻觉率度量**：对约 **500 条** AI 生成建议做人工标注评测（工程师 + 财务用户共同评审，并用自动化校验辅助）；只要任一断言（供应商身份、发票金额、付款条件、税码、计算总额）不被源记录支持即判为含幻觉。
- **部署指标**：hallucination rate、validation failure rate、entity resolution accuracy、solver feasibility rate、context sufficiency、time-to-live、user adoption。

## 实验结果
| 观察项 | 单智能体阶段 | 图谱支撑的多智能体校验后 |
|---|---|---|
| 含至少一处无依据断言的响应 | 约 36–43 / 500 | 约 4–5 / 500 |
| 幻觉率 | 约 7–9%（按查询类型 5–10%） | < 1% |
| 优化类查询 | 更高（更易生成无依据总额） | 剩余问题多为校验失败/缺上下文/数据质量例外 |
| 部署周期（kickoff → 上线） | 早期约 6 周 | 后期平均约 2 周 |

其他生产观察：① **ERP 数据质量**比 AI 建模更耗人力——供应商名跨系统不一致、重复供应商、付款条件为自由文本、日期/币种不一致、税码缺失或复用、源记录不完整、历史更正不同步；② **行业上下文差异显著**（制造要 PO/收货/库存/关键度，SaaS 要订阅/递延收入/流失风险，服务要项目里程碑/工时/未开票工时，电商要库存周转/平台结算/退款/支付网关时序，交易业务要币种敞口/供应商信用/客户预付/发货状态）；③ 用户看重**解释与可追溯性**而非仅推荐；④ 人类复核仍需保留（实体歧义、源记录缺失、不可行优化、大额付款、合规不确定、校验失败须升级人工）；⑤ **context policy 比 prompt wording 更重要**——最大可靠性收益来自更好的检索、图谱结构、校验与租户特定上下文组装；⑥ 最有用的复盘方式是 **trace-based review**（完整 trace 而非只看最终响应）。

## 局限性
- 作者自述：证据为**观察性而非随机对照**，<1% 幻觉率是特定条件下的生产观察而非普适基准；样本仅 15 例且按数据成熟度选择，可能高估效果；系统强依赖数据质量（缺失的源 truth 无法凭空制造）；不证明架构最优，也不隔离各组件的因果效应；无公开可复现基准（客户数据私有）；明确不主张知识图谱、优化或 multi-agent 是新的。
- 我的批判性意见：核心数字（7–9% → <1%、6 周 → 2 周）全部来自非受控观察，且混淆了"架构改进"与"团队学习/工具改进/客户选择变好"，因此不应用于任何量化承诺；论文提出的 context package 优化只有定性描述而无形式化求解，与本文声称的"优化问题"存在落差；LLM provider 细节（Gemini 版本、是否多次采样、温度）几乎完全缺失，使"模型无关"的论断无法验证。

## 评估与建议
- 是否推荐深入阅读：**否**（若只关心方法新颖性）/ **是**（若在做金融、企业级或高风险领域的 LLM 系统工程落地）
- 适用场景：金融/医疗/合规等需要可审计、确定性计算、多租户隔离的 LLM 系统设计；企业级 RAG 与 agent 编排的参考架构；建立"幻觉→校验"分层监控体系的蓝本
- 与知识库的关联：与 RAG/GraphRAG、multi-agent 框架（AutoGen、CrewAI）、金融知识图谱（FIBO）以及审计可追溯性主题直接相关；可作为"结构化高风险领域"类论文对照阅读
